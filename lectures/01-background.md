# 1장. 배경과 문제 정의

## 1.1 폐쇄망 안의 LLM

본 프로젝트가 진행된 환경은 인터넷이 완전히 차단된 사내 폐쇄망입니다. 사내에 LLM 서버가 구축되어 있고, 임직원들은 사내망 내부에서 이 모델을 활용하여 다양한 업무를 수행합니다. 외부 API 연동이나 웹 검색, 공개 패키지 저장소(PyPI 등) 접근은 일절 불가능합니다.

이 모델은 잘하는 작업과 못하는 작업이 매우 뚜렷합니다. 문서를 요약하거나 이메일 초안을 작성하는 일은 곧잘 해냅니다. 하지만 12자리 이상의 곱셈, 정밀한 단위 환산, 3천 행에 달하는 엑셀 데이터의 조건부 합계 계산, 복잡한 PDF 표에서 특정 값을 추출하는 등의 작업을 요청하면 그럴듯한 거짓 숫자(환각 현상)를 지어내곤 합니다. 대형 언어 모델(LLM)은 사전 학습된 가중치를 바탕으로 가장 자연스러운 다음 토큰을 확률적으로 선택할 뿐, 실제로 논리적 수치 계산을 수행하지는 않기 때문입니다. 특히 모델의 파라미터 규모가 작을수록 이러한 계산 실수는 더욱 빈번하게 발생합니다.

인터넷이 연결된 일반적인 환경이라면 널리 알려진 표준 해법이 있습니다. 모델에 코드 인터프리터(Code Interpreter) 도구를 연결하여 실제 계산을 Python 인터프리터에 위임하는 방식입니다. 모델은 "무엇을 어떻게 계산할지"를 Python 코드로 작성하고, 정확한 계산 결과와 데이터 처리는 인터프리터가 담당합니다. 본 프로젝트 역시 궁극적으로는 이와 같은 접근 방식을 취했습니다. 다만 외부망과 완전히 단절된 사내 폐쇄망 환경이었기에, 그 목표에 도달하기까지 해결해야 할 과제들이 결코 단순하지 않았습니다.

## 1.2 서버를 직접 수정할 수 없는 한계

가장 정석적인 접근법은 중앙 LLM 서버 자체에 코드 실행 환경을 구축하여 탑재하는 것입니다. 하지만 실무 사용자나 일반 개발팀에게는 해당 서버에 대한 시스템 관리자 권한은 물론, SSH 접속 권한조차 주어지지 않았습니다. 전사 인프라 관리팀에 정식으로 기능 추가를 요청할 수는 있으나, 보안 심의와 작업 승인을 거치는 데 수개월 이상의 긴 시간이 소요됩니다. 설령 어렵게 기능이 반영된다 하더라도 한 번 배포된 환경은 수정하기가 매우 까다롭습니다. 업무에 필요한 데이터 분석 라이브러리를 하나 추가하려 해도 매번 번거로운 변경 승인 절차를 처음부터 다시 밟아야 합니다.

이러한 상황에서 질문의 방향을 전환했습니다. "원격 서버를 직접 수정할 수 없다면, 우리가 온전히 통제하고 자유롭게 확장할 수 있는 영역은 어디인가?"

## 1.3 사용자 PC라는 우회로

그 해답은 바로 사용자 자신의 업무용 PC였습니다. 사용자들은 PC에 데스크톱 애플리케이션인 AnythingLLM을 설치하여 사용하고 있었으며, 이 앱은 사내 LLM 서버와 OpenAI 호환 API 규격으로 통신하고 있었습니다. 특히 AnythingLLM의 에이전트 기능은 로컬 환경에서 구동되는 MCP(Model Context Protocol) 서버를 외부 도구로 등록하여 연동할 수 있는 표준 메커니즘을 지원합니다.

이 세 가지 요소가 유기적으로 맞물리면서 명확한 해결책이 도출되었습니다. 사용자 PC 내부에서 Python 코드 실행 능력을 갖춘 경량 MCP 서버를 구동하고, 이를 AnythingLLM에 도구로 등록하는 방식입니다. 이렇게 구성하면 LLM 모델 자체는 원격 사내 서버에 그대로 위치하면서도, 수치 계산이나 파일 분석이 필요할 때마다 AnythingLLM을 거쳐 사용자 PC의 로컬 Python 인터프리터에 작업을 위임할 수 있습니다. 중앙의 원격 LLM 서버 환경은 단 한 줄도 수정할 필요가 없습니다.

```
사용자 ─── AnythingLLM (사용자 PC) ─────── 사내 LLM 서버 (원격, 수정 불가)
                 │
                 │  MCP (stdio)
                 ▼
          Python 샌드박스 (사용자 PC, 본 프로젝트)
```

추론과 판단은 원격 LLM이 담당하고, 정확한 계산과 실행은 로컬 Python이 분담하는 협업 구조입니다. 이와 같은 아키텍처 결정의 구체적인 배경과 기술적 트레이드오프는 [ADR-001](adr/adr-001-local-mcp-server.md)에 상세히 기록해 두었습니다.

## 1.4 핵심 요구사항

초기 요구 명세서에서 정의한 핵심 기능은 다음 네 가지로 요약할 수 있습니다.

**상태를 유지하는 실행기 (Stateful Runner).** 사용자가 100MB 크기의 대용량 엑셀 파일을 업로드한 후 "월별 합계를 계산해 줘", "그중 3월 데이터만 차트로 그려 줘", "전년 동기 대비 증감률도 비교해 줘"와 같이 연속적으로 대화를 이어가는 시나리오를 고려해야 합니다. 매 도구 호출마다 새로운 Python 프로세스를 매번 띄운다면 대화가 진행될 때마다 동일한 대용량 파일을 반복해서 다시 읽어야 합니다. 따라서 한 번 메모리에 적재된 데이터와 실행 상태는 대화 세션이 이어지는 동안 안정적으로 유지되어야 합니다.

**완전한 오프라인 동작 (Air-Gapped Operation).** 수치 연산(numpy, scipy, sympy), 정형 데이터 분석(pandas), 시각화(matplotlib, seaborn), 다양한 문서 파싱(PDF, Excel, CSV, XML, JSON, Word, Markdown)에 필요한 필수 패키지들을 사전에 빠짐없이 패키징하여 반입해야 합니다. 타깃 PC는 폐쇄망에 위치하므로 현장에서 `pip install` 명령을 실행할 수 없습니다.

**생성된 산출물 반환 (Artifact Delivery).** 실행된 Python 코드가 차트 이미지 파일이나 가공된 CSV 파일 등의 결과물을 생성하면, LLM의 최종 응답 텍스트에 해당 산출물 파일의 상대 경로와 마크다운 링크가 자동으로 첨부되어야 합니다.

**안전장치와 가용성 보장 (Safety Mechanisms).** 파일 입출력은 사전에 지정된 작업 디렉터리(워크스페이스) 내부로 엄격히 제한되어야 하며, 무한 루프나 블로킹에 빠진 사용자 코드는 설정된 타임아웃 제한 시간을 초과할 경우 시스템 중단 없이 강제로 차단하고 복구할 수 있어야 합니다.

초기 프로젝트 명세는 이를 5단계 개발 로드맵(환경 구성, 상태 유지 코어 엔진, MCP 래퍼 구현, 산출물 자동 탐지, AnythingLLM 클라이언트 연동)으로 정의하였으며, 첫 번째 릴리스인 v0.1.0에서 이 5단계를 모두 성공적으로 구현했습니다.

## 1.5 설계를 좌우한 제약 조건

본 프로젝트는 달성하고자 하는 목표 기능보다 주어진 엄격한 제약 조건들이 시스템의 실제 아키텍처를 결정짓는 핵심 동인이 되었습니다. 아래 표에 정리된 제약 조건들을 염두에 두시면, 후속 장에서 소개되는 수많은 기술적 설계 결정들이 어떤 불가피한 현실에서 비롯되었는지 쉽게 이해하실 수 있습니다.

| 제약 조건 | 아키텍처 및 설계에 미친 영향 |
|---|---|
| 외부 인터넷 연결 불가 | 실행에 필요한 모든 런타임과 라이브러리를 단일 폴더로 패키징하여 오프라인 반입합니다. 별도 OS 설치 과정 없이 압축 해제만으로 즉시 구동되는 포터블 Python(WinPython 기반)을 채택했습니다. |
| 로컬 관리자 권한 부재 | Docker 컨테이너나 전용 OS 서비스 계정 같은 시스템 수준의 강한 격리를 적용할 수 없습니다. 일반 사용자 권한 범위 내에서 안전하게 구동되는 "관습적 샌드박스" 설계를 수용했습니다. |
| 소형 LLM의 추론 능력 한계 | 프롬프트의 텍스트 지침만으로는 도구 사용 오류를 완벽히 통제하기 어렵습니다. 도구 인자의 스키마와 반환 응답 포맷 자체를 모델이 실수하기 어려운 단순한 형태로 설계했습니다. |
| AnythingLLM의 단일 MCP 프로세스 구동 | 여러 개의 채팅 세션이 단 하나의 MCP 서버 프로세스를 공유하므로, 대화 세션 간 변수와 실행 상태가 서로 간섭하지 않도록 네임스페이스별 격리 구조를 구축해야 했습니다. |
| 클라이언트의 60초 타임아웃 강제 제한 | AnythingLLM 클라이언트가 60초 후 응답을 강제 중단하므로, 서버의 모든 작업은 반드시 그 제한 시간보다 여유 있게 짧은 시간 예산(Timeout Budget) 내에 완료되도록 보장해야 했습니다. |
| 대상 운영체제가 Windows 환경임 | Windows 환경에서는 일부 블로킹 시스템 호출이 인터럽트 신호로 즉시 중단되지 않으므로, 프로세스/커널을 강제 재시작하고 복구하는 보조 메커니즘을 필수로 마련해야 했습니다. |

위 표에서 상위 두 가지(인터넷 차단 및 관리자 권한 부재)는 프로젝트 착수 시점부터 이미 인지하고 있던 고정 제약이었습니다. 반면 하위 세 가지 제약은 시스템을 실제로 개발하고 운영하는 과정에서 직접 부딪히며 새롭게 발견한 제약들입니다. AnythingLLM의 단일 프로세스 특성은 v0.3.0의 네임스페이스 격리 설계를 이끌어냈고, 60초 타임아웃 제한은 v0.7.0의 시간 예산 통제 구조를 탄생시켰습니다. Windows 환경의 인터럽트 한계는 첫 릴리스 이전 개발 단계에서 발견되어 v0.1.0부터 이미 대비책을 마련해 두었습니다. 한편 "모델의 성능이 충분하지 않다"는 사실은 초기부터 알고 있었으나, 이 점이 도구 인터페이스 설계에 얼마나 지대한 영향을 미치는지는 점진적인 개발 및 운영 과정을 통해 비로소 명확히 확인하게 되었습니다.

여기서 주목할 점은 v0.1.0 시점에 이미 최초 요구 명세서의 모든 기능 요건을 완벽히 갖춘 상태였다는 사실입니다. 이후에 이루어진 대부분의 변경은 새로운 기능을 무분별하게 확장한 것이 아니라, 실제 운영 환경에서 모델 및 사용자와 상호작용하며 드러난 현실적인 문제들을 하나씩 해결해 나간 과정이었습니다. 특히 v0.4.0과 v0.5.0의 변경은 시스템 코드 자체에 논리적 결함이 있어서 발생한 문제가 아니었습니다. 백엔드 코드는 설계한 규격대로 정상 동작했으나, 소형 LLM이 도구의 실행 결과나 인터페이스를 잘못 해석했기 때문에 발생한 문제였습니다. 이러한 모델 중심의 도구 설계 이야기는 4장에서 더욱 심도 있게 다룹니다.

## 생각해 볼 문제

1. 중앙 LLM 서버에 코드 실행 환경을 집중 구축하는 방식과, 본 프로젝트처럼 사용자 로컬 PC에 분산 배치하는 방식을 비교해 보시기 바랍니다. 만약 동시 사용자 수가 100명 이상으로 증가한다면 각 방식에서 어떤 병목과 운영상 문제가 먼저 발생하겠습니까?
2. "인터넷 연결 불가"와 "관리자 권한 부재"는 모두 환경 구성과 라이브러리 설치를 가로막는 제약입니다. 이 두 가지 제약이 아키텍처 설계와 기술 스택 선정에 각각 어떤 구체적인 차이를 만들어 냈습니까?
3. 프로젝트 변경 이력을 살펴보면 "모델이 도구 인터페이스를 오해하여" 발생한 문제가 상당수를 차지합니다. 이와 같은 문제를 개발 초기 단계에서 선제적으로 발견하고 검증하려면 어떠한 테스트 전략과 시나리오가 필요했겠습니까?
