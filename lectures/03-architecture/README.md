# 3장. 아키텍처

이번 장은 에어갭 Python 샌드박스의 전체 시스템 아키텍처를 다룹니다. 하나의 복잡한 시스템을 상호보완적인 세 가지 관점(View)으로 나누어 체계적으로 기술합니다.

| 아키텍처 뷰 | 답하고자 하는 핵심 질문 | 세부 문서 |
|---|---|---|
| 정적 뷰 (Static View) | 시스템은 어떤 구성 부품들로 이루어져 있으며, 부품 간의 정적 의존 관계는 어떠한가? | [01-static-view.md](01-static-view.md) |
| 동적 뷰 (Dynamic View) | 런타임 실행 중에 부품들이 어떤 순서와 흐름으로 상호작용하며 데이터를 주고받는가? | [02-dynamic-view.md](02-dynamic-view.md) |
| 배포 뷰 (Deployment View) | 부품들이 어떤 물리 머신, 프로세스, 파일시스템 경로에 배치되며, 오프라인 환경에 어떻게 반입되는가? | [03-deployment-view.md](03-deployment-view.md) |

관점을 나누어 기술하는 이유는 단 하나의 다이어그램에 시스템의 모든 복잡성을 한꺼번에 담으려 하면 아무것도 명확하게 전달되지 않기 때문입니다. 예를 들어 "커널 풀(Kernel Pool)"이라는 개념은 정적 뷰에서는 여러 커널 인스턴스를 소유하고 관리하는 독립 컴포넌트로 표현되고, 동적 뷰에서는 사전 기동된 예비 커널을 신규 대화 세션에 즉시 인계하는 실행 시퀀스로 나타나며, 배포 뷰에서는 사용자 PC의 메모리에 동시에 상주하는 최대 9개의 독립 Python 프로세스들로 구체화됩니다. 즉, 동일한 아키텍처 대상을 서로 다른 핵심 질문을 통해 다각도로 조망하는 것입니다.

본 개요 문서에서는 세 가지 뷰가 공통적으로 기반하고 있는 핵심 전제들을 먼저 정리합니다. 설계를 이끈 아키텍처 요구사항과 제약 조건, 다이어그램 표기 규약, 그리고 시스템 전반에서 쓰이는 공통 핵심 용어를 설명해 드립니다.

## 3.1 범위와 기준

- **기준 버전**: v0.7.0
- **분석 대상 범위**: 로컬 MCP 서버 프로세스, 서버가 직접 관리하는 Jupyter 커널 프로세스 풀, 파일 스토리지(작업 워크스페이스 및 사이드 venv), 그리고 오프라인 배포 패키지 번들
- **외부 연동 시스템**: AnythingLLM 데스크톱 애플리케이션, 사내 중앙 LLM 서버, 사내 PyPI 미러 서버

## 3.2 아키텍처 드라이버 (Architecture Drivers)

소프트웨어 아키텍처는 단순한 기능 목록보다 비기능적 품질 속성(Quality Attributes)과 물리적 제약 조건(Constraints)에 의해 훨씬 더 결정적인 영향을 받습니다. 본 시스템을 견인한 핵심 드라이버들을 정리하면 다음과 같습니다.

### 핵심 기능 요구사항

- LLM 에이전트가 임의의 Python 코드를 원격 실행하고 표준 출력/에러 결과를 반환받을 수 있어야 합니다.
- 이전 도구 호출에서 선언된 변수, 임포트된 모듈, 메모리에 로드된 대용량 데이터가 후속 대화에서도 안정적으로 유지되어야 합니다.
- 실행된 코드가 생성하거나 수정한 파일(차트 이미지, 가공된 데이터 파일 등)을 자동으로 탐지하여 마크다운 링크 형태로 반환해야 합니다.
- 워크스페이스 내부의 파일 목록을 조회하고, 임의의 텍스트를 파일로 안전하게 기록하며, 저장된 `.py` 파일을 스크립트 모드로 직접 실행할 수 있어야 합니다.
- 필요한 경우 사내 PyPI 미러 서버로부터 추가 패키지를 동적으로 설치할 수 있어야 합니다(v0.6.0 이후).

### 핵심 품질 속성

| 품질 속성 | 구체적인 시스템 달성 기준 | 대응하는 핵심 설계 결정 |
|---|---|---|
| 응답성 (Responsiveness) | 후속 질문 시 대용량 파일을 반복해서 다시 읽지 않습니다. 신규 대화의 첫 실행 요청 역시 지연 없이 즉시 처리합니다. | 영속 커널([ADR-002](../adr/adr-002-persistent-jupyter-kernel.md)), 사전 기동 예비 커널 풀([ADR-012](../adr/adr-012-kernel-pool-per-namespace.md)) |
| 오프라인 자급성 (Self-Containment) | 외부 인터넷 연결이 완전히 단절된 환경에서도 모든 핵심 기능이 자체적으로 동작합니다. | 독립형 포터블 Python 번들([ADR-004](../adr/adr-004-portable-python-bundle.md)) |
| 가용성 (Availability) | 사용자가 무한 루프 등 어떤 위험한 코드를 실행했더라도, 다음 호출 요청은 반드시 정상 동작하는 깨끗한 커널을 보장받습니다. | 타임아웃 감시 및 프로세스 강제 재시작([ADR-008](../adr/adr-008-conventional-sandbox-timeouts.md)) |
| 격리성 (Isolation) | 서로 다른 대화 세션 간에 변수나 상태가 오염되지 않습니다. 파일 조작 도구는 워크스페이스 경계 외부를 절대 침범하지 않습니다. | 대화별 네임스페이스 격리([ADR-011](../adr/adr-011-namespace-argument.md), [ADR-012](../adr/adr-012-kernel-pool-per-namespace.md)), 엄격한 경로 유효성 검증([ADR-014](../adr/adr-014-write-file-tool.md)) |
| 정직성 (Truthfulness) | 시스템이 완벽히 검증하지 못한 작업 결과를 함부로 '성공'이라고 단정하여 모델에 보고하지 않습니다. | 모호한 성공 제거 및 실행 판정 체계([ADR-017](../adr/adr-017-execution-verdict.md)), 커널 내부 직접 설치 검증([ADR-020](../adr/adr-020-verify-installs-directly.md)) |
| 모델 친화성 (Model Affinity) | 추론 능력이 다소 취약한 소형 LLM이라 할지라도 도구의 규격을 오해하지 않고 정확히 사용하도록 유도합니다. | 도구 설명문 내부 규칙 주입([ADR-007](../adr/adr-007-rules-in-tool-descriptions.md)), 전용 파일 기록 도구 분리([ADR-014](../adr/adr-014-write-file-tool.md)) |
| 복원 용이성 (Reversibility) | 런타임에 동적으로 설치되거나 변경된 모든 요소는 단 하나의 폴더만 삭제하면 초기 깨끗한 상태로 즉시 되돌릴 수 있습니다. | 베이스 환경을 보존하는 사이드 가상환경(venv)([ADR-019](../adr/adr-019-side-venv-installs.md)) |

여기서 '정직성'과 '모델 친화성'은 전통적인 소프트웨어 아키텍처 품질 속성 분류에서는 찾아보기 힘든 매우 독특한 항목입니다. 본 시스템의 직접적인 사용자가 인간 개발자가 아닌 '소형 LLM 에이전트'라는 특수성에서 비롯된 요구사항입니다. LLM이 도구의 반환 결과를 조금이라도 오해하면 그 왜곡된 해석이 최종 사용자에게 여과 없이 전달됩니다. 실제로 v0.4.0 이후 진행된 주요 아키텍처 개선의 대부분은 바로 이 두 가지 품질 속성을 만족시키기 위해 이루어졌습니다.

### 설계 제약 조건

- 대상 PC는 외부 인터넷이 완전히 차단되어 있습니다. 사내망에는 오직 원격 LLM 서버와, 후반에 신설된 사내 PyPI 미러 서버만 존재합니다.
- 사용자는 대상 PC와 중앙 LLM 서버 모두에 대해 관리자(Root/Administrator) 권한을 가지고 있지 않습니다.
- 연동 클라이언트는 AnythingLLM이며, 서버 프로세스를 단 하나만 구동하여 사용자의 모든 대화 창이 이를 공유합니다.
- AnythingLLM 클라이언트는 도구 요청 후 60초가 경과하면 응답을 강제로 취소합니다.
- 대상 운영체제는 Windows 64비트 환경으로 고정되어 있습니다.
- 사내에서 서비스되는 모델은 파라미터가 작고 추론 능력이 제한적인 경량 모델입니다. 긴 지침을 완벽히 기억하지 못하며, 프롬프트나 반환 결과의 도입부와 결론부에 과도하게 의존하는 특성을 보입니다.

## 3.3 C4 모델(C4 Model) 표기법

정적 뷰를 비롯하여 동적 뷰와 배포 뷰의 주요 아키텍처 다이어그램은 Simon Brown이 제안한 C4 모델 표기법을 준용하여 작성했습니다. C4 모델은 복잡한 소프트웨어 구조를 확대 수준(Zoom Level)이 서로 다른 4단계 계층 다이어그램으로 체계화하는 기법입니다. 이는 마치 온라인 지도 서비스에서 국가, 도시, 동네, 개별 건물 순으로 상세도를 점진적으로 좁혀가며 탐색하는 방식과 유사합니다.

| 다이어그램 단계 | 표현하고자 하는 시스템 범위 | 본 아키텍처 문서에서의 반영 |
|---|---|---|
| 1단계: 시스템 컨텍스트 (System Context) | 대상 시스템을 단일 블랙박스로 두고, 주변 사용자 및 외부 연동 시스템과의 관계를 조망합니다. | 정적 뷰 (01-static-view.md) |
| 2단계: 컨테이너 (Container) | 시스템을 구성하는 독립적인 런타임 실행 단위(프로세스) 및 데이터 저장소 단위를 표현합니다. | 정적 뷰 (01-static-view.md) |
| 3단계: 컴포넌트 (Component) | 개별 컨테이너 내부를 구성하는 주요 모듈과 책임 단위를 상세히 기술합니다. | 정적 뷰 (01-static-view.md) |
| 4단계: 코드 (Code) | 개별 클래스, 인터페이스, 함수 수준의 구현 상세를 다룹니다. | (과도한 세부사항이므로 본 문서에서는 생략) |

여기서 C4 모델이 정의하는 "컨테이너(Container)"는 Docker와 같은 OS 수준의 가상화 컨테이너를 의미하는 것이 아니라, 독자적으로 실행되는 프로세스나 독립된 데이터 저장 공간을 뜻합니다. 본 시스템에서는 MCP 서버 프로세스, 개별 Jupyter 커널 프로세스들, 작업 워크스페이스 폴더, 사이드 venv 디렉터리, 그리고 사전 점검 스크립트가 각각 하나의 컨테이너 단위가 됩니다.

또한 C4 모델에는 정적 구조 외에도 특정 비즈니스 흐름을 순차적으로 보여주는 동적 다이어그램(Dynamic Diagram)과, 물리적 인프라 배치를 표현하는 배포 다이어그램(Deployment Diagram)이 보조 표기법으로 포함되어 있습니다. 본 문서에서는 이러한 C4 다이어그램에 더해, 세밀한 조건 분기나 반복 흐름, 프로세스 상태 전이를 명확히 전달하기 위해 시퀀스 다이어그램(Sequence Diagram), 플로우차트(Flowchart), 상태 전이 다이어그램(State Diagram)을 적극적으로 병행하여 수록했습니다.

모든 다이어그램은 표준 Mermaid 문법으로 작성되었습니다. Mermaid의 C4 다이어그램 렌더링은 현재 발전 단계에 있으므로 일부 자동 노드 배치가 다소 투박할 수 있습니다. 상자의 절대적인 시각적 위치보다는 각 블록의 명칭과 화살표에 기술된 상호작용 텍스트를 중심으로 살펴보시기 바랍니다.

## 3.4 공통 핵심 용어 정의

| 핵심 용어 | 정확한 개념 정의 |
|---|---|
| 커널 (Kernel) | 사용자 코드를 실제로 컴파일하고 실행하는 독립된 IPython 프로세스입니다. 대화 세션의 변수와 객체를 메모리에 보존합니다. |
| 네임스페이스 (Namespace) | 사용자의 개별 대화 세션에 1:1로 대응하는 논리적 실행 격리 단위입니다. 네임스페이스마다 고유한 커널이 배정되며, `ns-3fa1`과 같은 고유 ID를 가집니다. |
| 예비 커널 (Pre-warmed Kernel) | 아직 어떤 네임스페이스에도 할당되지 않은 채 백그라운드에 미리 기동해 둔 유휴 커널입니다. 신규 대화가 시작되면 즉시 인계되어 첫 실행 지연(Cold Start)을 방지합니다. |
| 워크스페이스 (Workspace) | 사용자 입력 파일과 분석 산출물 파일이 저장되는 작업 디렉터리입니다. 모든 네임스페이스가 공유하며, 각 커널의 작업 디렉터리(cwd)로 설정됩니다. |
| 산출물 (Artifact) | 코드 실행 과정에서 워크스페이스 내부에 새롭게 생성되거나 내용이 수정된 파일(차트 PNG, 가공된 CSV 등)을 의미합니다. |
| 실행 판정 (Execution Verdict) | 코드 실행 결과를 서버가 신뢰도 등급에 따라 엄격히 평가한 결과입니다. 모델 응답 첫 줄의 `execution_status` 필드에 반영됩니다. |
| 인시던트 기록부 (Incident Ledger) | 일반 try-except 예외 처리로 잡히지 않는 실패(백그라운드 스레드 크래시, 서브프로세스 비정상 종료 등)를 감지하기 위해 커널 내부에 기록하는 특수 감사 로그입니다. |
| 도구 시간 예산 (Tool Time Budget) | 클라이언트의 타임아웃 강제 중단(60초)을 방어하기 위해 도구 호출 하나가 소비할 수 있는 최대 허용 시간입니다. (기본 45초) |

## 3.5 아키텍처 뷰와 의사결정 기록(ADR)의 연계

각 아키텍처 뷰에서 설명하는 구조적 설계와 메커니즘 뒤에는 당시 엔지니어링 팀이 치열하게 고민하고 선택한 근거인 아키텍처 결정 기록(ADR)이 든든하게 뒷받침되어 있습니다. 본문 곳곳에 관련 ADR 링크를 명시해 두었으니, 해당 설계가 도출된 기술적 배경과 포기해야 했던 대안들이 궁금하실 때 언제든지 연계하여 읽어보시기를 권합니다. 전체 ADR 목록과 결정 간의 상관관계도는 [adr/README.md](../adr/README.md)에서 확인하실 수 있습니다.
