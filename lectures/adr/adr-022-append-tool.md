# ADR-022. 이어 쓰기는 쓰기 도구의 모드가 아니라 별도 도구로 추가합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-10-01, v0.8.0

관련 결정: [ADR-006](adr-006-single-text-response.md), [ADR-007](adr-007-rules-in-tool-descriptions.md), [ADR-013](adr-013-shared-workspace.md), [ADR-014](adr-014-write-file-tool.md)

## 맥락 (Context)

[ADR-014](adr-014-write-file-tool.md)는 파일 저장 도구에 이어 쓰기(Append) 모드를 의도적으로 두지 않았습니다. 파일 본문은 모델이 직접 생성한 텍스트이므로 그 크기는 컨텍스트 윈도우가 먼저 제한한다고 보았고, 거의 쓰이지 않을 옵션 인자가 소형 모델의 오호출 위험만 늘린다고 판단했습니다.

이 서버를 멀티 에이전트 토론 플랫폼(MADO)의 코드 실행 도구로 함께 쓰면서 그 판단의 전제가 틀렸다는 것이 드러났습니다.

- 실제 제약은 컨텍스트 윈도우가 아니라 **응답 한 번의 출력 토큰 한도(`max_tokens`)**입니다. 도구 호출의 인자도 그 응답의 일부입니다. 수백~수천 줄의 코드 파일(예: 발표 자료 프레임워크 open-slide의 `index.tsx`는 완성본이 1,000~1,800줄)은 한 번의 호출에 담을 수 없고, 인자가 중간에 잘린 호출은 실패합니다.
- 덮어쓰기 도구로 나누어 쓰면 매 호출마다 앞부분까지 통째로 다시 보내야 합니다. 호출이 점점 커지다 결국 같은 한도에 다시 걸립니다.
- 파일을 여러 개로 쪼개는 우회는 형식이 파일 하나를 요구하면 쓸 수 없습니다.
- 작업 공간을 함께 쓰는 이웃 도구([ADR-013](adr-013-shared-workspace.md)), 즉 공식 filesystem MCP 서버의 `edit_file`은 찾아 바꾸기 도구입니다. 이것으로 "뒤에 덧붙이기"를 시키면 반복되는 줄(`);`, `</div>`)의 **첫 일치 위치**에 새 내용이 끼어들고, 찾을 문자열을 비우면 파일 **맨 앞**에 들어갑니다. MADO에서 실제로 TSX 파일이 이렇게 깨졌습니다.

검토한 선택지는 두 가지였습니다.

- **`write_workspace_file`에 `append` 인자를 추가:** 도구 수는 그대로입니다. 그러나 이미 `overwrite`를 가진 도구에 의미가 겹치는 불리언이 하나 더 붙어(`overwrite`와 `append`를 함께 켜면 무엇인가) ADR-014가 경계한 오호출 위험을 그대로 들여옵니다.
- **별도 도구 `append_workspace_file`:** 이름이 곧 동작입니다. 저장 도구의 인터페이스는 손대지 않습니다.

## 결정 (Decision)

**이어 쓰기는 별도 도구 `append_workspace_file(filename, content)`로 추가합니다.** `write_workspace_file`의 인터페이스는 바꾸지 않으며, 모드 인자를 두지 않는다는 ADR-014의 원칙은 그대로 유지합니다.

- 인자는 두 개입니다. 경로 규칙(`_resolve_new_workspace_path`), 호출당 크기 상한(`SANDBOX_MAX_WRITE_BYTES`), 인코딩(UTF-8, LF 유지)은 저장 도구와 같습니다.
- 파일이 없으면 만듭니다. 내용은 **받은 그대로** 붙이고 조각 사이에 아무것도 끼워 넣지 않습니다. 줄바꿈 없이 끝난 파일에 이어 붙였다면 응답에서 그 사실을 알립니다. 서버가 임의로 줄바꿈을 넣으면, 한 줄을 일부러 이어 쓰는 경우를 망가뜨립니다.
- 응답에는 **파일 끝 8줄을 줄 번호와 함께** 싣습니다(줄당 200자에서 자름). 모델은 자기가 어디까지 썼는지 확인한 뒤 다음 조각을 이어 씁니다. 파일 전체를 돌려주면 출력 한도 문제가 응답 쪽으로 옮겨 갈 뿐입니다.
- 빈 내용은 거부합니다. 아무것도 붙이지 않은 호출을 성공으로 답하면 모델은 썼다고 믿습니다.
- `write_workspace_file`의 설명문에 "파일이 길면 첫 부분만 여기서 쓰고 나머지는 `append_workspace_file`로 덧붙이라"는 한 줄을 넣어 두 도구의 경계를 잇습니다([ADR-007](adr-007-rules-in-tool-descriptions.md)).

## 결과 (Consequences)

**얻게 된 이점**

- 출력 한도보다 긴 파일을 처음부터 끝까지 순서대로 쌓을 수 있습니다. 매 호출의 크기는 조각 하나로 일정합니다.
- 저장 도구는 여전히 인자 세 개의 단순한 인터페이스이므로, 짧은 파일을 저장하는 대부분의 요청에서 소형 모델이 헷갈릴 여지가 늘지 않습니다.
- 응답의 꼬리 줄 덕분에 모델이 조각 경계(중복 전송, 빠뜨린 닫는 괄호)를 스스로 점검할 수 있습니다.

**감수한 비용**

- 도구가 일곱 개로 늘었습니다. 도구 목록 자체가 모든 요청에 실리므로 그만큼 입력 토큰이 늘어납니다.
- 다시 시작할 때 예전 내용 뒤에 이어 붙을 수 있습니다. 처음부터 다시 쓸 때는 `write_workspace_file(overwrite=true)`로 시작해야 하며, 서버는 이를 강제하지 않습니다.
- 같은 조각을 두 번 보내는 실수는 서버가 막지 않습니다. 내용의 의미를 서버가 판단할 수 없으므로, 꼬리 줄을 보여 주는 것까지가 서버의 몫입니다.
- ADR-014의 "컨텍스트 윈도우가 파일 크기를 먼저 제한한다"는 근거는 출력 한도를 놓친 것이었습니다. ADR-014의 결정 자체(모드 인자 없음, 실행하지 않는 저장 전용 도구)는 유효하므로 상태는 "채택됨"으로 두고 이 문서가 보완합니다.
