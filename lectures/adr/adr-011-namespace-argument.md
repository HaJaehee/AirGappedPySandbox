# ADR-011. 대화 구분은 필수 `namespace` 인자와 서버 발급 id로 한다

## 상태 (Status)

채택됨 (Accepted) · 2026-07-25, v0.3.0

관련 결정: [ADR-001](adr-001-local-mcp-server.md), [ADR-012](adr-012-kernel-pool-per-namespace.md), [ADR-013](adr-013-shared-workspace.md)

## 맥락 (Context)

AnythingLLM은 MCP 서버 프로세스를 인스턴스 단위로 하나만 띄운다. 사용자가 대화를 여러 개 열어도 모든 도구 호출이 같은 서버로 들어온다. v0.2.0까지는 커널도 하나였으므로, 모든 대화가 하나의 변수 공간을 나눠 썼다.

두 대화가 우연히 같은 변수 이름(`df`, `data`)을 쓰면 뒤의 대화가 앞의 대화의 값을 덮어쓴다. 실행은 락으로 한 번에 하나씩 처리되므로 메모리 수준의 경쟁 상태는 아니다. 그러나 앞 대화에서 후속 질문을 하면 엉뚱한 데이터로 계산한 답이 돌아온다. 오류 없이 조용히 틀린 답이 나온다는 점에서 가장 나쁜 종류의 버그다.

가장 깔끔한 해법은 프로토콜이 대화 id를 알려 주는 것이다. 그러나 MCP에는 당시 대화 id를 전달하는 표준 필드가 없었고, AnythingLLM도 요청 메타데이터(`_meta`)에 그런 값을 넣지 않았다. stdio 연결은 프로세스 전체에 하나뿐이라 연결 단위로 구분할 수도 없다. 요청 메타데이터에 스레드 id를 싣자는 논의가 여러 MCP 클라이언트 프로젝트에서 진행 중이었지만 당장 쓸 수는 없었다.

검토한 선택지는 다음과 같다.

1. **커널 하나를 그대로 쓴다.** 충돌을 방치한다.
2. **프로토콜의 대화 id를 쓴다.** 지금은 없다.
3. **모델이 스스로 id를 지어 매번 보내게 한다.** 약한 모델은 `"a"`, `"1"`, `"session"` 같은 뻔한 id를 지어 다른 대화와 겹치게 만든다. 컨텍스트가 잘리면 id를 잊고, 가끔은 그냥 빼먹는다. 정확성과 격리가 걸린 불변 조건을 확률적으로 동작하는 부품에 맡기는 셈이다.
4. **필수 인자로 받되 id는 서버가 발급하고, 응답마다 되돌려 준다.**

## 결정 (Decision)

4번을 택한다. 상태를 쓰는 도구(`execute_python_code`, `run_python_file`, `reset_kernel_state`, 그리고 v0.6.0에 추가된 `install_python_packages`)에 필수 인자 `namespace`를 둔다.

네임스페이스는 다음 순서로 정한다.

1. 요청 메타데이터에 대화 id가 있으면 그것을 쓴다. 지금은 항상 비어 있지만, 클라이언트가 보내기 시작하면 코드 수정 없이 바로 쓰인다.
2. 모델이 준 값이 있으면 그것을 쓴다. 영문자, 숫자, 밑줄, 하이픈만 남기고 40자로 자른다.
3. 모델이 `"new"`(또는 빈 값, `"auto"`, `"default"`, `"none"`, `"null"`)를 주면 서버가 `ns-`와 16진수 네 자리로 된 id를 새로 발급한다. 살아 있는 네임스페이스와 겹치지 않는지 확인한다.

모델이 id를 놓치지 않도록 두 겹으로 되풀이한다.

- 입력 쪽: 스키마에서 필수 인자로 만들어, 모델이 호출할 때마다 이 인자를 의식하게 한다. 인자 설명에는 "응답에 나온 값을 그대로 다시 보내라"고 적는다.
- 출력 쪽: 모든 응답의 맨 위에 `active_namespace: ns-XXXX` 배너를, 맨 아래에 "다음 호출에 이 값을 넘겨라"는 재안내를 붙인다. 가장 최근 컨텍스트에 id가 있어야, 앞선 대화가 잘려 나가도 모델이 계속 같은 값을 보낼 가능성이 높다.

## 결과 (Consequences)

**좋아진 점**

- 클라이언트의 도움 없이 대화별 격리를 얻었다. 두 네임스페이스가 모두 `df`를 써도 서로 섞이지 않는다는 것을 검증했다.
- 클라이언트가 대화 id를 보내기 시작하면 자동으로 진짜 대화 단위 격리로 올라간다.
- 서버가 발급한 id라 대화끼리 id가 겹치지 않는다.

**치른 비용**

- 연속성은 모델이 id를 다시 보내는지에 달려 있다. 컨텍스트가 잘려 id를 잃으면 새 네임스페이스가 생기고, 불러 둔 데이터가 사라진 것처럼 보인다.
- 이 완화책은 모델이 약할수록 덜 통한다. 그런데 이 프로젝트가 상대하는 것이 바로 약한 모델이다. 가장 필요한 곳에서 가장 약한 대책이라는 역설을 사용자와 함께 확인하고 받아들였다.
- 모든 실행 호출에 인자가 하나 늘었다.
- 파일은 여전히 공유된다. 격리되는 것은 메모리 안의 변수와 import뿐이다([ADR-013](adr-013-shared-workspace.md)).
