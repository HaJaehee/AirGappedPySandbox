# ADR-011. 대화 세션의 구분은 필수 `namespace` 인자와 서버 발급 ID를 활용합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-07-25, v0.3.0

관련 결정: [ADR-001](adr-001-local-mcp-server.md), [ADR-012](adr-012-kernel-pool-per-namespace.md), [ADR-013](adr-013-shared-workspace.md)

## 맥락 (Context)

AnythingLLM은 MCP 서버 프로세스를 인스턴스 단위로 단 하나만 구동합니다. 사용자가 화면에서 여러 개의 독립된 대화 탭을 열어 동시에 작업하더라도, 발생하는 모든 도구 호출 요청이 단 하나의 로컬 서버 프로세스로 쏟아져 들어옵니다. v0.2.0 이전 버전까지는 시스템 내부에 단 하나의 Jupyter 커널 프로세스만 존재했기 때문에, 모든 대화 세션이 단 하나의 메모리 변수 공간을 위태롭게 공유하고 있었습니다.

만약 두 대화 세션에서 우연히 동일한 변수명(예: `df`, `data`, `result`)을 사용하게 되면, 뒤에 실행된 대화의 코드가 앞선 대화의 변수 값을 메모리에서 조용히 덮어써 버립니다. 비록 커널 락을 통해 물리적 메모리 경쟁 상태(Race Condition)는 방어되었으나, 앞선 대화 탭으로 돌아와 후속 질문을 던지면 전혀 엉뚱한 다른 대화의 데이터로 계산된 오답이 반환되는 치명적인 문제가 발생했습니다. 런타임 오류 없이 정상적인 형태로 틀린 수치를 제시한다는 점에서 가장 위험하고 발견하기 어려운 형태의 버그였습니다.

가장 이상적인 해결책은 MCP 프로토콜이나 클라이언트 앱이 매 도구 호출마다 고유한 "대화 세션 ID"를 헤더나 메타데이터로 실어 보내주는 것입니다. 그러나 당시 MCP 표준 명세에는 대화 ID를 전달하는 표준 규격이 부재했고, AnythingLLM 역시 요청 메타데이터(`_meta`)에 세션 ID를 넣어주지 않았습니다. 또한 표준 입출력(stdio) 파이프 연결은 프로세스당 단 하나뿐이므로 소켓 연결 단위로 대화를 구분할 수도 없었습니다.

당시 검토했던 대안들은 다음과 같습니다.

1. **단일 커널 구조를 그대로 유지합니다.** 대화 간 상태 오염과 데이터 덮어쓰기 결함을 방치합니다.
2. **프로토콜 표준 대화 ID가 지원될 때까지 대기합니다.** 클라이언트 측의 구현 일정이 불투명하여 무기한 지연됩니다.
3. **모델 스스로 대화 ID를 작명하여 매번 인자로 전달하도록 유도합니다.** 소형 모델에게 ID 작명을 맡기면 `"a"`, `"1"`, `"session"`과 같은 단순한 단어를 지정하여 다른 대화 세션과 충돌을 유발합니다. 또한 컨텍스트가 조금만 길어져도 ID를 망각하거나 인자를 누락합니다. 시스템의 데이터 격리라는 불변 조건을 확률적으로 동작하는 LLM에 맡기는 셈이 됩니다.
4. **도구의 필수 인자로 수신하되, ID의 생성과 발급은 서버가 독점 통제하고 매 응답마다 이를 모델에게 주입해 줍니다.**

## 결정 (Decision)

4번 대안을 공식 채택했습니다. 커널 상태를 활용하는 모든 핵심 도구(`execute_python_code`, `run_python_file`, `reset_kernel_state`, 그리고 v0.6.0에 추가된 `install_python_packages`)에 필수(Required) 매개변수로 `namespace` 인자를 신설했습니다.

세션 네임스페이스는 다음의 3단계 우선순위에 따라 결정됩니다.

1. 클라이언트가 요청 메타데이터(`_meta`)에 대화 세션 ID를 실어 보냈다면 이를 최우선으로 채택합니다. (현재는 비어 있으나, 향후 클라이언트가 기능을 지원하기 시작하면 코드 수정 없이 즉시 자동 바인딩됩니다.)
2. 모델이 명시적인 세션 ID를 전달한 경우 이를 채택합니다. 이때 영문 대소문자, 숫자, 밑줄, 하이픈만을 허용하는 엄격한 새니타이징을 거쳐 최대 40자로 정규화합니다.
3. 모델이 `"new"`(또는 빈 문자열, `"auto"`, `"default"`, `"none"`, `"null"`)를 전달한 경우, 서버가 `ns-` 접두사 뒤에 16진수 4자리를 조합한 신규 고유 ID(예: `ns-3fa1`)를 즉시 발급합니다. 현재 활성화되어 있는 기존 네임스페이스와 충돌하지 않는지 엄격히 확인합니다.

소형 모델이 세션 ID를 잊어버리지 않도록 다음과 같은 이중 상기 장치를 마련했습니다.

- **입력 인터페이스**: 도구 스키마에서 필수 인자로 선언하여 모델이 호출할 때마다 세션 ID의 존재를 강하게 의식하도록 유도합니다. 인자 설명문에는 "이전 응답에 출력된 값을 그대로 다시 전달하라"고 명시합니다.
- **출력 인터페이스**: 모든 반환 응답 텍스트의 최상단에 `active_namespace: ns-XXXX` 배너를 고정 배치하고, 최하단에 "다음 호출 시 반드시 이 값을 전달하라"는 리마인더 문구를 반복 출력합니다. 가장 최근 컨텍스트 윈도우에 ID 문자열이 선명하게 노출되어 있어야만, 이전 대화가 잘려 나가더라도 모델이 올바른 세션 ID를 계속 유지할 수 있습니다.

## 결과 (Consequences)

**얻게 된 이점**

- 클라이언트 데스크톱 앱의 직접적인 지원 없이도 대화 세션별 완벽한 메모리 격리를 달성했습니다. 서로 다른 두 대화 창에서 동일하게 `df`라는 변수명을 사용하더라도 메모리가 상호 오염되지 않음을 검증 완료했습니다.
- 향후 AnythingLLM 클라이언트가 대화 ID를 프로토콜로 전달하기 시작하면, 별도의 아키텍처 재설계 없이 즉각 투명한 세션 격리로 자연스럽게 승격될 수 있는 확장성을 확보했습니다.
- 서버가 고유 ID 발급을 독점 통제하므로 세션 ID 간의 우발적인 충돌이 원천 방지됩니다.

**감수한 트레이드오프**

- 대화 세션의 연속성이 모델이 세션 ID를 성실히 되돌려주는지에 전적으로 의존하게 됩니다. 만약 대화가 길어져 컨텍스트가 축소되면서 모델이 ID를 분실하면 새로운 네임스페이스가 생성되어 기존 데이터가 사라진 것처럼 보이는 현상이 발생합니다.
- 이러한 프롬프트 수준의 완화책은 모델의 체급이 작을수록 효과가 반감되는 근본적인 한계가 있습니다. 그러나 이 프로젝트가 상대해야 할 현실의 대상이 바로 그 취약한 소형 모델이라는 점을 인정하고, 이 실용적인 트레이드오프를 수용하기로 결정했습니다.
- 모든 코드 실행 도구 호출마다 매개변수가 하나 더 추가되는 인터페이스 복잡성을 감수해야 합니다.
- 파일시스템 디렉터리는 여전히 모든 세션이 공유합니다. 네임스페이스를 통해 격리되는 영역은 커널 프로세스의 인메모리 변수와 임포트된 모듈 상태로 한정됩니다([ADR-013](adr-013-shared-workspace.md)).
