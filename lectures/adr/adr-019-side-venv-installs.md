# ADR-019. 패키지 설치를 허용하되 별도 venv에 격리한다

## 상태 (Status)

채택됨 (Accepted) · 2026-09-22, v0.6.0

[ADR-004](adr-004-portable-python-bundle.md)를 보완하고, [ADR-007](adr-007-rules-in-tool-descriptions.md)의 설치 금지 규칙을 개정한다.

관련 결정: [ADR-003](adr-003-separate-interpreters.md), [ADR-005](adr-005-snapshot-diff-artifacts.md), [ADR-012](adr-012-kernel-pool-per-namespace.md), [ADR-020](adr-020-verify-installs-directly.md), [ADR-021](adr-021-tool-time-budget.md)

## 맥락 (Context)

사내망에 PyPI 미러가 생겼다. "대상 PC에서는 pip을 쓸 수 없다"는 [ADR-004](adr-004-portable-python-bundle.md)의 전제가 바뀐 것이다. 기본 스택에 없는 라이브러리가 필요할 때마다 빌드 PC에서 다시 패키징하는 부담을 덜 기회였다.

그러나 지켜야 할 것이 있었다.

- **큐레이션한 포터블 Python은 그대로 두어야 한다.** 3.47GB짜리 배포판은 빌드 PC에서 검증한 그대로여야 한다. 여기에 런타임 설치가 섞이면, 잘못된 설치를 되돌리기 어렵고 무엇이 원래 들어 있던 것인지도 알 수 없게 된다.
- **pip의 인자를 모델에게 맡기면 안 된다.** 모델이 인덱스 주소나 설치 옵션을 정하게 하면, 엉뚱한 곳에서 받거나 기본 스택을 망가뜨릴 수 있다.

검토한 선택지는 다음과 같다.

1. **포터블 Python에 직접 설치한다.** 가장 단순하지만 위의 두 가지를 모두 어긴다.
2. **모델이 코드 안에서 pip을 부르게 둔다.** 규칙으로 금지해 온 일이고, 무엇을 어디에 설치하는지 통제할 수 없다.
3. **서버가 관리하는 별도 venv에 설치하는 도구를 만든다.**

## 결정 (Decision)

설치 전용 도구 `install_python_packages(packages, namespace)`를 추가한다.

**설치 위치**

- 패키지는 `SANDBOX_VENV`(기본은 서버 폴더의 `.sandbox-venv`)에 설치한다. 이 venv는 커널을 띄우는 인터프리터로, `--system-site-packages` 옵션을 붙여 만든다. 그래서 기본 스택이 그대로 보이고, pip은 이미 있는 패키지를 다시 받지 않는다.
- venv는 워크스페이스 밖에 둔다. 산출물 탐지기가 매 실행마다 워크스페이스 전체를 비교하므로, 안에 두면 설치된 파일 수천 개가 새 산출물로 보고된다([ADR-005](adr-005-snapshot-diff-artifacts.md)).

**요청 해석**

- `packages`는 배열이 아니라 문자열 하나다. 이름을 공백이나 쉼표로 구분하고, 버전 지정(`rapidfuzz>=3.0`)도 받는다. 작은 모델은 JSON 배열보다 평범한 문자열을 훨씬 안정적으로 만든다.
- 요구 사항 형식(PEP 508)에 맞지 않는 것, 즉 URL, 파일 경로, `-e`, pip 플래그는 pip을 실행하기 전에 어느 토큰이 문제인지 짚어 거절한다. 모델은 패키지만 고르고, 인덱스를 포함한 나머지 pip 인자는 모두 서버가 정한다.
- 한 번에 요청할 수 있는 패키지는 20개까지다.
- 요청한 이름이 모두 버전 지정 없이 적혀 있고 이미 import할 수 있다면 pip을 부르지 않는다.

**설치 후 반영**

- 설치가 끝나면 venv의 패키지 폴더를 살아 있는 모든 커널에 `site.addsitedir`로 붙인다. 커널을 재시작하지 않으므로 다른 대화가 불러 둔 데이터가 살아남는다.
- 새로 뜨는 커널은 시작할 때 이 경로를 자동으로 받는다.

**규칙 개정**

도구 규칙 1번을 "코드 안에서 pip, apt, conda를 쓰지 마라. 목록에 없는 라이브러리가 필요하면 설치 도구를 불러라. 이것이 라이브러리를 추가하는 유일한 방법이다"로 바꾼다.

## 결과 (Consequences)

**좋아진 점**

- 기본 스택에 없는 라이브러리 때문에 다시 패키징할 일이 줄었다.
- 되돌리기가 쉽다. 서버를 끄고 venv 폴더 하나만 지우면 그동안의 모든 설치가 사라진다. 배포판은 처음 반입한 그대로 남는다.
- 설치해도 다른 대화의 작업이 끊기지 않는다.

**치른 비용**

- `site.addsitedir`는 경로를 검색 목록의 뒤에 붙인다. 기본 스택에 이미 있는 패키지는 기본 버전이 계속 이긴다. 이 도구는 패키지를 **추가**할 뿐, 큐레이션한 스택을 **업그레이드**하지 못한다.
- 미러가 런타임 의존성이 되었다. 미러가 없거나 설정이 틀리면 설치 도구는 항상 실패한다. 이 실패를 정확히 알리는 일이 [ADR-020](adr-020-verify-installs-directly.md)의 주제다.
- 필수 패키지는 여전히 포터블 Python에 넣어 둔다. 사전 점검에서 필수 패키지 누락은 계속 치명적 오류로 다룬다. 미러는 정작 필요할 때 닿지 않을 수 있기 때문이다.
- 실제 미러에서 내려받는 과정은 자동 테스트로 확인할 수 없다. 미러가 있는 PC에서 배포할 때 사람이 한 번 직접 확인해야 한다.
- 설치는 오래 걸릴 수 있다. 이것이 곧 클라이언트 제한시간 문제로 이어졌다([ADR-021](adr-021-tool-time-budget.md)).
