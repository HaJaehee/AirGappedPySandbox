# ADR-019. 패키지 동적 설치를 허용하되 원본 런타임을 보호하기 위해 사이드 venv에 격리합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-09-22, v0.6.0

기존 [ADR-004](adr-004-portable-python-bundle.md)를 보완하며, [ADR-007](adr-007-rules-in-tool-descriptions.md)에 주입되어 있던 패키지 설치 절대 금지 규칙을 유연하게 개정합니다.

관련 결정: [ADR-003](adr-003-separate-interpreters.md), [ADR-005](adr-005-snapshot-diff-artifacts.md), [ADR-012](adr-012-kernel-pool-per-namespace.md), [ADR-020](adr-020-verify-installs-directly.md), [ADR-021](adr-021-tool-time-budget.md)

## 맥락 (Context)

사내 폐쇄망 인프라 차원에서 전사 PyPI 미러 서버가 공식 구축되었습니다. 이에 따라 "대상 PC에서는 런타임에 pip을 일절 실행할 수 없다"는 기존 [ADR-004](adr-004-portable-python-bundle.md)의 고정 전제에 근본적인 변화가 생겼습니다. 기본 번들에 포함되지 않은 서드파티 라이브러리가 필요할 때마다 외부 빌드 PC에서 전체 번들을 처음부터 다시 패키징하여 반입해야 했던 무거운 운영 부담을 획기적으로 덜어낼 수 있는 절호의 기회였습니다.

그러나 시스템 무결성을 지키기 위해 타협할 수 없는 두 가지 핵심 원칙이 있었습니다.

- **사전에 철저히 검증된 포터블 Python 베이스 런타임은 결코 오염되어서는 안 됩니다.** 3.47GB에 달하는 검증된 배포판은 현장에서 임의로 수정되지 않고 깨끗이 유지되어야 합니다. 만약 베이스 환경에 런타임 패키지 설치가 무분별하게 뒤섞이면, 잘못 설치된 라이브러리를 이전 상태로 되돌리기가 극히 어려워지며 어떤 패키지가 순정 상태였는지 추적할 수 없게 됩니다.
- **pip의 실행 인자와 설치 옵션 결정을 언어 모델에게 맡겨서는 안 됩니다.** 모델이 인덱스 URL이나 임의의 CLI 플래그를 스스로 지정하게 허용하면, 비인가 서버로 접속을 시도하거나 호스트 시스템 설정을 망가뜨릴 위험이 있습니다.

당시 검토했던 주요 대안들은 다음과 같습니다.

1. **포터블 Python 베이스 환경에 직접 패키지를 설치합니다.** 구현은 가장 단순하지만 위 두 가지 핵심 원칙을 모두 위배하여 장기적으로 환경이 회복 불가능하게 오염됩니다.
2. **모델이 코드 내부에서 `subprocess` 등으로 pip을 직접 실행하도록 방치합니다.** 설명문 규칙으로 금지해 온 위험한 행위이며, 어떤 패키지가 시스템 어디에 설치되는지 전혀 통제할 수 없습니다.
3. **MCP 서버가 전담 관리하는 격리된 사이드 가상환경(venv)을 구축하고 전용 설치 도구를 제공합니다.**

## 결정 (Decision)

독립적인 패키지 동적 설치 전용 도구인 `install_python_packages(packages, namespace)`를 새롭게 신설하기로 결정했습니다.

**격리된 설치 위치**

- 신규 패키지는 환경 변수 `SANDBOX_VENV`(기본값: 서버 디렉터리 내의 `.sandbox-venv`)에 격리 설치합니다. 이 가상환경은 커널을 기동하는 인터프리터를 기반으로 `--system-site-packages` 옵션을 활성화하여 생성합니다. 이를 통해 상위 베이스 Python에 이미 존재하는 대용량 패키지(pandas, numpy 등)들을 투명하게 참조할 수 있으므로, pip은 이미 설치된 패키지를 중복 다운로드하지 않고 즉시 재사용합니다.
- 사이드 venv 디렉터리는 워크스페이스 경계 바깥에 독립 배치합니다. 산출물 탐지기가 매 도구 실행마다 워크스페이스 전체를 스캔하므로, 만약 venv가 워크스페이스 내부에 존재한다면 패키지 설치 시 생성되는 수천 개의 라이브러리 내부 파일이 전부 "새로운 사용자 산출물"로 오인되어 LLM 프롬프트에 쏟아져 컨텍스트 윈도우를 낭비하는 문제가 발생하기 때문입니다([ADR-005](adr-005-snapshot-diff-artifacts.md)).

**도구 요청 인자의 정규화 및 보안 검증**

- `packages` 인자는 복잡한 JSON 배열이 아닌 단순한 단일 텍스트 문자열로 수신합니다. 패키지명을 공백이나 쉼표로 자연스럽게 구분하며, 표준 버전 조건식(`rapidfuzz>=3.0`, `polars<2.0`)도 유연하게 지원합니다. 소형 언어 모델은 JSON 배열보다 평범한 텍스트 문자열을 훨씬 더 안정적으로 생성합니다.
- PEP 508 표준 규격에 부합하지 않는 임의의 입력(외부 URL, 파일시스템 로컬 경로, 편집 가능 설치 옵션 `-e`, 기타 pip CLI 플래그)은 pip 명령을 실행하기 전에 서버 계층에서 어떤 토큰이 잘못되었는지 정확히 짚어내어 사전 거절합니다. 모델은 오직 설치할 패키지 명칭과 버전만을 선택하며, 미러 인덱스 URL을 포함한 모든 pip 실행 인자는 서버가 엄격히 독점 통제합니다.
- 단일 호출에서 한 번에 요청할 수 있는 패키지 개수는 최대 20개로 제한합니다.
- 요청된 모든 패키지에 버전 지정이 없고 현재 커널 환경에서 이미 정상 임포트가 가능한 상태라면 불필요한 pip 실행을 생략하는 고속 경로(Fast-Path)를 적용합니다.

**실행 중인 커널 세션에 대한 무중단 동적 반영**

- 설치가 성공적으로 완료되면 사이드 venv의 패키지 설치 경로를 현재 활성화되어 있는 모든 Jupyter 커널 프로세스들의 모듈 검색 경로(`sys.path`)에 `site.addsitedir()`를 통해 즉시 주입합니다. 커널 프로세스를 재부팅하지 않으므로 다른 대화 세션의 사용자들이 작업 중이던 메모리 데이터는 안전하게 보존됩니다.
- 이후 새롭게 부팅되는 모든 커널 프로세스는 기동 초기화 시점에 이 경로를 자동으로 주입받습니다.

**도구 설명문 규칙의 공식 개정**

도구 설명문의 1번 규칙을 "코드 실행 중 pip, apt, conda를 직접 호출하지 마십시오. 기본 목록에 없는 신규 패키지가 필요하다면 `install_python_packages` 전용 도구를 호출하십시오. 이것이 샌드박스에 패키지를 안전하게 추가할 수 있는 유일한 공식 경로입니다"로 개정했습니다.

## 결과 (Consequences)

**얻게 된 이점**

- 기본 번들에 포함되지 않은 특수 라이브러리가 필요할 때마다 외부 빌드 PC에서 전체 번들을 번거롭게 재패키징하여 반입 심의를 거쳐야 했던 운영 오버헤드를 획기적으로 해소했습니다.
- 시스템 환경의 복원 및 초기화가 극도로 간편합니다. MCP 서버를 종료한 후 배포 디렉터리 내의 `.sandbox-venv` 폴더 하나만 삭제하면 그동안 추가 설치되었던 모든 외부 패키지가 말끔히 제거되고, 시스템은 최초 오프라인 반입 당시의 순정 상태로 즉시 완벽 복원됩니다.
- 패키지를 동적으로 설치하더라도 다른 대화 세션의 기존 분석 작업이나 메모리 데이터가 중단되지 않습니다.

**감수한 트레이드오프**

- `site.addsitedir()` 함수는 주입된 신규 경로를 모듈 검색 우선순위 목록의 가장 뒤편에 추가합니다. 따라서 베이스 포터블 환경에 이미 사전 탑재되어 있는 기존 라이브러리는 언제나 원본 버전이 우선적으로 로드됩니다. 즉, 본 도구는 새로운 패키지를 **추가**하는 기능만을 제공할 뿐, 기본 번들에 내장된 기존 패키지의 버전을 상향 **업그레이드**하지는 못합니다.
- 사내 PyPI 미러 서버가 시스템의 중요한 런타임 외부 의존성으로 편입되었습니다. 미러 서버가 일시 장애 상태이거나 설정이 잘못되어 있으면 패키지 설치 도구는 항상 실패하게 됩니다. 이러한 네트워크 실패의 근본 원인을 모델과 사용자에게 투명하게 알리는 방안이 후속 [ADR-020](adr-020-verify-installs-directly.md)의 핵심 주제가 되었습니다.
- 기본 핵심 패키지들은 여전히 오프라인 포터블 Python 번들에 사전 설치하여 유지합니다. 사전 점검 도구에서도 필수 패키지의 누락은 계속해서 치명적 실패로 다룹니다. 사내 미러 서버는 네트워크 사정에 따라 정작 필요한 순간에 도달하지 못할 위험이 있기 때문입니다.
- 실제 사내 미러로부터 패키지를 다운로드하는 과정은 단위 자동화 테스트 스위트의 범위를 벗어납니다. 미러가 존재하는 사내망 PC에 배포할 때 엔지니어가 수동으로 최종 실측 테스트를 수행해야 합니다.
- 패키지 다운로드 및 설치는 수십 초 이상의 긴 시간이 소요될 수 있습니다. 이로 인해 AnythingLLM 클라이언트의 60초 타임아웃 제한과 충돌하는 문제가 즉각 대두되었습니다([ADR-021](adr-021-tool-time-budget.md)).
