# ADR-018. 검증식(`expect`) 인자를 추가하여 모델에게 객관적으로 "검증된 성공"을 요구합니다

## 상태 (Status)

**제안됨 (Proposed)** · 2026-09-22 설계 완료, 정식 릴리스 전 미구현 상태

[ADR-017](adr-017-execution-verdict.md) 설계 당시 계획했던 5단계 로드맵 중 3단계였으나, 도구의 입력 JSON 스키마를 직접 확장해야 하는 중대한 변경이 수반되어 별도의 독립 릴리스 과제로 분리했습니다.

관련 결정: [ADR-017](adr-017-execution-verdict.md)

## 맥락 (Context)

[ADR-017](adr-017-execution-verdict.md)을 통해 시스템은 스스로 완벽히 검증하지 못한 작업 결과를 함부로 '성공'이라 부르지 않도록 개편되었습니다. 그러나 여전히 물리적으로 메울 수 없는 관측의 사각지대가 존재합니다.

- 사용자 코드가 `try: ... except: pass` 구문으로 치명적 예외를 자체적으로 집어삼켜 버리면 서버는 백그라운드 실패를 감지할 방법이 없습니다.
- 코드가 문법적으로는 예외 없이 끝까지 돌았으나, 비즈니스 계산 공식이 틀려 전혀 엉뚱한 오답을 산출했는지 여부는 런타임 서버가 판단할 수 없습니다.

결과적으로 현재 시스템의 최상위 판정 등급은 `RAN_UNVERIFIED`("검증되지 않은 실행")에 머무르게 됩니다. 이는 지극히 정직한 태도이지만, 한편으로는 언어 모델이 실제로 사용자의 지시를 100% 완벽히 수행해 낸 경우에도 그 성공을 객관적으로 공인해 줄 수단이 부재하다는 아쉬움을 남깁니다.

## 결정 (Decision)

(향후 로드맵 제안) 코드 실행 도구에 선택적(Optional) 매개변수로 **`expect` 검증식 인자**를 추가하기로 제안했습니다.

- 모델은 코드 실행 결과가 성공했다고 확신할 수 있는 논리적 단언식을 단 한 줄의 Python 표현식으로 작성하여 동봉합니다. (예: `len(df) == 1200`, `Path('chart.png').exists()`, `'total' in df.columns`)
- 서버는 본 사용자 코드를 실행한 직후, 동일한 커널 세션 메모리에서 이 검증식 표현식을 독립된 셀로 조용히 평가합니다.
- 평가 결과에 따라 다음과 같이 고도화된 판정 등급을 부여합니다.

| 판정 코드 | 판정 조건 및 의미 |
|---|---|
| `VERIFIED_OK` | 본 코드가 예외 없이 실행되었으며, 모델이 제출한 검증식 조건문 역시 참(True)으로 완벽히 입증되었습니다. |
| `FAILED` (check failed) | 본 코드는 실행되었으나, 모델이 제출한 검증식이 거짓(False)으로 평가되어 과업이 실패했습니다. |
| `CHECK_ERROR` | 검증식 표현식 자체를 평가하는 도중 런타임 문법 오류나 NameError 예외가 발생했습니다. |

- 만약 모델이 `expect` 인자를 전달하지 않고 생략했다면, 기존과 동일하게 최상위 판정은 `RAN_UNVERIFIED`로 유지됩니다.
- 도구 설명문에 간결하고 명확한 1줄 검증식 작성 예시들을 주입하여 소형 모델도 손쉽게 따라 할 수 있도록 유도합니다.

핵심 원리는 "과업의 성공"이라는 긍정적 단어를 서버가 공짜로 제공하지 않고, **모델 스스로 객관적인 증거를 시스템에 제출하여 엄격히 검증받았을 때만 부여**하는 것입니다. 비즈니스 성공을 의미하는 단어는 본 판정 체계가 정식 도입될 때 시스템 반환 응답에 최초로 등장하게 됩니다.

## 결과 (Consequences)

현재 정식 구현 전 제안 상태이므로 아래 내용은 기대 효과 및 예상 리스크 분석입니다.

**기대하는 이점**

- 코드 내부에서 삼켜진 예외나 잘못된 비즈니스 계산이라 할지라도, 모델이 유의미한 검증식을 작성했다면 실패가 수면 위로 즉각 드러납니다.
- 최종 사용자에게 "요청하신 과업을 성공적으로 완료했습니다"라고 당당히 보고할 수 있는 시스템 차원의 객관적 근거가 마련됩니다. 사용자는 시스템 판정만을 보고도 분석 결과를 높은 신뢰도로 수용할 수 있습니다.

**예상되는 비용과 기술적 과제**

- 도구의 공식 입력 JSON Schema가 변경됩니다. AnythingLLM 클라이언트가 도구 목록을 다시 수집해야 하며, 도구 설명문의 토큰 길이도 다소 늘어납니다.
- 검증식을 평가하는 내부 프로브 셀이 추가되므로 매 호출마다 커널 왕복 오버헤드가 증가합니다.
- 추론 능력이 다소 부족한 소형 모델이 판정 통과만을 노리고 `assert True`나 `1 == 1`과 같은 무의미한 항진식을 남발할 위험이 있습니다. 서버가 검증식의 시맨틱 유효성까지 완벽히 판단하기는 어려우므로, 설명문과 양질의 예시를 통해 양심적인 작성을 유도하는 엔지니어링이 선행되어야 합니다. 이 위험을 억제할 수 있는 구체적인 가드레일은 향후 구현 단계에서 추가로 논의해야 합니다.

**본 ADR이 주는 엔지니어링 교훈**

제안(Proposed) 상태의 ADR 역시 매우 높은 문서화 가치를 지닙니다. 이 기능을 왜 당장 구현하지 않고 보류했는지(스키마 변경에 따른 영향도 분리), 무엇을 기대하고 있으며 어떤 잠재적 리스크를 경계하고 있는지가 상세히 기록되어 있으면, 차기 프로젝트 개발자가 그 맥락을 즉시 이어받아 완성도 높은 구현을 이어갈 수 있습니다.
