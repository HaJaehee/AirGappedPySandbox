# ADR-010. 스크립트 실행은 `__main__` 의미론을 따르되 실행 결과를 커널 메모리에 유지합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-07-23, v0.2.0 채택 · 2026-09-22, v0.5.0에서 내부 실행 메커니즘 전면 개정

관련 결정: [ADR-002](adr-002-persistent-jupyter-kernel.md), [ADR-014](adr-014-write-file-tool.md), [ADR-017](adr-017-execution-verdict.md)

## 맥락 (Context)

사용자가 워크스페이스에 저장된 `.py` 파일을 가리키며 "이 스크립트를 직접 실행해 줘"라고 요청하는 시나리오가 빈번히 발생합니다. 만약 일반 코드 실행 도구만을 사용해야 한다면 모델이 `runpy.run_path()`나 `exec()`를 호출하는 복잡한 보일러플레이트 코드를 직접 작성해야 하는데, 추론 능력이 취약한 소형 모델은 이러한 코드 래핑 과정에서 잦은 실수를 범합니다.

실무 사용자가 스크립트 파일 실행 도구에 기대하는 동작은 다음 두 가지 핵심 요건입니다.

- 명령줄에서 `python script.py`로 직접 실행할 때처럼 파일 하단의 `if __name__ == "__main__":` 블록이 누락 없이 정상 가동되어야 합니다.
- 스크립트 파일의 실행이 끝난 뒤, 해당 파일 내부에 정의된 함수와 생성된 데이터 변수들을 후속 대화에서 그대로 메모리에서 재사용할 수 있어야 합니다.

### v0.2.0 초기 설계와 한계

v0.2.0 당시에는 표준 라이브러리인 `runpy`를 사용하여 스크립트를 독립된 `__main__` 네임스페이스로 실행한 뒤, 실행이 완료되면 반환된 결과 딕셔너리를 커널의 전역 네임스페이스에 후처리로 병합(Merge)하는 방식을 취했습니다.

### v0.5.0에서 발견된 심각한 결함

`runpy`는 스크립트가 인터프리터 예외 없이 정상 반환되어야만 결과 네임스페이스 딕셔너리를 돌려줍니다. 그러나 일반적인 Python 스크립트에서 가장 표준적으로 사용하는 관용구인 `sys.exit(main())` 패턴은 내부적으로 `SystemExit` 예외를 던집니다. 이 예외가 발생하면서 결과 네임스페이스를 커널 전역에 병합하는 단계가 실행되지 못하고 건너뛰어지면서 다음과 같은 이중 결함이 발생했습니다.

- 지극히 정상적으로 실행을 마친 스크립트가 심각한 런타임 에러로 모델에 보고되었습니다. IPython 인터프리터가 `SystemExit`를 오류로 간주하기 때문입니다.
- 스크립트 내부에 선언된 함수와 변수들이 커널 메모리에 단 하나도 병합되지 않고 모두 증발했습니다. 도구 설명문에서 "실행 후에도 최상위 함수와 변수가 메모리에 안전하게 남는다"고 모델에게 약속했던 계약이 완전히 깨진 것입니다.

실제로 `sys.exit(main())`으로 끝나는 스크립트를 실행한 직후 커널 메모리에서 `'main' in globals()`를 확인해 보면 `False`가 반환되는 심각한 결함이 있었습니다.

## 결정 (Decision)

v0.5.0부터 취약한 `runpy` 모듈을 완전히 폐기했습니다. 대신 대상 스크립트 파일의 소스코드를 디스크에서 직접 읽어 들여 파싱 및 컴파일한 후, 백엔드 커널 프로세스의 전역 네임스페이스(Global Scope)에서 직접 순차 평가하는 방식으로 전면 재설계했습니다.

- IPython 커널의 전역 스코프는 모듈명(`__name__`)이 기본적으로 `"__main__"`으로 설정되어 있으므로 `if __name__ == "__main__":` 블록이 자연스럽게 정상 실행됩니다.
- 함수와 변수는 바인딩되는 즉시 전역 공간에 등록됩니다. 따라서 스크립트가 중간에 `sys.exit()`를 호출하여 종료되거나 런타임 예외로 중단되더라도, 그 직전 시점까지 정의된 모든 함수와 변수들은 커널 메모리에 온전히 보존됩니다.
- 스크립트가 실행되는 동안 임시로 `__file__` 및 `sys.argv[0]` 변수를 해당 스크립트 파일의 실제 경로로 세팅해 주고, 실행이 완료되면 원래 값으로 안전하게 복원합니다.
- `SystemExit` 예외를 시스템 차원에서 가로채어 종료 코드를 추출합니다. 추출된 리턴 코드가 0이거나 생략된 경우 정상 종료로 판정하고, 0이 아닌 에러 코드인 경우에만 비로소 `FAILED` 등급으로 올바르게 판정합니다([ADR-017](adr-017-execution-verdict.md)).

아울러 파일 경로와 확장자에 대한 보안 검사는 커널 프로세스에 코드를 전송하기 전 MCP 서버 계층에서 선제적으로 수행합니다.

- 대상 파일이 디스크에 반드시 실재해야 하며, 정규화된 물리 경로가 워크스페이스 경계 내부여야 합니다.
- 파일 확장자가 반드시 `.py`여야 합니다(v0.4.0부터 강제 적용).
- 입력 경로는 `fib.py`, `./workspace/fib.py`, 워크스페이스 내부의 절대 경로 등 다양한 표기법을 유연하게 수용합니다.

## 결과 (Consequences)

**얻게 된 이점**

- 명령줄 스크립트 본연의 실행 의미론(`__main__` 블록 실행, `sys.exit` 종료 코드 존중)과 대화형 환경의 장점인 '실행 상태 영속성'을 완벽하게 동시에 달성했습니다.
- `sys.exit(0)`을 호출하여 정상 종료된 스크립트가 더 이상 에러로 잘못 보고되지 않습니다.
- 파일 저장 전용 도구와 완벽한 시너지를 이룹니다. 모델은 "코드 저장"과 "스크립트 실행"이라는 두 단계의 단순한 도구 호출만으로 복잡한 스크립트 기반 작업을 안정적으로 완수할 수 있게 되었습니다([ADR-014](adr-014-write-file-tool.md)).

**감수한 트레이드오프**

- 스크립트 파일의 최상위 전역 변수명이 기존 네임스페이스 세션에 이미 존재하던 동일한 이름의 변수를 덮어쓸 수 있습니다. 예를 들어 스크립트 내부에서 사용된 임시 변수 `df`가 이전 대화에서 사용자가 메모리에 로드해 두었던 분석 데이터프레임 `df`를 대체할 수 있습니다.
- `__file__`과 `sys.argv`는 실행 후 원래대로 복원되지만, 스크립트 코드가 실행 도중 변경한 기타 런타임 전역 상태(예: `os.chdir`을 통한 작업 디렉터리 임의 변경, 서드파티 모듈의 전역 옵션 수정 등)는 커널 세션에 그대로 잔류합니다.
- 순수 라이브러리 모듈로서의 임포트(즉, `__main__` 실행 블록을 실행하지 않고 순수 함수 정의만 가져오는 방식)는 현재 직접 지원하지 않습니다. 필요할 경우 향후 선택적 인자로 추가하는 방안을 로드맵 과제로 관리하고 있습니다.
