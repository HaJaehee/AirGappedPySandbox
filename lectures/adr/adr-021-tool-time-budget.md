# ADR-021. 모든 도구 호출은 클라이언트 타임아웃 제한 시간보다 여유 있게 먼저 응답합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-09-22, v0.7.0

관련 결정: [ADR-008](adr-008-conventional-sandbox-timeouts.md), [ADR-012](adr-012-kernel-pool-per-namespace.md), [ADR-019](adr-019-side-venv-installs.md), [ADR-020](adr-020-verify-installs-directly.md)

## 맥락 (Context)

사내 PyPI 미러 서버가 정상 동작하는 업무용 PC 환경에서 기이한 장애 리포트가 접수되었습니다. OS 셸 콘솔에서 `pip install` 명령을 직접 실행하면 패키지가 정상 다운로드되고, 미러 관련 환경 변수 2종도 바르게 설정되어 있었습니다. 그러나 AnythingLLM 화면에서 패키지 설치 도구를 호출하면 매번 "Context server request timeout"이라는 오류만 출력되며 작업이 중단되었습니다.

이 오류 메시지는 MCP 서버가 반환한 것이 아니라, AnythingLLM 데스크톱 앱이 강제로 출력한 에러였습니다. MCP 클라이언트가 요청을 스스로 취소했다는 뜻입니다. MCP 클라이언트 SDK의 기본 요청 타임아웃 제한 시간은 60초인데, 샌드박스의 설치 도구는 백그라운드 pip 프로세스가 완전히 끝날 때까지 서버 응답을 무작정 붙잡고 있었습니다. 설상가상으로 최초 1회 호출 시에는 사이드 venv 디렉터리를 최초 생성하는 I/O 오버헤드까지 겹쳤습니다. 포터블 Python 환경에서 venv를 생성하는 작업은 단독으로도 수십 초가 소요될 수 있습니다.

그로 인해 다음과 같은 심각한 사용자 경험(UX) 저하가 발생했습니다.

- 아무런 이상이 없는 사내 미러 서버가 마치 심각한 고장이 난 것처럼 오인되었습니다.
- 백그라운드에서는 pip 설치 작업이 보이지 않게 계속 진행되고 있었으나, LLM 모델은 그 최종 결과를 확인할 방법이 영구히 차단되었습니다.
- 최종 사용자는 서버가 생성한 친절한 진단 메시지를 전혀 보지 못한 채, 클라이언트의 불친절한 한 줄짜리 타임아웃 에러만 마주하게 되었습니다.

구조를 면밀히 조사해 보니 동일한 잠재적 결함이 코드 실행 도구(`execute_python_code`)에도 도사리고 있었습니다. 단일 코드 실행 제한 기본값이 60초로 설정되어 있어 클라이언트의 요청 타임아웃(60초)과 완전히 동일했습니다. 장시간 연산 셀이 실행될 때 서버의 깔끔한 `TIMEOUT` 판정 응답으로 정돈될지, 아니면 클라이언트의 불투명한 강제 연결 중단으로 끝날지가 실행 타이밍에 따라 갈리는 위험한 경쟁 상태(Race Condition)였습니다.

## 결정 (Decision)

**대원칙: 시스템의 어떤 도구 호출도 사전에 할당된 도구 시간 예산(`SANDBOX_TOOL_BUDGET`, 기본 45초)을 초과하여 응답을 지연시키지 않습니다.** 클라이언트의 타임아웃 제한(60초)이 시스템 전체의 실질적인 마감선(Deadline)입니다. 서버 내부의 모든 I/O 및 대기 시간은 반드시 이 시간 예산 아래로 엄격히 통제되어야만, 사용자에게 전달되는 실패 메시지가 언제나 서버가 작성한 친절한 진단 설명문이 되도록 보장할 수 있습니다.

이 핵심 원칙에 따라 다음과 같은 아키텍처 개편을 단행했습니다.

1. **패키지 설치 작업을 백그라운드 워커 스레드로 전면 위임합니다.** 도구 함수는 메인 루프를 블로킹하지 않고 설치 스레드를 기동한 뒤, 0.5초 주기로 타이머를 폴링하며 시간 예산이 소진될 때까지만 대기합니다. 만약 45초 이내에 작업이 끝나지 않으면 즉시 `install_status: RUNNING` 상태를 반환합니다. 응답에는 "결코 실패가 아니며 백그라운드에서 정상 진행 중이다"라는 사실을 명시하고, 잠시 후 다시 호출할 수 있도록 동일한 `packages` 문자열과 `namespace` 인자를 정확히 되돌려 줍니다.
2. **동일한 설치 요청은 단일 백그라운드 작업으로 안전하게 합류(Task Coalescing)시킵니다.** 진행 중인 설치 태스크는 패키지 목록을 정렬한 문자열을 키(Key)로 삼아 레지스트리에 등록됩니다. 모델이 동일한 인자로 도구를 다시 호출하면 새로운 pip을 중복 실행하지 않고 이미 진행 중인 기존 작업의 완료를 대기합니다. 이 구조가 보장되어야만 모델에게 "안심하고 동일한 인자로 다시 호출하라"고 안전하게 지시할 수 있습니다. 최종 결과를 수거하면 레지스트리에서 등록을 해제하여 향후 재설치가 가능하도록 합니다.
3. **클라이언트에 실시간 진행률 알림(Progress Notification)을 전송합니다.** 설치를 대기하는 동안 5초 주기로 FastMCP 컨텍스트를 통해 진행 알림을 전송합니다. 일부 고도화된 클라이언트는 이 알림을 수신하면 타임아웃 제한 시간을 능동적으로 연장해 줍니다. 다만 클라이언트 연장은 보조 수단일 뿐이며, 근본적인 방어선은 서버의 45초 시간 예산입니다.
4. **사이드 venv는 서버 프로세스가 최초 기동하는 시점에 사전 생성합니다.** 서버 부팅 시 예비 커널 준비와 병렬로 venv를 미리 빌드해 둡니다. 이를 통해 첫 번째 패키지 설치 도구 호출이 venv 생성 오버헤드를 떠안지 않도록 완벽히 방어했습니다.
5. **단일 코드 실행 제한 기본값을 기존 60초에서 45초(`SANDBOX_EXEC_TIMEOUT=45`)로 하향 조정했습니다.** 더 긴 연산 시간이 불가피하게 필요하다면 코드 실행 제한, 도구 예산, 그리고 클라이언트 자체의 타임아웃 제한까지 세 가지 값을 함께 상향 조정해야 합니다.
6. **다른 세션의 커널을 대기하느라 시간 예산을 소진하지 않습니다.** 패키지 설치 완료 후 활성화된 모든 커널 프로세스에 venv 경로를 주입할 때, 개별 커널당 락 획득 대기 시간을 최대 5초로 엄격히 제한합니다. 장시간 연산을 수행 중인 특정 네임스페이스 때문에 전체 패키지 설치 도구의 시간 예산이 고갈되는 연쇄 지연을 차단합니다. 5초 내에 갱신하지 못한 커널은 응답 텍스트에 안내되며, 해당 커널은 다음 유휴 시점에 자동으로 경로를 전달받습니다.
7. **도구 설명문 내부에 `RUNNING` 상태의 의미와 대처 가이드를 명시했습니다.** 모델이 직접 읽는 도구 설명문 안에 "RUNNING은 실패가 아니며, 동일한 인자로 즉시 재호출해야 한다"는 행동 지침을 추가했습니다.

시스템 내 시간 값들 사이의 수학적·논리적 포함 관계는 다음과 같이 엄격히 정립됩니다.

```
코드 실행 타임아웃 (SANDBOX_EXEC_TIMEOUT: 45초)
  ≤ 도구 허용 시간 예산 (SANDBOX_TOOL_BUDGET: 45초)
  < 클라이언트 강제 취소 제한 시간 (AnythingLLM: 60초)
```

## 결과 (Consequences)

**얻게 된 이점**

- 사용자가 화면에서 마주하는 모든 에러는 이제 클라이언트의 불친절한 타임아웃 메시지가 아니라, 서버가 정돈하여 작성한 친절한 원인 진단 설명문이 됩니다.
- 사내 미러 서버의 다운로드 속도가 다소 느리더라도 타임아웃 중단 없이 정상적으로 대용량 패키지를 설치할 수 있게 되었습니다. 모델은 `RUNNING` 상태를 수신한 뒤 안내에 따라 재호출하여 안전하게 최종 결과를 수거합니다.
- 긴 연산 코드가 실행 제한을 초과하더라도 클라이언트의 강제 취소에 걸리지 않고 항상 서버의 정돈된 `TIMEOUT` 판정 응답으로 정상 마무리됩니다.

**감수한 트레이드오프**

- 대용량 패키지 설치 시 모델이 도구를 2회 이상 연속 호출해야 작업이 최종 완료되는 워크플로 지연을 감수해야 합니다. 만약 약한 모델이 재호출 지침을 따르지 않고 대화를 끝내버리면 백그라운드 설치는 성공했으나 결과를 아무도 수거하지 않은 고아 태스크로 남게 됩니다. (다만 이후 동일한 패키지 설치 요청이 다시 들어오면 즉시 결과가 전달됩니다.)
- 진행 중인 설치 태스크 레지스트리는 서버 메모리에만 상주합니다. 만약 설치 도중 MCP 서버 프로세스가 강제 재시작되면 진행 중이던 작업의 결과를 정상 수거할 수 없습니다.
- 시간 관련 환경 변수 3종(`SANDBOX_EXEC_TIMEOUT`, `SANDBOX_TOOL_BUDGET`, 클라이언트 타임아웃)을 항상 세트로 일관되게 관리해야 합니다.

**뒤늦게 발견하여 일괄 바로잡은 설정 동기화**

v0.7.0 릴리스 당시 소스코드 상의 기본값은 45초로 올바르게 수정되었으나, AnythingLLM 설정 예제 JSON 파일, 수동 실행 스크립트, 공식 사용자 배포 매뉴얼, 그리고 내부 위키 문서에는 과거의 레거시 값인 `SANDBOX_EXEC_TIMEOUT=60`이 그대로 방치되어 있었습니다. 사용자는 기본값에 의존하기보다 문서의 예제 설정을 그대로 복사하여 사용하는 경우가 많으므로, 이 불일치를 방치했다면 본 ADR이 해결하고자 했던 60초 타임아웃 경합 버그가 현장에서 다시 되살아났을 것입니다. 본 교육자료를 정밀 검토하는 과정에서 이 누락을 발견하여 2026-09-24에 관련 10개 파일의 예제 값들을 모두 45초로 일괄 동기화했습니다. 기본값을 변경할 때는 해당 값을 담고 있는 모든 문서와 설정 예시들을 전수 조사하여 함께 수정해야 한다는 중요한 교훈을 남겼습니다.

**테스팅 엔지니어링 기법**

단위 테스트는 수 분이 걸리는 실제 pip 다운로드를 실행하지 않습니다. 백그라운드 스레드에서 정밀한 지연을 시뮬레이션하여, 도구 인터페이스가 메인 루프를 블로킹하지 않고 45초 이내에 `RUNNING`을 반환하는지, 백그라운드 작업이 고아가 되지 않는지, 동일 인자 재호출 시 결과를 안전하게 수거하는지, 수거 후 레지스트리가 깨끗이 비워지는지, 그리고 바쁜 커널을 무한정 대기하지 않는지를 정밀 검증합니다. 이 리팩토링 과정에서 기존 비동기 테스트 중 일부가 `await` 누락으로 인해 사실상 단언문을 검증하지 못하고 있었다는 결함도 함께 발견하여 완벽히 수정했습니다.

**본 ADR이 주는 엔지니어링 교훈**

타임아웃은 시스템의 가장 바깥쪽 계층(클라이언트)이 일방적으로 결정합니다. 따라서 내부 하위 계층들의 모든 허용 시간은 반드시 상위 바깥 계층의 제한 시간보다 여유 있게 짧아야만, 장애가 발생했을 때 가장 상세한 원인 정보를 알고 있는 내부 시스템이 사용자에게 구체적인 실패 원인을 전달할 수 있는 마지막 기회를 확보할 수 있습니다.
