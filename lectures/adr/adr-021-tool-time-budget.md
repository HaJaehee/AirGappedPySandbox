# ADR-021. 모든 도구 호출은 클라이언트 제한시간보다 먼저 응답한다

## 상태 (Status)

채택됨 (Accepted) · 2026-09-22, v0.7.0

관련 결정: [ADR-008](adr-008-conventional-sandbox-timeouts.md), [ADR-012](adr-012-kernel-pool-per-namespace.md), [ADR-019](adr-019-side-venv-installs.md), [ADR-020](adr-020-verify-installs-directly.md)

## 맥락 (Context)

미러가 정상인 PC에서 이상한 보고가 들어왔다. 셸에서 `pip install`을 직접 하면 잘 되고, 미러 관련 환경 변수도 둘 다 설정되어 있었다. 그런데 설치 도구를 부르면 매번 "Context server request timeout"으로 끝났다.

이 문구는 서버가 쓴 것이 아니라 AnythingLLM의 것이다. MCP 클라이언트가 요청을 취소했다는 뜻이다. MCP 클라이언트 SDK의 기본 요청 제한은 60초인데, 설치 도구는 pip이 끝날 때까지 응답을 붙잡고 있었다. 게다가 첫 호출에서는 venv를 만드는 비용까지 함께 치렀다. 포터블 Python에서 venv 생성은 수십 초가 걸릴 수 있다.

그 결과는 이랬다.

- 멀쩡한 미러가 고장 난 것처럼 보였다.
- 설치는 보이지 않는 곳에서 계속 진행되었지만, 모델은 그 결말을 알 방법이 없었다.
- 사용자가 본 오류 메시지는 서버의 설명이 아니라 클라이언트의 짧은 문구뿐이었다.

살펴보니 같은 문제가 코드 실행에도 숨어 있었다. 실행 제한 기본값이 60초로, 클라이언트 제한과 똑같았다. 긴 셀은 서버의 깔끔한 `TIMEOUT` 판정으로 끝날지, 클라이언트의 불투명한 취소로 끝날지 운에 맡겨져 있었다.

## 결정 (Decision)

**원칙: 어떤 도구 호출도 도구 예산(`SANDBOX_TOOL_BUDGET`, 기본 45초)보다 오래 응답을 미루지 않는다.** 클라이언트의 인내심이 진짜 마감이다. 서버의 모든 대기 시간을 그 아래에 둬야 사용자가 보는 실패가 언제나 서버가 쓴 설명이 된다.

이 원칙에 따라 다음을 바꿨다.

1. **설치는 백그라운드 스레드에서 한다.** 도구는 설치를 시작한 뒤 0.5초 간격으로 확인하며 예산이 다할 때까지만 기다린다. 그 안에 끝나지 않으면 `install_status: RUNNING`으로 답한다. 응답에는 "실패가 아니다, 설치는 뒤에서 계속된다"고 분명히 적고, 다시 보낼 `packages` 문자열과 `namespace`를 정확히 적어 준다.
2. **같은 요청은 같은 작업에 합류한다.** 설치 작업은 패키지 목록을 정렬한 문자열을 열쇠로 등록한다. 모델이 같은 인자로 다시 부르면 두 번째 pip을 띄우지 않고 진행 중인 작업을 기다린다. 이 성질이 있어야 모델에게 "다시 불러라"고 안전하게 말할 수 있다. 결과를 거두면 등록을 지워, 나중에 같은 설치를 다시 할 수 있게 한다.
3. **진행 알림을 보낸다.** 기다리는 동안 5초마다 진행 알림을 보낸다. 이 알림을 받으면 제한시간을 연장하는 클라이언트도 있다. 다만 알림은 덤일 뿐, 실제 방어책은 예산이다.
4. **venv는 서버가 시작할 때 만든다.** 예비 커널 준비와 나란히 한다. 첫 설치 호출이 venv 생성 비용을 치르지 않게 한다.
5. **실행 제한 기본값을 60초에서 45초로 줄인다.** 더 긴 셀이 필요하면 실행 제한, 도구 예산, 클라이언트 제한을 함께 올려야 한다.
6. **남의 커널을 무한정 기다리지 않는다.** 설치 후 모든 커널에 경로를 붙일 때, 커널마다 최대 5초만 락을 기다린다. 전에는 긴 셀을 돌리는 네임스페이스 하나가 다른 사람의 설치 예산을 통째로 써 버릴 수 있었다. 갱신하지 못한 네임스페이스는 응답에 적고, 그 커널은 다음에 시작할 때 경로를 받는다.
7. **도구 설명문에 `RUNNING`의 뜻과 대처를 적는다.** 모델이 실제로 읽는 곳에 "실패가 아니다, 같은 인자로 다시 불러라"를 넣었다.

시간 값 사이의 관계는 다음과 같이 정리된다.

```
코드 실행 제한 (45초) ≤ 도구 예산 (45초) < 클라이언트 요청 제한 (60초)
```

## 결과 (Consequences)

**좋아진 점**

- 사용자가 보는 실패는 언제나 서버가 쓴 설명이다. "Context server request timeout"이 더는 원인을 가리지 않는다.
- 느린 미러도 정상적으로 쓸 수 있다. 모델은 `RUNNING`을 받고 다시 불러 결과를 거둔다.
- 코드 실행의 제한시간 초과도 항상 서버의 `TIMEOUT` 판정으로 끝난다.

**치른 비용**

- 느린 설치는 모델이 한 번 더 불러야 끝난다. 약한 모델이 다시 부르지 않으면 설치는 끝났는데 결과를 아무도 모르는 상태로 남는다. 다음에 같은 요청이 오면 그때 결과가 전달된다.
- 설치 작업 목록은 서버 메모리에만 있다. 서버가 재시작되면 진행 중이던 작업의 결과를 거둘 수 없다.
- 시간 값 세 개를 함께 관리해야 한다. 하나만 올리면 원칙이 깨진다.

**뒤늦게 정리한 것**

v0.7.0에서 코드의 기본값은 바뀌었지만, AnythingLLM 설정 예시, 수동 실행 스크립트, 사용자 문서와 위키의 예시에는 `SANDBOX_EXEC_TIMEOUT`이 `60`으로 남아 있었다. 사용자는 기본값보다 예시를 복사하는 경우가 많으므로, 그대로 두었다면 이 ADR이 막으려던 경합이 설정을 통해 되살아났을 것이다. 교육자료를 만들며 발견해 2026-09-24에 모두 45로 맞췄다. 기본값을 바꿀 때는 그 값을 적어 둔 예시까지 함께 찾아 바꿔야 한다.

**시험 방법**

테스트는 pip을 실제로 돌리지 않는다. 느린 설치를 흉내 내고, 도구가 막히지 않고 `RUNNING`으로 답하는지, 작업이 뒤에서 계속되는지, 다시 부르면 결과를 거두는지, 거둔 뒤 등록부가 비는지, 바쁜 커널을 기다리지 않는지를 확인한다. 확인하려는 것이 설치가 아니라 응답이기 때문이다. 이 작업 중에 기존 테스트 일부가 비동기 함수를 `await`하지 않아 사실상 아무것도 확인하지 않고 있었다는 사실도 드러나 함께 고쳤다.

**이 ADR에서 배울 점**

타임아웃은 가장 바깥쪽 계층이 결정한다. 내부 계층의 제한시간은 반드시 바깥 계층의 제한시간보다 짧아야 하며, 그래야 실패를 설명할 권한이 가장 많은 정보를 가진 쪽에 남는다.
