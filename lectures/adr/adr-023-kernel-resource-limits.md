# ADR-023. 커널별 OS 자원 상한 옵션 도입 (파일 및 네트워크 격리 제외)

## 상태 (Status)

채택됨 (Accepted) · 2026-11-02, v0.10.0

관련 결정: [ADR-002](adr-002-persistent-jupyter-kernel.md), [ADR-008](adr-008-conventional-sandbox-timeouts.md), [ADR-012](adr-012-kernel-pool-per-namespace.md), [ADR-015](adr-015-pin-mcp-sdk-1x.md), [ADR-021](adr-021-tool-time-budget.md)

## 맥락 (Context)

[ADR-008](adr-008-conventional-sandbox-timeouts.md)에서는 OS 수준의 격리를 구축하려면 관리자 권한이나 추가 소프트웨어 설치가 불가피하다고 판단하여, 현실적인 대안으로 '관례적 샌드박스' 모델을 채택했습니다. 시스템 가용성은 엄격한 실행 시간 제한(타임아웃)과 비정상 커널의 강제 재시작을 통해 확보했습니다. 그러나 시간 제한만으로는 완전히 방어할 수 없는 다음과 같은 한계들이 존재했습니다.

- **메모리 폭주**: 단일 코드 셀이 메모리를 무한정 할당할 경우, 타임아웃 제한에 도달하기 전에 호스트 OS가 심각한 페이징(스왑)에 빠지게 됩니다. 이로 인해 동일한 PC에서 구동 중인 호스트 애플리케이션(AnythingLLM, MADO 등) 전체가 함께 응답 불능 상태에 빠집니다.
- **자식 프로세스 대량 생성**: 자식 프로세스를 끝없이 분기(fork/spawn)하는 코드를 억제할 수단이 부재했습니다.
- **커널 외부의 CPU 독점**: 메인 실행 스레드가 아닌 백그라운드 스레드나 별도 자식 프로세스에서 회전하는 무한 루프에는 인터럽트 신호가 전달되지 않습니다.
- **고아 프로세스 잔류**: Windows 환경에서 jupyter_client의 프로세스 종료(kill) 로직은 최상위 커널 프로세스만 종료합니다. 호스트가 본 MCP 서버를 종료할 때도 서버 프로세스만 종료되므로, 커널이 구동했던 자식 프로세스들은 시스템에 고아 프로세스로 영구히 잔류하는 문제가 있었습니다.

본 서버를 멀티 에이전트 토론 플랫폼(MADO) 등의 코드 실행 백엔드로 활용하면서 이러한 취약점의 위험성이 한층 부각되었습니다. 사람의 직접적인 모니터링 없이 다수의 에이전트 커널이 동시에 동작하는 환경에서는, 단 하나의 커널에서 발생한 자원 폭주가 시스템 전체와 다른 세션의 대화까지 마비시킬 수 있기 때문입니다.

이에 따라 ADR-008의 기본 전제를 재검토했습니다. Windows의 Job Object와 Linux의 rlimit 메커니즘은 관리자 권한이나 추가 패키지 설치 없이도 일반 사용자 권한으로 즉시 사용할 수 있습니다.

검토한 선택지는 다음과 같이 세 가지였습니다.

- **파일 및 네트워크까지 전면 격리**: Linux에서는 bubblewrap, Windows에서는 Low 무결성 수준(Low Integrity Level), 제한 토큰(Restricted Token), AppContainer 등을 활용하는 방식입니다. 프론티어 코딩 도구들(Claude Code, Codex CLI 등)의 로컬 샌드박스가 이 방식을 취하고 있습니다. 그러나 Windows 환경에서 파일 읽기 권한까지 완전히 통제하려면 다음 중 하나가 필수적입니다.
  - 관리자 권한을 활용해 전용 OS 계정을 생성하고 전용 방화벽 규칙을 적용하는 방법
  - AppContainer 환경 적용 (이 경우 커널과 MCP 서버 간의 루프백 ZeroMQ 통신을 허용하기 위해 관리자 권한의 루프백 예외 등록이 요구됨)

  관리자 권한 없이 구현 가능한 Low 무결성 수준은 파일 쓰기만을 차단할 뿐이며, 그마저도 사용자 작업 디렉터리에 무결성 레이블을 영구적으로 부여해야 하는 번거로움이 있습니다. 이는 단일 사용자 로컬 PC를 전제로 하는 ADR-008의 현실적인 위협 모델에 비해 과도한 비용이었습니다.
- **커널별 OS 자원 상한 적용**: 메모리, 프로세스 수, CPU 우선순위, 자식 프로세스 자동 정리에 한하여 OS 수준의 제약을 적용하는 방식입니다. 관리자 권한이나 파일 권한 수정이 일절 필요 없습니다. 따라서 이 방식을 최종 채택하기로 결정했습니다.
- **서버 전체 합산 상한 및 호스트 차원의 자원 예산 분할**: 구현 복잡도를 고려하여 초기 단계에서는 적용하지 않기로 했습니다.

## 결정 (Decision)

**`SANDBOX_ISOLATION=limits` 설정 시 각 커널에 OS 자원 상한을 적용합니다. 기본값은 `off`입니다.** 미확인 값이 지정된 경우 시스템 보호를 위해 `limits`로 간주하여 처리하고 경고 로그를 남깁니다. 이는 사용자가 `on`, `strict` 등 더 강력한 격리를 의도하고 설정했을 가능성을 고려한 조치입니다.

- **Windows**: 커널마다 익명 Job Object를 하나씩 생성합니다. Job 핸들은 MCP 서버 프로세스만 보유하므로, 커널 내부 코드가 임의로 상한을 해제하거나 우회할 수 없습니다.
  - **커밋 메모리 합계 상한(`JOB_MEMORY`)**: 커널 및 그 하위 자식 프로세스가 사용하는 커밋 메모리의 총합을 제한합니다. 상한 초과 시 메모리 할당이 실패하여 Python의 `MemoryError`가 발생하며, 대개의 경우 커널 프로세스와 기존 변수 상태는 안전하게 보존됩니다.
  - **동시 활성 프로세스 수(`ACTIVE_PROCESS`)**: 동시에 유지 가능한 프로세스 수를 제한합니다 (기본값: 32개).
  - **낮은 CPU 우선순위(`BELOW_NORMAL`)**: 커널이 CPU를 100% 점유하더라도 호스트 시스템과 UI가 원활하게 응답합니다.
  - **오류 대화상자 억제(`DIE_ON_UNHANDLED_EXCEPTION`)**: 비정상 종료 시 윈도우 오류 보고(WER) 팝업 창이 뜨지 않도록 하여 무인 자동화 환경에서 프로세스가 멈추는 현상을 방지합니다.
  - **Job 종료 시 자식 정리(`KILL_ON_JOB_CLOSE`)**: 커널을 종료하거나 재시작할 때 `TerminateJobObject`를 통해 모든 자식 프로세스를 일괄 종료합니다. 서버 프로세스가 예기치 않게 종료되어 Job 핸들이 닫힐 때도 동일하게 자식 프로세스들이 자동 정리됩니다.
  - **기동 동기화**: 커널을 **일시 정지 상태(`CREATE_SUSPENDED`)로 기동한 직후** Job Object에 배정하고 실행을 재개합니다. venv 환경의 `python.exe`는 수 밀리초 내에 실제 인터프리터를 기동하는 경량 런처 프로세스이므로, 런처가 종료되기 전에 Job에 할당하지 못하면 실제 커널 프로세스가 자원 상한 적용 범위에서 누락될 위험이 있기 때문입니다.
- **Linux**: 커널 프로세스 기동 직후 서버가 `prlimit`을 통해 커널의 `RLIMIT_DATA`를 소프트 및 하드 리밋 모두에 적용하고, CPU 스케줄링 우선순위를 nice 10으로 낮춥니다. 하드 리밋까지 함께 낮추므로 커널이 임의로 상한을 다시 높일 수 없으며, 이후 생성되는 자식 프로세스에도 동일한 상한이 상속됩니다. (단, Linux의 `RLIMIT_NPROC`는 개별 프로세스 트리가 아닌 시스템 사용자 단위로 프로세스 수를 계산하므로 프로세스 수 상한은 적용하지 않습니다.)
- **연결 지점**: `KernelManager`의 서브클래스(`SandboxKernelManager`)를 정의하여 `_async_launch_kernel` 및 `_async_cleanup_resources` 메서드를 오버라이드합니다. 커널 재시작(`restart_kernel`)은 자체 `_launch_locked`를 거치지 않으므로, 최초 기동과 재시작이 모두 통과하는 이 두 메서드에 자원 제약 로직을 연결해야 합니다. 이는 내부 비공개(private) API에 의존하는 것이므로, [ADR-015](adr-015-pin-mcp-sdk-1x.md)와 동일한 맥락에서 `jupyter_client<9` 버전을 엄격히 고정합니다.
- **메모리 기본값 산정**: 물리 메모리의 25%를 기본값으로 하되, **numpy 라이브러리가 정상 import될 수 있는 최소 하한선**(512 MB + 스레드당 64 MB) 밑으로는 내려가지 않도록 보정합니다.
  - numpy를 import할 때 내부의 OpenBLAS 라이브러리가 스레드별 작업 버퍼를 미리 할당합니다. 20스레드 CPU 환경 기준 Windows 커밋 메모리와 Linux `RLIMIT_DATA` 모두 약 1.2 GB의 메모리를 선점합니다.
  - 이 초기 버퍼 할당에 실패하면 Python `MemoryError`를 정상 처리하지 못하고 **프로세스가 강제 종료**됩니다. 메모리 상한이 이 하한선보다 낮게 설정되면 샌드박스 전체가 기동 불가 상태에 빠지게 됩니다.
  - 환경 변수를 통해 MB 단위의 정수를 명시적으로 지정한 경우에는 해당 값을 그대로 존중하되, 최소 하한선 미만일 경우 경고 로그를 출력합니다.
- **실행 중 커널 비정상 종료(사망) 즉시 감지 (격리 옵션 활성화 여부와 무관)**: iopub 채널 메시지를 대기하는 동안 백엔드 커널 프로세스가 예기치 않게 종료되면, 타임아웃 제한 시간까지 불필요하게 대기하지 않고 즉각 결과를 반환합니다.
  - 실행 판정은 `FAILED`이며, `error_name`은 `KernelDied`로 기록됩니다.
  - 기존에는 프로세스가 이미 크래시되었음에도 타임아웃 제한 시간까지 무의미하게 대기한 뒤 `TIMEOUT`으로 오판하던 문제가 있었습니다.
  - 반환 메시지에 "The kernel had to be restarted" 문구를 명시하여, 호스트(AnythingLLM 등)가 커널 메모리 상태가 유실되었음을 정확히 인지할 수 있도록 합니다.
- **상태 보고**: 적용된 자원 상한 내역은 서버 기동 시 stderr 로그로 한 줄 요약 출력됩니다 (stdout은 MCP 통신 전용 채널이므로 오염 방지). 아울러 `check_environment.py` 스크립트는 테스트 커널을 직접 기동하여 해당 커널에 실제 OS 자원 상한이 정상 적용되었는지를 실시간으로 검증합니다.

## 결과 (Consequences)

**얻게 된 이점**

- 특정 커널에서 메모리 폭주, 자식 프로세스 대량 생성, CPU 독점이 발생하더라도 해당 피해가 그 커널 내부에 격리됩니다. 호스트 PC 및 다른 대화 세션의 커널은 안정적인 응답성을 계속 유지합니다.
- 메모리 상한을 초과한 코드 셀은 `MemoryError` 예외와 함께 안전하게 중단되며, 커널 프로세스와 기존에 로드된 변수 상태는 유지됩니다. LLM은 데이터를 청크 단위로 분할하여 재시도하라는 후속 조치 안내를 받게 됩니다.
- Windows 환경에서 커널이 생성했던 하위 자식 프로세스들이 커널 재시작, 세션 종료, MCP 서버 프로세스 강제 종료 시 예외 없이 완벽하게 자동 정리됩니다.
- 시스템 관리자 권한, 추가 소프트웨어 설치, 파일시스템 권한 변경 등의 부담이 일절 발생하지 않습니다.

**감수한 비용과 기술적 한계**

- 파일시스템 및 네트워크 격리는 여전히 관례적 샌드박스 수준으로 유지됩니다. 실행 코드는 현재 사용자의 OS 권한으로 접근 가능한 모든 로컬 파일을 읽고 쓸 수 있으며, 사내망 내부로 네트워크 소켓을 생성할 수 있습니다. ADR-008에서 수용한 트레이드오프가 그대로 유효합니다.
- 자원 상한은 개별 커널 단위로 적용됩니다. 다수의 커널이 동시에 상한에 근접하여 자원을 소비할 경우 전체 사용량은 (개별 상한 × 활성 커널 수)에 달할 수 있으므로, 동시 세션 상한(`SANDBOX_MAX_NAMESPACES`)과 함께 종합적으로 설계해야 합니다.
- Linux 환경의 `RLIMIT_DATA` 메커니즘에는 다음과 같은 구조적 한계가 존재합니다.
  - 프로세스 단위로 적용되므로, 새로 생성되는 자식 프로세스마다 동일한 크기의 상한을 독립적으로 부여받습니다.
  - 실제 물리 메모리 점유량(RSS)이 아닌 예약된 가상 주소 공간 크기를 기준으로 제한합니다.
  - 프로세스 생성 수 자체를 차단하지 못하며, 자식 프로세스 정리는 프로세스 그룹 시그널에 의존하므로 `setsid()` 등을 통해 새 세션으로 분리된 자식 프로세스는 잔류할 수 있습니다.
- Windows venv 환경의 `python.exe`는 런처와 실제 인터프리터 총 2개 프로세스로 동작하므로, 최대 프로세스 수 상한은 최소 2 이상으로 유지되어야 합니다.
- 메모리 할당 실패 시 Python 수준의 `MemoryError`를 발생시키지 못하고 비정상 종료되는 네이티브 C 확장의 경우, 커널 프로세스가 크래시될 수 있습니다. 이 경우 커널 사망 감지 로직이 즉시 `KernelDied` 상태로 포착하여 후속 복구를 유도합니다.
- jupyter_client의 내부 비공개(private) 메서드를 오버라이드하므로, 향후 jupyter_client의 메이저 버전 업그레이드 시 해당 메서드 시그니처의 변경 여부를 철저히 검증해야 합니다.
