# ADR-023. 커널마다 OS 자원 상한을 거는 선택 옵션을 둡니다 (파일·네트워크 격리는 하지 않습니다)

## 상태 (Status)

채택됨 (Accepted) · 2026-11-02, v0.10.0

관련 결정: [ADR-002](adr-002-persistent-jupyter-kernel.md), [ADR-008](adr-008-conventional-sandbox-timeouts.md), [ADR-012](adr-012-kernel-pool-per-namespace.md), [ADR-015](adr-015-pin-mcp-sdk-1x.md), [ADR-021](adr-021-tool-time-budget.md)

## 맥락 (Context)

[ADR-008](adr-008-conventional-sandbox-timeouts.md)은 OS 수준 격리에 관리자 권한이나 추가 소프트웨어가 필요하다고 보고 관례적 샌드박스를 택했습니다. 가용성은 실행 시간 제한과 강제 재시작으로 지켰습니다. 그런데 시간 제한이 막지 못하는 경우가 남아 있었습니다.

- **메모리 폭주**: 셀 하나가 메모리를 끝없이 잡으면 시간 제한에 닿기 전에 호스트가 스왑에 빠집니다. 같은 PC 에서 도는 호스트 앱(AnythingLLM, MADO)도 함께 멈춥니다.
- **자식 프로세스 대량 생성**: 자식을 끝없이 띄우는 코드를 막을 수단이 없었습니다.
- **커널 밖의 CPU 독점**: 스레드나 자식 프로세스 안에서 도는 무한 루프에는 인터럽트가 닿지 않습니다.
- **고아 프로세스**: Windows 에서 jupyter_client 의 kill 은 커널 프로세스 하나만 끝냅니다. 호스트가 이 서버를 끝낼 때도 서버 프로세스만 끝납니다. 그래서 커널이 띄운 자식은 어느 경우에도 남습니다.

이 서버를 멀티 에이전트 토론 플랫폼(MADO)의 코드 실행 도구로 쓰면서 이 빈틈의 무게가 커졌습니다. 여러 에이전트의 커널이 사람이 지켜보지 않는 동안 동시에 돌기 때문에, 한 커널의 폭주가 호스트와 다른 대화를 함께 멈춥니다.

ADR-008 의 전제도 다시 보았습니다. Windows Job Object 와 Linux rlimit 은 관리자 권한도 설치도 필요 없습니다.

검토한 선택지는 세 가지였습니다.

- **파일·네트워크까지 격리**: Linux 는 bubblewrap, Windows 는 Low 무결성 수준, 제한 토큰, AppContainer 를 씁니다. 프론티어 코딩 앱(Claude Code, Codex CLI)의 로컬 샌드박스가 이쪽입니다. 그러나 Windows 에서 읽기까지 막으려면 둘 중 하나가 필요합니다.
  - 관리자 권한으로 전용 사용자 계정과 방화벽 규칙을 만드는 방법.
  - AppContainer. 이 경우 커널과 서버를 잇는 loopback ZeroMQ 에 관리자 예외가 필요합니다.

  관리자 권한 없이 할 수 있는 Low 무결성 수준은 쓰기만 막습니다. 그마저도 사용자 작업 폴더에 무결성 레이블을 영구로 붙여야 합니다. 단일 사용자 PC 라는 ADR-008 의 위협 모델에 비해 과합니다.
- **커널마다 자원 상한만**: 메모리, 프로세스 수, CPU 우선순위, 자식 정리. 관리자 권한도 파일 권한 변경도 필요 없습니다. 이 선택지를 택했습니다.
- **서버 전체 합계 상한과 호스트 쪽 예산 분할**: 첫 단계에서는 하지 않습니다.

## 결정 (Decision)

**`SANDBOX_ISOLATION=limits` 이면 커널마다 OS 자원 상한을 겁니다. 기본값은 `off` 입니다.** 알 수 없는 값은 보호 쪽으로 해석해 `limits` 로 다루고 경고합니다. `on`, `strict` 처럼 더 강한 것을 원한 경우이기 때문입니다.

- **Windows**: 커널마다 이름 없는 Job Object 를 하나 둡니다. 핸들은 서버만 쥐므로 커널 코드가 상한을 풀 수 없습니다.
  - 커널과 그 자식의 커밋 메모리 합(`JOB_MEMORY`). 넘으면 할당이 실패해 `MemoryError` 가 나고, 대개 커널과 변수는 그대로 남습니다.
  - 동시에 살아 있는 프로세스 수(`ACTIVE_PROCESS`). 기본값은 32 입니다.
  - 낮은 우선순위(`BELOW_NORMAL`). 커널이 CPU 를 다 써도 호스트가 응답합니다.
  - 충돌 대화상자를 띄우지 않습니다(`DIE_ON_UNHANDLED_EXCEPTION`). 무인 실행이 WER 창에서 멈추지 않게 하기 위해서입니다.
  - `KILL_ON_JOB_CLOSE`. 커널을 내리거나 재시작할 때 `TerminateJobObject` 로 자식까지 끝냅니다. 서버가 죽으면 핸들이 닫히면서 같은 일이 일어납니다.
  - 커널은 **일시 정지 상태(`CREATE_SUSPENDED`)로 띄운 뒤** Job 에 넣고 재개합니다. venv 의 `python.exe` 는 몇 밀리초 안에 실제 인터프리터를 띄우는 런처인데, 그 전에 배정하지 못하면 실제 커널이 상한 밖으로 빠집니다.
- **Linux**: 띄운 직후 서버가 커널에 `RLIMIT_DATA` 를 soft 와 hard 모두에 걸고(`prlimit`), 우선순위를 nice 10 으로 낮춥니다. hard 값까지 낮추므로 커널이 다시 올릴 수 없고, 이후 띄우는 자식도 이 값을 물려받습니다. 프로세스 수 상한은 두지 않습니다. `RLIMIT_NPROC` 는 커널이 아니라 사용자 전체의 프로세스를 셉니다.
- **연결 지점**: `KernelManager` 의 서브클래스(`SandboxKernelManager`)가 `_async_launch_kernel` 과 `_async_cleanup_resources` 를 오버라이드합니다. 재시작(`restart_kernel`)은 우리의 `_launch_locked` 를 거치지 않으므로, 시작과 재시작이 모두 지나는 이 두 메서드에 걸어야 합니다. private API 라서 [ADR-015](adr-015-pin-mcp-sdk-1x.md)와 같은 이유로 `jupyter_client<9` 로 고정합니다.
- **메모리 기본값**: 물리 메모리의 25% 이되, **numpy 가 import 될 수 있는 하한**(512 MB + 스레드당 64 MB) 아래로는 내려가지 않습니다.
  - numpy 를 import 할 때 OpenBLAS 가 스레드마다 버퍼를 미리 잡습니다. 20스레드 PC 에서 Windows 커밋 메모리와 Linux `RLIMIT_DATA` 모두 약 1.2 GB 였습니다.
  - 이 버퍼를 잡지 못하면 `MemoryError` 를 내는 대신 **프로세스를 끝냅니다**. 하한보다 낮으면 샌드박스가 고장 난 것처럼 보입니다.
  - MB 로 직접 적은 값은 그대로 따르고 경고만 합니다.
- **실행 중 커널 사망 감지** (격리 여부와 무관): iopub 메시지를 기다리는 동안 커널 프로세스가 사라지면 곧바로 결과를 돌려줍니다.
  - 판정은 `FAILED` 이고 `error_name` 은 `KernelDied` 입니다.
  - 지금까지는 시간 제한까지 기다린 뒤 `TIMEOUT` 으로 잘못 보고했습니다.
  - 문구에 "The kernel had to be restarted" 를 넣습니다. 호스트가 이 문구로 커널 상태 유실을 판단합니다.
- **상태 보고**: 적용된 상한은 서버 시작 시 stderr 에 한 줄로 남깁니다. stdout 은 MCP 채널이기 때문입니다. `check_environment.py` 는 커널 하나를 띄워, 그 커널이 실제로 상한 안에 있는지 확인합니다.

## 결과 (Consequences)

**얻게 된 이점**

- 한 커널의 메모리 폭주, 자식 프로세스 대량 생성, CPU 독점이 그 커널 안에서 끝납니다. 호스트와 다른 대화의 커널은 계속 응답합니다.
- 메모리 상한에 걸린 셀은 `MemoryError` 로 끝나고 커널과 앞서 만든 변수가 남습니다. 모델은 데이터를 나눠 다시 시도하라는 안내를 받습니다.
- Windows 에서 커널이 띄운 자식 프로세스가 커널 재시작, 커널 종료, 서버 강제 종료 때 모두 함께 정리됩니다.
- 관리자 권한, 추가 설치, 파일 권한 변경이 모두 필요 없습니다.

**감수한 비용과 한계**

- 파일과 네트워크는 여전히 관례적입니다. 실행 코드는 사용자가 읽고 쓸 수 있는 모든 파일에 접근하고, 사내망 소켓을 열 수 있습니다. ADR-008 의 트레이드오프가 그대로 남습니다.
- 상한은 커널 단위입니다. 여러 커널이 동시에 상한 가까이 쓰면 합계는 상한 × 커널 수가 됩니다. 커널 수 상한(`SANDBOX_MAX_NAMESPACES`)과 함께 정해야 합니다.
- Linux 의 `RLIMIT_DATA` 에는 세 가지 한계가 있습니다.
  - 프로세스 단위입니다. 자식마다 새로 같은 상한을 받습니다.
  - 실제 사용량이 아니라 예약된 주소 공간을 셉니다.
  - 프로세스 수는 막지 못하고, 자식 정리는 프로세스 그룹 kill 에 기댑니다. 그래서 `setsid` 로 빠져나간 자식은 남습니다.
- Windows 에서 venv 의 `python.exe` 는 런처와 실제 인터프리터, 프로세스 두 개로 셉니다. 프로세스 상한은 2 미만으로 내리지 않습니다.
- 메모리를 잡지 못한 C 확장은 `MemoryError` 대신 프로세스를 끝낼 수 있습니다. 이 경우는 커널 사망 감지가 `KernelDied` 로 보고합니다.
- jupyter_client 의 private 메서드에 기대므로, 메이저 버전을 올릴 때마다 두 메서드가 그대로인지 확인해야 합니다.
