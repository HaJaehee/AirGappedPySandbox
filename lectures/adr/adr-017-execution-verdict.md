# ADR-017. 실행 판정에서 `SUCCESS`를 없앤다

## 상태 (Status)

채택됨 (Accepted) · 2026-09-22, v0.5.0

v0.1.0부터 쓰던 `SUCCESS` / `ERROR` / `TIMEOUT` 판정을 대체한다. 원래 설계 문서의 5단계 중 1, 2, 4단계를 구현했고, 3단계는 [ADR-018](adr-018-expect-verification.md)로 분리했다.

관련 결정: [ADR-006](adr-006-single-text-response.md), [ADR-007](adr-007-rules-in-tool-descriptions.md), [ADR-010](adr-010-run-script-file.md), [ADR-020](adr-020-verify-installs-directly.md)

## 맥락 (Context)

v0.4.1까지 실행 도구는 셀이 예외 없이 끝나면 `execution_status: SUCCESS`를 돌려줬다. 이 값의 실제 뜻은 "인터프리터가 예외 없이 끝났다"였다. 그러나 약한 모델은 SUCCESS라는 단어를 "사용자가 시킨 일이 끝났다"로 읽었고, 그 이상 확인하지 않은 채 사용자에게 완료를 보고했다.

실제 커널로 여러 실패 유형을 재현해 측정한 결과는 이랬다.

| 실행한 코드 | 당시 판정 | 실제 |
|---|---|---|
| `try: 1/0` / `except: print('handled')` | SUCCESS | 서버가 원리상 알 수 없다(모델의 책임) |
| `logging.error('db unreachable')` | SUCCESS | stderr에 오류가 찍혔다 |
| `traceback.print_exc()` | SUCCESS | stderr에 트레이스백 전체가 찍혔다 |
| 백그라운드 스레드에서 예외 | SUCCESS | stderr에 트레이스백이 찍혔다 |
| `subprocess.run(...)`이 종료 코드 3 | SUCCESS | 종료 코드가 무시되었다 |
| `print('FAIL: expected 5')` | SUCCESS | 테스트가 실패했다 |
| `x = 1` | SUCCESS | 아무 일도 하지 않았다 |
| `sys.exit(0)` | **ERROR** | 정상 종료였다. 반대 방향의 오판 |
| `sys.exit(1)` | ERROR | 맞지만 종료 코드를 구분하지 못했다 |

근본 원인은 한 문장으로 요약된다. 상태 값은 "인터프리터가 예외 없이 끝났는가"만 뜻하는데, 이름이 SUCCESS라서 모델은 "과업 성공"으로 읽었다.

규칙에 "실행되었다고 성공한 것은 아니다"라는 문장을 더하는 것만으로는 부족했다. 약한 모델은 긴 규칙을 읽지 않지만, 응답의 첫 줄은 읽는다.

## 결정 (Decision)

세 가지 원칙을 세웠다.

1. "실행되었다"와 "성공했다"를 분리한다. 서버가 알 수 있는 것은 전자뿐이다.
2. 서버가 모르는 것을 성공이라고 말하지 않는다. 기본값은 "검증되지 않음"이어야 한다.
3. 규칙 문장으로 설득하지 말고 응답의 값과 배치로 강제한다.

### 판정 어휘

| 판정 | 뜻 |
|---|---|
| `RAN_UNVERIFIED` | 예외 없이 끝났다. 성공의 증거는 아니다 |
| `RAN_NO_OUTPUT` | 끝났지만 출력도, 마지막 식의 값도, 바뀐 파일도 없다 |
| `RAN_WITH_ERRORS` | 끝났지만 실행 중에 오류가 보고되었다 |
| `FAILED` | 예외가 났거나, 0이 아닌 종료 코드로 끝났거나, 도구가 요청을 거절했다 |
| `TIMEOUT` | 제한시간에 걸려 끝나지 못했다 |

필드 이름 `execution_status`는 그대로 두고 값만 바꿨다. 이미 이 이름을 참조하는 문서와 프롬프트와의 호환을 위해서다.

### 판정 순서

위에서부터 먼저 걸리는 쪽으로 정한다.

1. 제한시간을 넘겼으면 `TIMEOUT`.
2. `SystemExit`이 아닌 예외가 났으면 `FAILED`. `SystemExit`이면 종료 코드를 읽어, 0이거나 없으면 정상 종료로 되돌리고(IPython이 붙이는 "use %tb" 잡음도 지운다) 그 밖의 값이면 `FAILED`.
3. 예외 없이 끝났는데 실패 신호가 있으면 `RAN_WITH_ERRORS`.
4. 출력도, 마지막 식의 값도, 산출물도 없으면 `RAN_NO_OUTPUT`.
5. 나머지는 `RAN_UNVERIFIED`.

### 예외 없는 실패를 모으는 방법

추측이 아니라 확실히 잡을 수 있는 것부터 모은다.

- **사건 장부.** 커널이 시작될 때 스레드 예외 훅, `subprocess.run`과 `call`, `Popen.wait`, `os.system`을 감싸, 백그라운드 예외와 0이 아닌 종료 코드를 커널 안의 목록에 기록한다. 감싼 함수는 원래 함수를 그대로 호출하므로 모델이 보던 출력은 사라지지 않는다. 기록은 최대 20건이다.
- **숨은 프로브 셀.** 매 실행 직후 서버가 조용히 장부를 읽고 비운다. 결과는 특수한 표식을 붙인 JSON 한 줄로 받아, 사용자 코드의 `print`와 섞이지 않게 한다. 실행 이력에 남기지 않아 사용자가 쓰는 `_` 값도 건드리지 않는다. 실패한 셀에서도 반드시 비운다. 비우지 않으면 남은 항목이 다음 호출의 결과에 "유령 실패"로 붙는다.
- **stderr 패턴.** 예외 없이 끝난 셀의 stderr에 트레이스백 머리글이나 `ERROR:`·`CRITICAL:`로 시작하는 줄이 있으면 신호로 본다. 예외가 난 셀에는 적용하지 않는다. 그 트레이스백은 이미 보고 대상이기 때문이다.
- stdout의 `FAIL` 같은 단어는 판정에 쓰지 않는다. 일반 출력으로 판정을 바꾸면 오탐이 너무 많다.

### 응답 배치

- 판정이 첫 줄이고, 그 뜻을 한 줄로 풀어 쓴다.
- 마지막 줄은 `next_action:`으로 시작하는 명령문이다. 판정마다 다르게, 모델이 다음에 할 일을 구체적으로 지시한다.
- stderr를 stdout보다 위로 올린다. 판정의 근거가 판정 바로 아래에 오게 한다.
- 도구 규칙에 6번 "실행되었다고 성공한 것은 아니다"를 추가한다.

### 과잉 경보 방지

`RAN_WITH_ERRORS`를 "실패"로 단정하면, 약한 모델은 `logging.warning` 수준의 잡음에도 멀쩡한 코드를 끝없이 고치려 든다. 그래서 이 판정의 문구는 "실패했다"가 아니라 "보고하기 전에 확인하라"로 정하고, `next_action`은 "실제 문제라면 한 번 고쳐서 다시 실행하고, 무해하다면 그렇다고 분명히 말하라"로 정했다.

## 결과 (Consequences)

**좋아진 점**

| 실행한 코드 | v0.4.1 | v0.5.0 |
|---|---|---|
| `print('answer', 42)` | SUCCESS | `RAN_UNVERIFIED` |
| `x = 1` | SUCCESS | `RAN_NO_OUTPUT` |
| `logging.error(...)` | SUCCESS | `RAN_WITH_ERRORS` |
| `traceback.print_exc()` | SUCCESS | `RAN_WITH_ERRORS` |
| 백그라운드 스레드 예외 | SUCCESS | `RAN_WITH_ERRORS` |
| `subprocess.run(...)` 종료 코드 3 | SUCCESS | `RAN_WITH_ERRORS` |
| `1/0` | ERROR | `FAILED` |
| `sys.exit(1)` | ERROR | `FAILED` |
| `sys.exit(0)` | ERROR | `RAN_UNVERIFIED` |
| `sys.exit(main())` 스크립트 실행 후 상태 | 사라짐 | 보존됨([ADR-010](adr-010-run-script-file.md)) |

- 모델이 서버에게서 "성공"이라는 말을 공짜로 얻을 수 없게 되었다.
- 도구 스키마가 바뀌지 않았으므로 AnythingLLM 설정을 다시 할 필요가 없었다.
- 이 표 전체를 판정 매트릭스 테스트로 고정했다.
- 같은 원칙이 설치 도구의 `INSTALLED` 판정에도 적용되었다([ADR-020](adr-020-verify-installs-directly.md)).

**치른 비용**

- 실행마다 커널 왕복이 한 번 늘었다(프로브 셀).
- 과잉 경보의 위험이 생겼다. 위와 같이 문구로 완화했지만 계속 지켜봐야 한다.

**남은 한계**

- 모델이 `try`/`except`로 삼킨 예외는 보이지 않는다. 커널 바깥에서는 관측할 수단이 없다. 이 틈은 [ADR-018](adr-018-expect-verification.md)의 검증식으로만 메울 수 있다.
- 백그라운드 스레드가 프로브 이후에 죽으면 그 사건은 다음 호출에 붙는다. 장부 항목에 트레이스백이 들어 있어 구분은 가능하지만, 귀속이 한 칸 밀린다.

**이 ADR에서 배울 점**

샌드박스는 실패를 증명할 수 있어도 성공을 증명할 수는 없다. 증명할 수 없는 것에 긍정적인 이름을 붙이면, 사용자가 사람이든 모델이든 그 이름을 믿는다.
