# ADR-017. 실행 판정 어휘 체계에서 모호한 `SUCCESS` 상태를 완전히 폐지합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-09-22, v0.5.0

v0.1.0 초기부터 사용되던 모호한 `SUCCESS` / `ERROR` / `TIMEOUT` 판정 체계를 전면 대체합니다. 본 개편은 최초 설계 명세의 5단계 로드맵 중 1, 2, 4단계를 구현한 것이며, 3단계(검증식 평가)는 [ADR-018](adr-018-expect-verification.md)로 분리하여 제안했습니다.

관련 결정: [ADR-006](adr-006-single-text-response.md), [ADR-007](adr-007-rules-in-tool-descriptions.md), [ADR-010](adr-010-run-script-file.md), [ADR-020](adr-020-verify-installs-directly.md)

## 맥락 (Context)

v0.4.1 버전까지 코드 실행 도구는 셀 내부에서 예외가 밖으로 던져지지 않고 끝나면 무조건 `execution_status: SUCCESS`를 반환했습니다. 이 상태 코드의 기술적인 실체는 단순히 "Python 인터프리터가 예외 없이 무사히 종료되었다"는 뜻에 불과했습니다. 그러나 소형 언어 모델은 `SUCCESS`라는 단어를 "사용자가 요청한 비즈니스 과업이 완벽히 성공했다"로 단정적으로 해석했고, 표준 출력을 더 이상 면밀히 검증하지 않은 채 사용자에게 작업을 완료했다고 거짓 보고를 올렸습니다.

실제 Jupyter 커널 환경에서 다양한 실패 유형들을 시뮬레이션하여 실측한 결과는 다음과 같았습니다.

| 실행된 Python 코드 예시 | 당시 반환 상태 | 실제로 발생한 런타임 현상 |
|---|---|---|
| `try: 1/0` / `except: print('handled')` | SUCCESS | 서버가 원리상 알 수 없음 (코드가 자체 은폐함) |
| `logging.error('db unreachable')` | SUCCESS | stderr에 치명적인 DB 오류 로그가 출력되었습니다. |
| `traceback.print_exc()` | SUCCESS | 코드가 예외를 잡아서 stderr에 에러 트레이스백만 출력했습니다. |
| 백그라운드 스레드 내부 크래시 | SUCCESS | 워커 스레드가 비정상 사망했으나 메인 스레드는 종료되었습니다. |
| `subprocess.run(...)` 종료 코드 3 | SUCCESS | 하위 CLI 프로세스가 실패 코드를 반환했습니다. |
| `print('FAIL: expected 5')` | SUCCESS | 비즈니스 로직 테스트가 실패했습니다. |
| `x = 1` | SUCCESS | 콘솔에 아무런 출력도 남기지 않았습니다. |
| `sys.exit(0)` | **ERROR** | 정상적인 스크립트 종료였음에도 IPython 때문에 에러로 오판되었습니다. |
| `sys.exit(1)` | ERROR | 에러 판정은 맞으나 세부 종료 코드를 구분하지 못했습니다. |

문제의 근본 원인은 명확했습니다. 상태 값의 실제 기술적 의미는 "인터프리터가 예외 없이 끝났는가"에 불과한데, 상태 명칭이 `SUCCESS`로 되어 있어 모델이 이를 "과업 성공"으로 오해한 것입니다.

도구 설명문 규칙에 "실행되었다고 해서 성공한 것은 아니다"라는 경고 문장을 추가하는 것만으로는 부족했습니다. 소형 모델은 긴 프롬프트 규칙은 흘려 읽어도, 반환 응답의 최상단 첫 줄만큼은 확실하게 읽기 때문입니다.

## 결정 (Decision)

다음과 같은 3대 엔지니어링 원칙을 새롭게 수립했습니다.

1. **"코드가 실행되었다"는 사실과 "과업이 성공했다"는 가치 판단을 철저히 분리합니다.** 런타임 샌드박스가 객관적으로 관측할 수 있는 영역은 전자뿐입니다.
2. **서버가 직접 확인하지 못한 사실을 함부로 성공이라고 선언하지 않습니다.** 오류가 없는 경우의 기본값은 반드시 "검증되지 않음"이어야 합니다.
3. **프롬프트 문장으로 모델을 설득하려 하지 말고, 응답의 상태 값과 텍스트 레이아웃 배치로 모델의 행동을 강제합니다.**

### 개편된 표준 판정 어휘 체계

| 판정 코드 | 판정의 정확한 의미와 보장 범위 |
|---|---|
| `RAN_UNVERIFIED` | 코드가 인터프리터 수준에서 예외 없이 실행을 마쳤습니다. 그러나 과업이 실제로 성공했음을 보장하지는 않습니다. |
| `RAN_NO_OUTPUT` | 코드가 종료되었으나 표준 출력도 없고, 마지막 식 평가값도 없으며, 워크스페이스 내 생성된 파일도 전혀 없습니다. |
| `RAN_WITH_ERRORS` | 코드가 인터프리터를 통과했으나, 실행 과정에서 오류 로그나 하위 프로세스 실패가 포착되었습니다. |
| `FAILED` | 처리되지 않은 예외가 발생했거나, 0이 아닌 종료 코드로 끝났거나, 도구 입력 검증 단계에서 거절되었습니다. |
| `TIMEOUT` | 허용된 시간 예산을 초과하여 인터럽트 또는 강제 프로세스 재시작 조치가 단행되었습니다. |

필드 명칭인 `execution_status`는 기존 프롬프트 및 호환성을 유지하기 위해 그대로 보존하고, 내부 값 어휘만을 전면 개편했습니다.

### 판정 우선순위 평가 알고리즘

관측 결과에 대해 상단 규칙부터 순서대로 평가하며, 먼저 일치하는 등급으로 최종 확정합니다.

1. 제한시간을 초과했으면 `TIMEOUT`으로 판정합니다.
2. `SystemExit`가 아닌 일반 예외가 발생했으면 `FAILED`로 판정합니다. `SystemExit` 예외인 경우 종료 코드를 검사하여, 0이거나 생략된 경우 정상 종료로 복원하고(IPython의 `use %tb` 잡음 로그도 제거) 0이 아니면 `FAILED`로 판정합니다.
3. 예외 없이 끝났으나 사건 장부에 항목이 있거나 stderr에 에러 신호가 감지되면 `RAN_WITH_ERRORS`로 판정합니다.
4. 표준 출력도 없고, 마지막 식 평가값도 없으며, 산출물도 없다면 `RAN_NO_OUTPUT`으로 판정합니다.
5. 위 모든 오류 조건에 해당하지 않는 정상 실행의 경우 최종적으로 `RAN_UNVERIFIED`를 부여합니다.

### 침묵하는 실패를 능동적으로 포착하는 메커니즘

추측에 의존하지 않고 객관적으로 증명할 수 있는 실패 신호들을 수집합니다.

- **커널 내부 사건 장부 (Incident Ledger)**: 커널 기동 시 스레드 예외 훅(`threading.excepthook`), `subprocess.run`, `subprocess.call`, `Popen.wait`, `os.system`을 감싸는 계측 훅을 주입하여, 백그라운드 스레드 크래시와 0이 아닌 서브프로세스 종료 코드를 커널 메모리의 링 버퍼에 기록합니다. 훅은 원본 함수를 그대로 호출하므로 사용자의 정상 콘솔 출력은 전혀 훼손되지 않습니다. (최대 20건 보관)
- **비가시 프로브 셀 (Invisible Probe Cell)**: 매 코드 실행 직후 서버가 조용히 커널에 감사 셀을 실행하여 사건 장부를 읽어오고 즉시 비웁니다. 사용자 코드의 `print()`와 섞이지 않도록 특수 마커를 부착한 JSON 문자열로 수신하며, IPython 히스토리에 남기지 않아 사용자의 직전 결과 특수 변수인 `_` 값을 오염시키지 않습니다. 실패한 셀에서도 반드시 실행하여 장부를 비워내야만 다음 호출로 에러가 이월되는 "유령 실패"를 방지할 수 있습니다.
- **stderr 정밀 패턴 매칭**: 예외 없이 끝난 셀의 stderr 스트림에 트레이스백 헤더가 존재하거나 `ERROR:`, `CRITICAL:`로 시작하는 로그 라인이 존재하면 실패 신호로 간주합니다.
- **stdout 출력 단어 배제**: stdout에 출력된 `FAIL`, `Error` 등의 임의 단어는 판정에 일절 반영하지 않습니다. 일반 업무 출력 텍스트로 판정을 흔들 경우 오탐(False Positive)이 지나치게 많아지기 때문입니다.

### 반환 응답 텍스트 레이아웃

- 최상단 첫 줄에 판정 등급을 명시하고 바로 다음 줄에 그 정확한 의미를 한 줄로 설명합니다.
- 최하단 마지막 줄은 `next_action:`으로 시작하는 단문 명령형 지침을 배치하여 모델이 취해야 할 후속 행동을 명확히 지시합니다.
- 표준 에러(stderr) 스트림을 표준 출력(stdout)보다 상단에 우선 배치하여 판정의 근거를 즉시 확인할 수 있도록 유도합니다.
- 도구 설명문 규칙에 6번 "실행 완료는 과업 성공이 아니다" 지침을 공식 추가했습니다.

### 과잉 경보(Alarm Fatigue) 방지책

만약 `RAN_WITH_ERRORS`를 치명적인 "실패"로 단정해 버리면, 소형 모델은 단순 정보성 경고 로그에도 패닉에 빠져 멀쩡한 코드를 끝없이 수정하려 듭니다. 따라서 이 판정의 안내 문구는 "실패했다"가 아니라 "사용자에게 보고하기 전에 면밀히 확인하라"는 중립적 권고로 정립했으며, `next_action` 지침 역시 "실제 결함이라면 수정하여 재실행하고, 무해한 로그라면 사용자에게 정직하게 설명하라"는 균형 잡힌 가이드를 제공합니다.

## 결과 (Consequences)

**얻게 된 이점**

| 실행된 코드 유형 | 과거 v0.4.1 판정 | 개편된 v0.5.0 판정 |
|---|---|---|
| `print('answer', 42)` | SUCCESS | `RAN_UNVERIFIED` |
| `x = 1` | SUCCESS | `RAN_NO_OUTPUT` |
| `logging.error(...)` | SUCCESS | `RAN_WITH_ERRORS` |
| `traceback.print_exc()` | SUCCESS | `RAN_WITH_ERRORS` |
| 백그라운드 스레드 크래시 | SUCCESS | `RAN_WITH_ERRORS` |
| `subprocess.run(...)` 종료 코드 3 | SUCCESS | `RAN_WITH_ERRORS` |
| `1/0` (처리되지 않은 예외) | ERROR | `FAILED` |
| `sys.exit(1)` (에러 종료) | ERROR | `FAILED` |
| `sys.exit(0)` (정상 종료) | ERROR | `RAN_UNVERIFIED` |
| `sys.exit(main())` 스크립트 실행 후 메모리 상태 | 모두 소멸됨 | 안전하게 보존됨([ADR-010](adr-010-run-script-file.md)) |

- 언어 모델이 샌드박스로부터 "성공"이라는 단어를 공짜로 얻어내어 사용자에게 거짓 보고를 올리는 환각을 완벽히 차단했습니다.
- 도구의 입력 JSON 스키마를 변경하지 않고 반환 텍스트 어휘만을 개선했으므로 AnythingLLM 클라이언트 설정을 재구성할 필요가 전혀 없었습니다.
- 위 비교 검증 표 전체를 데이터 주도형 판정 매트릭스 단위 테스트로 완벽히 형상 관리하여 로직의 퇴행을 방지했습니다.
- 동일한 정직성 원칙이 패키지 설치 도구의 `INSTALLED` 검증 판정에도 일관되게 확대 적용되었습니다([ADR-020](adr-020-verify-installs-directly.md)).

**감수한 트레이드오프**

- 매 코드 실행마다 커널 내부 프로브 셀을 파견하는 1회의 내부 IPC 왕복 오버헤드가 추가되었습니다.
- 모델이 경고에 민감하게 반응할 수 있는 과잉 경보의 잠재적 위험이 생겨났으며, 지침 문구 튜닝을 통해 이를 지속적으로 완화하고 있습니다.

**남겨진 기술적 한계**

- 사용자 코드가 `try: ... except: pass` 구문으로 예외를 자체적으로 집어삼켜 버린 경우 커널 외부에서는 이를 관측할 수단이 없습니다. 이 사각지대는 향후 검증식 인자([ADR-018](adr-018-expect-verification.md)) 도입을 통해서만 완벽히 메울 수 있습니다.
- 백그라운드 스레드가 메인 코드와 프로브 셀의 실행이 모두 끝난 직후 사망할 경우 해당 실패는 바로 다음 도구 호출의 사건 장부로 이월되어 수거됩니다.

**본 ADR이 주는 엔지니어링 교훈**

샌드박스 런타임은 실패는 객관적으로 증명할 수 있으나, 비즈니스 과업의 성공은 결코 증명할 수 없습니다. 시스템이 증명할 수 없는 불완전한 결과에 함부로 긍정적인 이름을 붙이면, 최종 사용자가 인간이든 AI 에이전트든 그 이름을 맹신하게 됩니다.
