# ADR-008. 격리는 관례적 수준으로 수용하고, 엄격한 시간 제한과 강제 재시작으로 가용성을 방어합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-07-23, v0.1.0 (v0.7.0에서 단일 실행 제한 기본값을 60초에서 45초로 하향 조정)

관련 결정: [ADR-001](adr-001-local-mcp-server.md), [ADR-002](adr-002-persistent-jupyter-kernel.md), [ADR-021](adr-021-tool-time-budget.md)

## 맥락 (Context)

대형 언어 모델이 생성하는 Python 코드는 어떠한 위험한 동작도 포함할 수 있습니다. 단순한 연산 실수로 인한 무한 루프, 수백 MB에 달하는 콘솔 출력 폭주, 수십 분짜리 `time.sleep` 호출, 그리고 워크스페이스 경계를 벗어난 임의 디렉터리 파일 조작 등이 모두 가능합니다. 이러한 위험 코드를 원천 차단하는 정석적인 해법은 OS 수준의 강력한 격리입니다. 권한을 극도로 제한한 전용 OS 서비스 계정, Docker 컨테이너, 혹은 경량 가상머신(VM) 등이 이에 해당합니다. 그러나 이러한 인프라 기법들은 모두 호스트 머신에 대한 '관리자 권한'을 필수적으로 요구하거나 폐쇄망 PC에 무거운 서드파티 소프트웨어를 추가로 설치해야 합니다. 실무 사용자에게는 이 두 가지가 모두 불가능했습니다.

한편 본 시스템은 단일 사용자의 업무용 로컬 PC에서, 오직 그 사용자 자신의 업무 데이터만을 다루는 환경입니다. 따라서 다수의 비인가 사용자가 동일한 서버에 임의의 코드를 동시에 제출하는 퍼블릭 클라우드 서비스와는 위협 모델(Threat Model)의 성격이 근본적으로 다릅니다.

이 환경에서 절대적 격리보다 훨씬 더 시급하고 치명적인 요구사항은 바로 **시스템 가용성(Availability)**이었습니다. 만약 악성 코드나 무한 루프로 인해 백엔드 커널 프로세스가 단 한 번이라도 영구 블로킹에 빠진다면, 후속으로 유입되는 모든 도구 호출이 멈춘 커널에 차단되어 해당 대화 세션 전체가 완전히 마비되기 때문입니다.

여기에 대상 OS인 Windows 특유의 I/O 처리 한계가 존재했습니다. Jupyter의 인터럽트 신호는 순수 Python 바이트코드로 회전하는 루프는 0.2초 이내에 신속히 중단시키지만, `time.sleep`이나 C 확장의 블로킹 I/O처럼 시스템 콜 수준에서 멈춘 프로세스는 인터럽트 신호로 깨워내지 못합니다. 즉, 소프트웨어 인터럽트 신호만으로는 커널의 정상 복귀를 결코 보장할 수 없었습니다.

## 결정 (Decision)

완벽한 보안 경계가 아닌 현실적인 "관례적 샌드박스(Conventional Sandbox)" 모델을 공식 수용하기로 결정했습니다. 공식 사용자 문서에도 "본 시스템은 OS 레벨의 완전 격리 환경이 아니다"라는 보안 한계를 솔직하게 명시하고, 보다 강력한 보안 격리가 필요한 기업 환경이라면 서버 전체를 제한된 권한의 전용 서비스 계정이나 컨테이너 내부에서 구동하도록 권고했습니다.

그 대신 시스템의 가용성과 안정성을 지키기 위해 다음과 같은 다단계 완화책을 구축했습니다.

- 모델에게 워크스페이스 내부에서 상대 경로로만 파일을 조작하도록 강력히 안내하며, 파일 조작 도구는 경로 검증기를 통해 워크스페이스 경계 바깥으로의 탈출을 엄격히 거절합니다.
- 콘솔 출력 스트림(stdout, stderr)의 길이에 엄격한 상한선(각 20,000자)을 둡니다.
- 단일 코드 실행마다 명확한 시간 예산 제한(`SANDBOX_EXEC_TIMEOUT`, 기본 45초)을 설정하고, 이를 초과할 경우 다음과 같은 2단계 복구 시퀀스를 순차 집행합니다.
  1. 먼저 커널에 인터럽트 신호(`KeyboardInterrupt`)를 전송합니다.
  2. 최대 5초 동안 커널이 `idle` 상태로 안전하게 복귀하기를 대기합니다.
  3. 5초 내에 정상 복귀하면 해당 커널을 그대로 유지합니다. 메모리의 변수와 데이터는 안전하게 보존됩니다.
  4. 5초가 지나도 응답이 없으면 OS 레벨에서 커널 프로세스를 강제 종료(Kill)하고 깨끗이 재기동합니다. 메모리의 기존 변수는 모두 초기화되며, 반환 응답에 프로세스가 리셋되었음을 명확히 안내합니다.
- 만약 외부 요인으로 인해 커널 프로세스가 이미 비정상 종료되어 있는 상태라면, 다음 코드 실행 요청을 처리하기 직전에 선제적으로 커널을 재부팅합니다.

## 결과 (Consequences)

**얻게 된 이점**

- 호스트 머신의 시스템 관리자 권한이 전혀 없는 일반 사용자 PC에서도 즉시 배포하여 구동할 수 있습니다.
- 사용자가 어떤 위험하거나 멈춘 코드를 실행했더라도, 바로 다음 도구 호출은 반드시 정상 응답하는 깨끗한 커널 환경을 보장받습니다.
- 인터럽트 신호로 정상 복귀하는 대다수의 일반적인 무한 루프 상황에서는 기존 대화의 메모리 분석 상태가 안전하게 보존됩니다.

**감수한 트레이드오프**

- 모델이 작성하여 실행한 코드는 현재 사용자의 OS 로그인 계정이 접근할 수 있는 모든 로컬 파일을 읽고 쓸 수 있는 잠재적 권한을 가집니다. 경로 검증기는 서버의 파일 전용 도구에만 적용되며, 인터프리터 내부에서 동적 실행되는 임의의 Python 코드 자체를 OS 레벨에서 차단하지는 못합니다.
- 실행 코드가 사내망 내부의 다른 호스트로 네트워크 소켓을 생성할 수 있습니다. "네트워크 호출 금지"는 도구 설명문의 지침일 뿐이며 OS 방화벽으로 강제되지 않습니다. 데이터가 공용 인터넷으로 유출되지 않는 것은 소프트웨어 샌드박스의 공로가 아니라 물리적 사내 폐쇄망 인프라 덕분입니다.
- 2단계 강제 재시작이 단행되면 해당 대화 세션에서 메모리에 누적해 두었던 데이터프레임과 변수들이 모두 소멸합니다.
- 5초의 인터럽트 유예 대기 시간이 소스코드에 상수로 고정되어 있습니다. 대규모 연산으로 인해 불필요한 재시작이 잦다면 향후 환경 변수 설정으로 노출할 필요가 있습니다 (로드맵 과제).

**현업 운영 시 주의사항**

2단계 프로세스 강제 재시작 경로는 어떠한 악성 상황에서도 커널을 항상 응답 가능하게 방어하는 가장 핵심적인 생명선입니다. "재시작되면 메모리 상태가 날아가니 인터럽트 신호만 보내도록 단순화하자"는 식으로 이 재시작 로직을 함부로 제거해서는 안 됩니다. Windows 환경에서 C 레벨 블로킹 I/O를 만나는 순간 대화 세션 전체가 영구 교착 상태에 빠지게 됩니다.

아울러 v0.7.0에서는 단일 실행 제한 기본값을 기존 60초에서 **45초**로 전격 하향 조정했습니다. 과거의 60초 설정은 AnythingLLM 클라이언트의 자체 타임아웃 제한 시간과 완전히 동일하여, 긴 연산이 수행될 때 서버의 `TIMEOUT` 판정 응답과 클라이언트의 강제 연결 중단 중 어느 쪽이 먼저 도착할지 예측할 수 없는 심각한 경쟁 상태가 발생했기 때문입니다([ADR-021](adr-021-tool-time-budget.md)).
