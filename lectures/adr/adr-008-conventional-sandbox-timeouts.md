# ADR-008. 격리는 관습 수준으로 두고, 시간 제한과 강제 재시작으로 가용성을 지킨다

## 상태 (Status)

채택됨 (Accepted) · 2026-07-23, v0.1.0 (v0.7.0에서 실행 제한 기본값 60초 → 45초)

관련 결정: [ADR-001](adr-001-local-mcp-server.md), [ADR-002](adr-002-persistent-jupyter-kernel.md), [ADR-021](adr-021-tool-time-budget.md)

## 맥락 (Context)

모델이 쓰는 코드는 무엇이든 될 수 있다. 무한 루프, 수백 MB의 출력, 몇 분짜리 `sleep`, 워크스페이스 밖의 파일 쓰기까지. 이런 코드를 막는 정석은 강한 격리다. 권한을 제한한 전용 OS 계정, 컨테이너, 가상 머신 같은 것들이다. 그러나 모두 관리자 권한이 필요하거나 폐쇄망 PC에 추가 소프트웨어를 들여야 한다. 사용자에게는 둘 다 불가능했다.

한편 이 시스템은 사용자 한 명의 PC에서, 그 사용자의 데이터를 다룬다. 여러 사람의 코드를 한 서버에서 돌리는 공용 서비스와는 위협의 성격이 다르다.

격리보다 더 시급한 것은 가용성이었다. 커널이 한 번 멈추면 그 뒤의 모든 호출이 멈춘 커널에 걸려 대화 전체가 망가진다.

여기에 Windows 특유의 문제가 있었다. 커널 인터럽트는 파이썬 코드로 도는 루프라면 0.2초 안에 끊는다. 그러나 `time.sleep`처럼 C 수준에서 한 번에 길게 멈춘 호출은 깨우지 못한다. 인터럽트만으로는 커널이 반드시 돌아온다고 보장할 수 없다.

## 결정 (Decision)

보안 경계가 아닌 관습 수준의 샌드박스를 받아들인다. 사용자 문서에도 "강화된 감옥이 아니다"라고 명시하고, 더 강한 격리가 필요하면 서버 전체를 제한된 계정이나 컨테이너에서 돌리라고 권고한다.

대신 다음 완화책을 둔다.

- 모델에게 워크스페이스 안에서 상대 경로로 파일을 다루라고 안내한다. 파일을 다루는 도구는 경로를 검증해 워크스페이스 밖을 거절한다.
- stdout과 stderr의 길이에 상한을 둔다.
- 실행마다 제한시간을 둔다(`SANDBOX_EXEC_TIMEOUT`). 넘기면 다음 순서로 처리한다.
  1. 커널을 인터럽트한다.
  2. 최대 5초 동안 커널이 idle로 돌아오기를 기다린다.
  3. 돌아오면 커널을 그대로 쓴다. 변수는 보존된다.
  4. 돌아오지 않으면 커널을 재시작한다. 변수는 모두 사라지며, 응답에 그 사실을 분명히 적는다.
- 커널이 죽어 있으면 다음 실행 요청 때 먼저 다시 띄운다.

## 결과 (Consequences)

**좋아진 점**

- 관리자 권한 없이 배포할 수 있다.
- 어떤 코드를 실행했든 다음 호출은 응답하는 커널을 받는다.
- 인터럽트로 끝나는 대부분의 경우에는 대화의 상태가 보존된다.

**치른 비용**

- 모델이 쓴 코드는 사용자 계정이 접근할 수 있는 모든 파일을 읽고 쓸 수 있다. 경로 검증은 파일 도구에만 적용되고, 실행되는 코드 자체에는 적용되지 않는다.
- 코드는 사내망에 접속할 수 있다. "네트워크 호출 금지"는 규칙일 뿐 강제되지 않는다. 인터넷으로 데이터가 나가지 못하는 것은 서버 덕분이 아니라 폐쇄망 덕분이다.
- 강제 재시작은 그 대화가 쌓아 온 데이터를 날린다.
- 유예 시간 5초는 코드에 고정되어 있다. 재시작이 너무 잦다면 설정으로 뺄 필요가 있다(로드맵).

**운영 시 주의**

재시작 경로는 커널을 항상 응답 가능하게 지키는 안전망이다. "재시작하면 상태가 날아가니 인터럽트만 하자"는 식으로 제거하면, Windows에서 긴 블로킹 호출 하나가 대화 전체를 멈추게 된다.

v0.7.0에서 실행 제한 기본값을 60초에서 45초로 줄였다. 60초는 MCP 클라이언트의 요청 제한과 같아서, 긴 셀이 서버의 `TIMEOUT` 판정과 클라이언트의 취소 중 무엇으로 끝날지 운에 맡겨졌기 때문이다([ADR-021](adr-021-tool-time-budget.md)).
