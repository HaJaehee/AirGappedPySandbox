# ADR-007. 핵심 도구 사용 규칙을 도구 설명문(Description) 내부에 직접 주입합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-07-23, v0.1.0

주입된 상세 규칙의 내용은 v0.3.0, v0.4.1, v0.5.0, v0.6.0에 걸쳐 시스템 발전과 함께 지속적으로 개정되었습니다 (하단 "규칙의 점진적 개정 과정" 참조).

관련 결정: [ADR-014](adr-014-write-file-tool.md), [ADR-017](adr-017-execution-verdict.md), [ADR-019](adr-019-side-venv-installs.md)

## 맥락 (Context)

언어 모델은 도구의 구체적인 사용 방법과 제약 조건을 오직 도구 설명문(Description) 텍스트와 입력 JSON Schema를 통해서만 학습합니다. 개발자가 정성껏 작성한 프로젝트 README나 내부 아키텍처 문서는 모델의 시야에 전혀 닿지 않습니다. 한편 AnythingLLM의 시스템 프롬프트(작업 지침)는 개별 사용자가 각자의 기호에 맞게 임의로 설정하는 영역이므로 MCP 서버 측에서 통제할 수 없습니다.

실제 환경에서 모델이 저지를 수 있는 전형적이고 치명적인 실패 패턴들은 사전에 명확히 예측되었습니다.

- 실행 코드 내부에서 습관적으로 `pip install` 명령을 실행합니다. 폐쇄망 환경에서는 타임아웃에 걸려 오랜 시간 멈춰 있다가 결국 실패합니다.
- GUI 화면이 없는 헤드리스 커널에서 `plt.show()`를 호출하여 아무런 이미지 파일도 디스크에 남기지 못합니다.
- 계산 코드를 열심히 실행해 놓고 최종 결과를 `print()`로 감싸지 않아 모델에게 아무런 수치도 돌아가지 않습니다.
- 엉뚱한 임의의 디렉터리 경로에 파일을 저장하여 산출물 자동 탐지망을 벗어납니다.
- 런타임 에러가 발생했을 때 해결을 포기하거나 아무런 수정 없이 동일한 오류 코드를 그대로 반복 재전송합니다.

## 결정 (Decision)

번호를 매긴 엄격한 핵심 사용 규칙(Rule 0~6)을 코드 실행 계열 도구(`execute_python_code`, `run_python_file`)의 독스트링 설명문 내부에 직접 주입하기로 결정했습니다. 아울러 사전에 설치되어 즉시 임포트 가능한 주요 라이브러리 목록도 설명문 안에 함께 명시했습니다.

반면 단순 파일 저장 도구(`write_workspace_file`)나 파일 목록 조회 도구(`list_workspace_files`)에는 이러한 무거운 규칙들을 일절 넣지 않았습니다. 가볍고 단순하게 사용되어야 할 유틸리티 도구의 설명문을 비대하게 만들면 본래의 설계 목적이 훼손되기 때문입니다. 더욱이 규칙의 0번 항목은 이 두 도구에서는 애초에 받지 않는 `namespace` 인자의 사용을 강제하고 있으므로, 일괄 주입할 경우 소형 모델에게 극심한 혼란만 가중시키게 됩니다. 대신 실행 도구의 설명문 내부에 "순수 파일 저장만 하려는 목적이라면 `write_workspace_file` 도구를 사용하라"는 명시적인 분기 안내를 추가하여 도구 간의 책임 경계를 명확히 분리했습니다.

## 결과 (Consequences)

**얻게 된 이점**

- 핵심 사용 규칙이 도구 정의 자체에 내장되어 도구와 함께 전달됩니다. 사용자가 AnythingLLM에서 어떤 클라이언트를 쓰든, 시스템 프롬프트를 어떻게 설정하든 관계없이 모델은 항상 동일한 표준 규칙을 일관되게 주입받습니다.
- 도구 사용 규칙을 개선하거나 추가할 때 서버 코드만 업데이트하면 즉시 반영됩니다. 개별 사용자들에게 복잡한 프롬프트 수정 작업을 일일이 요청할 필요가 없습니다.

**감수한 트레이드오프**

- 도구 하나당 설명문 길이가 약 500토큰에 달할 정도로 길어집니다. 등록된 전체 도구 목록이 모델의 시스템 프롬프트 컨텍스트를 상시 점유하므로 토큰 비용 부담이 결코 작지 않습니다.
- 서버 측에서 규칙을 수정하더라도 클라이언트 데스크톱 앱이 도구 목록(`tools/list`)을 다시 조회하여 캐시를 갱신하기 전까지는 즉각 반영되지 않습니다.
- 추론 능력이 취약한 소형 모델은 문장이 길어지면 설명문 내부의 규칙을 끝까지 준수하지 못하는 경향이 있습니다. 결국 가장 중요한 원칙(실행 결과를 함부로 성공으로 단정하지 않기)은 텍스트 규칙만으로 통제하지 못하고, 반환 응답의 물리적 레이아웃 자체로 강제해야만 했습니다([ADR-017](adr-017-execution-verdict.md)).

**규칙의 점진적 개정 과정**

| 버전 | 개정된 주요 규칙 내용 | 개정하게 된 실무적 계기 |
|---|---|---|
| v0.3.0 | 0번 "대화별 세션 네임스페이스" 관리 규칙 신설 | 대화 세션 간 변수 격리 아키텍처 도입([ADR-011](adr-011-namespace-argument.md)) |
| v0.4.1 | 4번 경로 규칙을 "`./workspace/`를 붙여라"에서 "순수 파일 이름만 써라"로 전면 수정 | 커널 프로세스의 작업 디렉터리를 워크스페이스 내부로 일치시킴([ADR-016](adr-016-kernel-cwd-workspace.md)) |
| v0.5.0 | 6번 "실행 완료는 과업 성공이 아니다" 검증 규칙 신설 | 모호한 `SUCCESS` 폐지 및 정직한 실행 판정 체계 개편([ADR-017](adr-017-execution-verdict.md)) |
| v0.6.0 | 1번 규칙을 "pip 완전 금지"에서 "코드 내부 실행 금지, 필요시 패키지 설치 전용 도구 호출"로 완화 | 사내 PyPI 미러 서버 신설 및 사이드 venv 설치 기능 도입([ADR-019](adr-019-side-venv-installs.md)) |

여기서 주목할 점은 설명문 내부의 규칙들이 시스템의 아키텍처 진화 과정을 그대로 충실하게 반영하며 발전해 왔다는 사실입니다. 도구 설명문은 개발 초기에 한 번 작성하고 방치하는 정적 텍스트가 아니라, 시스템 인터페이스의 핵심 부품으로서 백엔드 코드와 함께 엄격히 형상 관리되어야 합니다.
