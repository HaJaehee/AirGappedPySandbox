# ADR-007. 사용 규칙은 도구 설명문에 심는다

## 상태 (Status)

채택됨 (Accepted) · 2026-07-23, v0.1.0

규칙의 내용은 v0.3.0, v0.4.1, v0.5.0, v0.6.0에서 개정되었다(아래 "결과" 참고).

관련 결정: [ADR-014](adr-014-write-file-tool.md), [ADR-017](adr-017-execution-verdict.md), [ADR-019](adr-019-side-venv-installs.md)

## 맥락 (Context)

모델은 도구의 사용법을 도구 설명문과 입력 스키마로만 배운다. README나 위키는 모델에게 보이지 않는다. AnythingLLM의 시스템 프롬프트는 사용자가 저마다 설정하는 것이라 서버가 통제할 수 없다.

미리 예상할 수 있는 실패가 여럿 있었다.

- 코드 안에서 `pip install`을 시도한다. 폐쇄망에서는 한참 멈췄다가 실패한다.
- `plt.show()`를 부른다. 화면이 없는 커널에서는 아무것도 남지 않는다.
- 결과를 `print`하지 않는다. 계산은 했는데 아무것도 돌아오지 않는다.
- 엉뚱한 경로에 파일을 쓴다. 산출물로 잡히지 않는다.
- 오류가 나면 포기하거나 같은 코드를 그대로 다시 보낸다.

## 결정 (Decision)

번호를 붙인 사용 규칙을 코드 실행 도구(`execute_python_code`, `run_python_file`)의 설명문에 넣는다. 미리 설치된 라이브러리 목록도 함께 적는다.

파일 저장 도구와 목록 도구에는 규칙을 넣지 않는다. 가볍게 쓰라고 만든 도구의 설명문을 무겁게 만들면 그 목적이 무너진다. 또 규칙의 첫 항목이 이 두 도구가 받지 않는 `namespace`를 요구하므로, 붙이면 모델만 헷갈린다. 대신 실행 도구의 설명문에 "저장만 하려면 저장 도구를 써라"는 한 줄을 넣어 두 도구의 경계를 나눈다.

## 결과 (Consequences)

**좋아진 점**

- 규칙이 도구를 따라다닌다. 어떤 클라이언트, 어떤 시스템 프롬프트 아래에서도 모델은 같은 규칙을 본다.
- 규칙을 고치면 서버만 업데이트하면 된다. 사용자가 프롬프트를 손볼 필요가 없다.

**치른 비용**

- 설명문이 도구 하나당 500토큰 가까이 길어진다. 도구 목록 전체가 모델의 컨텍스트를 차지하므로 부담이 작지 않다.
- 규칙이 바뀌어도 클라이언트가 도구 목록을 다시 받아 가야 반영된다.
- 약한 모델은 긴 규칙을 끝까지 따르지 않는다. 결국 가장 중요한 것(실행 결과를 성공으로 오해하지 않기)은 규칙이 아니라 응답의 모양으로 강제해야 했다([ADR-017](adr-017-execution-verdict.md)).

**규칙이 바뀌어 온 과정**

| 버전 | 바뀐 내용 | 계기 |
|---|---|---|
| v0.3.0 | 0번 "네임스페이스" 규칙 추가 | 대화별 격리 도입([ADR-011](adr-011-namespace-argument.md)) |
| v0.4.1 | 4번 경로 규칙을 "`./workspace/`를 붙여라"에서 "파일 이름만 써라"로 변경 | 커널 작업 디렉터리 변경([ADR-016](adr-016-kernel-cwd-workspace.md)) |
| v0.5.0 | 6번 "실행됨은 성공함이 아니다" 추가 | 판정 체계 개편([ADR-017](adr-017-execution-verdict.md)) |
| v0.6.0 | 1번을 "pip 금지"에서 "코드 안에서 pip 금지, 필요하면 설치 도구를 써라"로 개정 | 사내 미러 등장([ADR-019](adr-019-side-venv-installs.md)) |

규칙이 시스템의 변화를 그대로 따라 바뀌었다는 점에 주목하자. 설명문은 한 번 쓰고 끝나는 문서가 아니라, 인터페이스의 일부로서 코드와 함께 관리해야 한다.
