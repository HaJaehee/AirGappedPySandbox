# ADR-016. Jupyter 커널의 작업 디렉터리(cwd)를 워크스페이스 내부로 일치시킵니다

## 상태 (Status)

채택됨 (Accepted) · 2026-08-28, v0.4.1

기존 [ADR-009](adr-009-kernel-cwd-project-root.md)를 전면 대체합니다.

관련 결정: [ADR-005](adr-005-snapshot-diff-artifacts.md), [ADR-007](adr-007-rules-in-tool-descriptions.md), [ADR-010](adr-010-run-script-file.md)

## 맥락 (Context)

과거 [ADR-009](adr-009-kernel-cwd-project-root.md)에서는 Jupyter 커널을 서버 프로젝트 루트 디렉터리에서 실행하고, 모델에게 모든 파일 입출력 시 일관되게 `./workspace/` 상대 경로를 사용하도록 지시했습니다. 그러나 사용자가 환경 변수 `SANDBOX_WORKSPACE`를 통해 워크스페이스를 프로젝트 디렉터리 외부(예: 다른 드라이브의 전용 분석 폴더)로 변경하자 다음과 같은 3가지 치명적인 결함이 발생했습니다.

1. **파일 산출물 증발 현상**: 모델이 코드에서 `./workspace/chart.png`를 저장하면 프로젝트 루트 하위의 서버 폴더에 파일이 기록되었으나, 파일 조작 도구와 산출물 탐지기는 환경 변수로 지정된 외부 워크스페이스 폴더만 바라보고 있었습니다. 그 결과 파일은 생성되었으나 도구에서 감지되지 않아 사용자 눈에는 파일이 감쪽같이 사라진 것처럼 보였습니다.
2. **실행 호스트에 따른 상대 경로 불일치**: `SANDBOX_WORKSPACE`에 상대 경로를 지정하면 MCP 서버 프로세스의 현재 작업 디렉터리를 기준으로 해석되었습니다. 그런데 프로세스의 작업 디렉터리는 서버를 구동하는 호스트 런처(AnythingLLM, 수동 실행 스크립트 등)에 의해 결정되므로, 동일한 설정임에도 호스트에 따라 서로 다른 엉뚱한 폴더를 가리켰습니다. 동일한 작업 폴더를 공유해야 할 다른 로컬 MCP 서버와의 경로 싱크도 완전히 어긋났습니다.
3. **마크다운 링크 깨짐 현상**: 워크스페이스가 프로젝트 외부에 위치할 때 산출물 파일 링크가 절대 경로로 조립되어, 마크다운 본문에 `./D:/...`와 같이 정상적이지 않은 깨진 링크가 생성되었습니다.

스크립트 실행 도구(`run_python_file`) 역시 심각한 오작동을 겪었습니다. `./workspace/script.py`를 프로젝트 루트 기준으로 해석하다 보니, 워크스페이스를 외부로 옮겼을 때 파일을 찾지 못하거나 프로젝트 내부에 과거에 남아 있던 동일한 이름의 오래된 레거시 파일을 엉뚱하게 집어 들고는 "워크스페이스 경계 바깥"이라며 실행을 거절하는 기이한 현상이 발생했습니다.

## 결정 (Decision)

시스템 전체에서 "파일의 물리적 기준 위치가 어디인가"라는 핵심 질문에 대한 정답을 **워크스페이스 디렉터리 단 하나로 통일**하기로 결정했습니다.

- Jupyter 커널 프로세스를 기동할 때 커널의 OS 현재 작업 디렉터리(cwd)를 '설정된 실제 워크스페이스 디렉터리'로 직접 바인딩합니다. 이제 모델의 코드가 별도의 경로 접두사 없이 단순히 `plt.savefig("chart.png")`라고만 작성해도 파일은 정확히 워크스페이스 내부에 안전하게 저장됩니다.
- 도구 설명문의 4번 경로 규칙을 전면 개정했습니다. 이제는 `./workspace/` 접두사를 붙이지 말고 순수 파일 이름만 작성하도록 모델에게 안내합니다.
- 환경 변수 `SANDBOX_WORKSPACE`에 상대 경로가 주어질 경우, 호스트 프로세스의 작업 디렉터리가 아닌 'MCP 서버 소스코드가 위치한 기준 디렉터리'를 중심으로 절대 경로화합니다. 호스트가 서버를 어떤 임의의 디렉터리에서 구동하더라도 항상 동일한 폴더를 정확히 바라보도록 보장합니다.
- 파일 조작 도구들은 `./workspace/`, `workspace/`, `/workspace/`로 시작하는 경로 입력을 받으면 해당 접두사를 유연하게 제거하고 워크스페이스 기준 상대 경로로 투명하게 정규화합니다. 과거의 습관이 남아 있는 모델이 접두사를 붙여 호출하더라도 정상 동작하도록 포용합니다.
- 워크스페이스가 프로젝트 디렉터리 외부에 위치하더라도 산출물 링크는 항상 일관된 `workspace/<파일명>` 형태의 상대 경로를 유지하도록 보정했습니다.

## 결과 (Consequences)

**얻게 된 이점**

- 백엔드 커널 프로세스, MCP 파일 도구 계층, 산출물 자동 탐지 엔진이 모두 동일한 기준 디렉터리를 일관되게 공유합니다. 과거 기본 설정 환경에서만 우연히 맞아떨어지던 불안정한 상태가, 어떤 사용자 정의 경로 설정 하에서도 완벽히 동작하는 견고한 구조로 완성되었습니다.
- 모델이 프롬프트나 인자에 작성해야 할 파일 경로가 훨씬 짧고 단순해졌습니다. 경로 접두사를 실수로 누락하여 발생하던 수많은 에러가 완전히 사라졌습니다.
- 작업 워크스페이스를 로컬 D 드라이브나 사내 전용 대용량 공유 디렉터리로 완벽히 자유롭게 이동하여 운영할 수 있게 되었습니다.

**감수한 트레이드오프와 하위 호환 잔재**

- 커널 초기화 코드는 하위 호환성을 위해 작업 디렉터리 내부에 `workspace`라는 이름의 하위 폴더를 여전히 자동 생성해 둡니다. 구형 프롬프트를 학습한 모델이 과거 습관대로 `./workspace/chart.png`에 파일을 저장하더라도 I/O 오류로 실패하지 않도록 보호하기 위한 안전장치입니다. 이렇게 저장된 파일 역시 워크스페이스 하위 디렉터리에 실재하므로 산출물로 정상 탐지됩니다. 다만 워크스페이스 내부에 `workspace` 폴더가 한 겹 더 생겨나는 시각적 부작용이 남게 되었습니다.
- 사용자 배포 매뉴얼, 도구 설명문 규칙, 단위 테스트 코드를 전면 일괄 수정해야 했습니다. 파일 경로 규약은 LLM 모델, 인간 사용자, 백엔드 코드가 모두 공유하는 핵심 계약이므로 어느 한 부분만 수정하고 넘어갈 수 없었습니다.

**본 ADR이 주는 엔지니어링 교훈**

기본 설정값에서 정상 동작한다고 해서 그 소프트웨어 아키텍처가 올바르게 설계되었다고 단정할 수 없습니다. 환경 변수나 설정 파일로 변경할 수 있는 파라미터가 존재한다면, 반드시 기본값이 아닌 임의의 외부 값으로도 혹독하게 테스트해야 합니다. 본 버전에서 프로젝트 외부 워크스페이스 경로를 검증하는 독립 스모크 테스트가 대거 확충된 이유가 바로 여기에 있습니다.
