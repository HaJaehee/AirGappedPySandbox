# ADR-002. 호출마다 새 프로세스를 띄우는 대신 영속 Jupyter 커널로 상태를 유지합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-07-23, v0.1.0

관련 결정: [ADR-003](adr-003-separate-interpreters.md), [ADR-008](adr-008-conventional-sandbox-timeouts.md), [ADR-012](adr-012-kernel-pool-per-namespace.md), [ADR-017](adr-017-execution-verdict.md)

## 맥락 (Context)

코드 실행 도구를 가장 손쉽게 구현하는 방법은 매 호출마다 OS 명령줄에서 `python`을 새로운 자식 프로세스로 띄워 실행하는 방식입니다. 하지만 이 방식은 프로세스가 종료될 때마다 메모리에 적재되었던 모든 실행 상태가 즉시 소멸합니다.

본 시스템의 전형적인 실무 사용 시나리오는 "사용자가 분석할 데이터 파일을 하나 올려두고 연속해서 여러 차례 질문을 이어가는 형태"입니다. 100MB 크기의 대용량 엑셀이나 CSV 파일을 pandas로 읽어 들이는 데만 수 초에서 수십 초의 I/O 시간이 소요됩니다. 사용자가 질문을 던질 때마다 매번 이 대용량 파일을 반복해서 다시 읽는다면 시스템의 응답 속도가 현저히 느려지며, 모델 역시 매 호출마다 파일을 처음부터 다시 로드하는 코드를 작성해야 하므로 코드 생성 실수를 범할 확률이 크게 증가합니다.

또한 안정적인 코드 실행기에는 표준 출력 스트림 캡처, 런타임 예외 추적, 무한 루프 코드의 인터럽트 중단, 프로세스 비정상 종료 시의 자동 복구 등 수많은 복잡한 기능들이 요구됩니다. 이러한 엔지니어링 메커니즘을 밑바닥부터 직접 개발하는 것은 상당한 개발 비용과 불안정성을 수반합니다.

당시 검토했던 주요 대안들은 다음과 같습니다.

1. **매 호출마다 새로운 프로세스를 기동합니다.** 구조는 단순하지만 이전 대화의 변수나 데이터 상태를 전혀 유지할 수 없습니다.
2. **신규 프로세스를 띄우되 중간 상태를 디스크에 직렬화합니다.** 실행 결과를 pickle 파일 등으로 저장했다가 다음 호출에서 다시 역직렬화하여 로드하는 방식입니다. 그러나 열려 있는 파일 핸들, 활성화된 데이터베이스 커넥션, 모듈 내부 전역 설정 등은 물리적으로 직렬화가 불가능하며, 수백 MB에 달하는 대용량 데이터프레임을 매번 파일로 쓰고 읽는 오버헤드 역시 매우 큽니다.
3. **MCP 서버 프로세스 내부에서 Python `exec()` 함수로 직접 실행합니다.** 프로세스 기동 비용이 없어 빠르지만, 사용자 코드가 치명적인 오류를 내면 메인 MCP 서버 전체가 함께 크래시됩니다. 또한 무한 루프에 빠진 코드를 강제로 중단시킬 안전한 방법이 없으며, 서버와 커널이 동일한 인터프리터를 공유할 수밖에 없습니다.
4. **Jupyter 커널 아키텍처를 도입합니다.** 코드 실행 환경을 독립된 외부 프로세스로 완전히 분리하면서도, 해당 프로세스를 메모리에 지속적으로 상주시켜 상태를 보존합니다. 표준 출력 스트림, 최종 표현식 결과, 예외 트레이스백, 인터럽트 및 프로세스 재시작 메커니즘이 이미 프로토콜 수준에서 정교하게 정의되어 있습니다.

## 결정 (Decision)

`jupyter_client` 라이브러리를 활용하여 백엔드 IPython 커널을 독립된 외부 프로세스로 구동하고, MCP 서버가 가동되는 동안 해당 커널 세션을 영속적(Persistent)으로 유지하기로 결정했습니다.

실행할 코드는 ZeroMQ의 `shell` 채널을 통해 `execute_request` 메시지로 전달합니다. 실행 결과는 `iopub` 채널로 쏟아지는 이벤트 스트림 중 해당 요청의 고유 `msg_id`와 일치하는 메시지만을 선별 수집하며, 최종적으로 `status: idle` 메시지가 수신되면 실행이 완료된 것으로 판단합니다. 새로운 요청을 보내기 직전에는 이전 작업이 남겨두었을지 모를 소켓 잔여 메시지를 깨끗이 플러시합니다. 아울러 각 커널 객체는 전용 락(`RLock`)으로 보호하여 한 번에 단 하나의 실행 요청만을 순차 처리하도록 강제합니다.

MCP 서버와 Jupyter 커널 간의 통신은 ZeroMQ 라이브러리를 사용하여 로컬 루프백 주소(`127.0.0.1`)를 통해 고속으로 수행됩니다.

## 결과 (Consequences)

**얻게 된 이점**

- 후속 질문의 처리 속도가 압도적으로 빨라집니다. 한 번 로드된 데이터프레임과 임포트된 모듈이 메모리에 그대로 보존됩니다. 실제로 최초 1회 `import pandas` 실행 시 약 1.1초가 소요되지만, 동일 커널 내에서의 2회차 호출은 약 0.06초 만에 완료됩니다.
- 프로토콜 메시지 유형에 따라 일반 표준 출력, 최종 식 평가값, 런타임 예외를 객관적으로 명확히 구분하여 수신할 수 있습니다. 이 정밀한 구분은 이후 v0.5.0의 엄격한 실행 판정 체계를 구축하는 핵심 기반이 되었습니다([ADR-017](adr-017-execution-verdict.md)).
- 인터럽트 및 재시작 제어 명령이 Jupyter 표준 프로토콜에 내장되어 있어 신뢰할 수 있는 타임아웃 방어 체계를 손쉽게 구현할 수 있었습니다([ADR-008](adr-008-conventional-sandbox-timeouts.md)).
- 사용자 코드가 치명적인 세그멘테이션 오류나 C 레벨 패닉을 일으켜 커널 프로세스가 비정상 종료되더라도 상위 MCP 서버 프로세스는 안전하게 생존합니다.
- 순수 로컬 루프백 통신만을 사용하므로 물리 네트워크 어댑터가 없는 완전 오프라인 환경에서도 아무런 제약 없이 완벽하게 동작합니다.

**감수한 트레이드오프**

- 커널 프로세스가 로드해 둔 대용량 데이터의 크기만큼 시스템 메모리를 지속적으로 점유합니다.
- 대화가 길어질수록 메모리 상태가 누적됩니다. 이전 호출에서 정의된 변수명이 후속 코드 실행에 의도치 않게 간섭할 위험이 있습니다. 이에 대응하기 위해 커널 메모리를 수동으로 즉시 비울 수 있는 상태 초기화 도구(`reset_kernel_state`)를 함께 제공했습니다.
- 신규 커널 프로세스가 최초 부팅될 때 약 2.5초의 초기 지연이 발생합니다. 이는 이후 백그라운드에 예비 커널을 미리 띄워두는 사전 기동 풀 방식으로 성공적으로 개선했습니다([ADR-012](adr-012-kernel-pool-per-namespace.md)).
- 커널 기동 시 콘솔 로그에 "암호화 없이 TCP로 동작한다"는 Jupyter 안내 경고가 출력됩니다. PC 내부의 로컬 루프백 통신이므로 보안상 무해하나, 처음 접하는 사용자에게 혼란을 줄 수 있습니다.

**이후에 새롭게 드러난 파급 효과**

- 시스템 전체에 단 하나의 커널 프로세스만 존재했기 때문에, 서로 다른 대화 탭을 열어 작업할 경우 변수 공간이 충돌하는 심각한 한계가 드러났습니다. 이에 따라 v0.3.0에서 대화 세션별로 커널을 독립 분리하는 네임스페이스 풀 아키텍처를 도입하게 되었습니다([ADR-011](adr-011-namespace-argument.md), [ADR-012](adr-012-kernel-pool-per-namespace.md)).
