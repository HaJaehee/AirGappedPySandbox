# ADR-002. 호출마다 새 프로세스를 띄우는 대신 영속 Jupyter 커널로 상태를 유지한다

## 상태 (Status)

채택됨 (Accepted) · 2026-07-23, v0.1.0

관련 결정: [ADR-003](adr-003-separate-interpreters.md), [ADR-008](adr-008-conventional-sandbox-timeouts.md), [ADR-012](adr-012-kernel-pool-per-namespace.md), [ADR-017](adr-017-execution-verdict.md)

## 맥락 (Context)

코드 실행 도구를 가장 쉽게 만드는 방법은 호출마다 `python`을 새 프로세스로 띄우는 것이다. 하지만 그러면 호출이 끝날 때마다 메모리가 사라진다.

이 시스템의 전형적인 사용 방식은 "파일 하나를 올려 두고 여러 번 묻기"다. 100MB짜리 엑셀을 pandas로 읽는 데 수 초에서 수십 초가 걸린다. 질문마다 이를 반복하면 응답이 느려지고, 모델은 매번 파일을 읽는 코드를 다시 써야 하므로 실수할 기회도 늘어난다.

실행기에는 출력 캡처, 예외 보고, 무한 루프 중단, 죽은 프로세스 복구 같은 기능도 필요하다. 이를 처음부터 만들면 상당한 양이다.

검토한 선택지는 다음과 같다.

1. **호출마다 새 프로세스.** 단순하지만 상태가 없다.
2. **새 프로세스 + 상태 직렬화.** 결과를 pickle 파일로 저장했다가 다음 호출에서 불러온다. 열린 파일 핸들, DB 연결, import된 모듈의 설정처럼 직렬화할 수 없는 상태가 많고, 큰 데이터프레임은 저장과 복원에도 시간이 든다.
3. **서버 프로세스 안에서 `exec`.** 빠르지만 사용자 코드가 서버를 죽일 수 있고, 무한 루프를 강제로 멈출 방법이 마땅치 않으며, 서버와 같은 인터프리터를 쓸 수밖에 없다.
4. **Jupyter 커널.** 코드 실행을 별도 프로세스로 분리하면서 그 프로세스를 계속 살려 둔다. 출력, 결과, 예외, 인터럽트, 재시작이 이미 프로토콜로 정의되어 있다.

## 결정 (Decision)

jupyter_client로 IPython 커널을 별도 프로세스로 띄우고, 서버가 살아 있는 동안 계속 유지한다.

코드는 shell 채널의 실행 요청으로 보낸다. 결과는 iopub 채널에서 그 요청의 `msg_id`에 딸린 메시지만 골라 모으고, `status: idle`이 오면 끝난 것으로 본다. 요청을 보내기 전에는 앞선 요청이 남긴 메시지를 비운다. 커널 하나는 락으로 보호해 한 번에 한 요청만 처리한다.

서버와 커널 사이의 통신은 ZeroMQ를 127.0.0.1 루프백으로 쓴다.

## 결과 (Consequences)

**좋아진 점**

- 후속 질문이 빠르다. 한 번 읽은 데이터와 import가 메모리에 남는다. 예를 들어 첫 `import pandas`는 약 1.1초, 두 번째는 약 0.06초다.
- 메시지 종류로 출력, 마지막 식의 값, 예외를 구분할 수 있다. 이 구분은 나중에 실행 판정의 재료가 되었다([ADR-017](adr-017-execution-verdict.md)).
- 인터럽트와 재시작이 프로토콜에 들어 있어 시간 제한을 구현하기 쉬웠다([ADR-008](adr-008-conventional-sandbox-timeouts.md)).
- 사용자 코드가 커널을 죽여도 서버는 살아남는다.
- 루프백 통신이라 네트워크 어댑터 없이도 동작한다.

**치른 비용**

- 커널 프로세스가 불러온 데이터만큼 메모리를 계속 차지한다.
- 상태가 쌓인다. 앞선 호출의 변수가 뒤 호출에 의도치 않게 쓰일 수 있다. 이를 비우는 초기화 도구(`reset_kernel_state`)를 함께 두었다.
- 커널 부팅에 약 2.5초가 걸린다. 이후 예비 커널을 미리 띄워 두는 방식으로 대응했다([ADR-012](adr-012-kernel-pool-per-namespace.md)).
- 커널이 뜰 때 "암호화 없이 TCP로 동작한다"는 경고가 로그에 남는다. 루프백 통신이라 실제 위험은 아니지만 처음 보는 사람을 놀라게 한다.

**이후에 드러난 일**

- 커널이 하나뿐이라 여러 대화가 같은 변수 공간을 쓰게 되었다. v0.3.0에서 대화마다 커널을 나누었다([ADR-011](adr-011-namespace-argument.md), [ADR-012](adr-012-kernel-pool-per-namespace.md)).
