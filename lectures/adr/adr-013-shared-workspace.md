# ADR-013. 워크스페이스 디스크 디렉터리는 모든 네임스페이스 세션 간에 공유합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-07-25, v0.3.0 · 실무 사용자와의 직접 검토를 거쳐 확정된 불변 결정

사용자 측의 새로운 공식 요구가 없는 한 재논의하지 않기로 확정했습니다.

관련 결정: [ADR-005](adr-005-snapshot-diff-artifacts.md), [ADR-011](adr-011-namespace-argument.md), [ADR-014](adr-014-write-file-tool.md)

## 맥락 (Context)

[ADR-011](adr-011-namespace-argument.md)과 [ADR-012](adr-012-kernel-pool-per-namespace.md)를 통해 대화 세션별로 독립된 메모리 커널이 배정되었습니다. 이에 따라 "파일시스템의 작업 디렉터리 역시 세션별로 물리적으로 분리해야 하는가?"라는 자연스러운 아키텍처 의문이 제기되었습니다.

워크스페이스를 네임스페이스별 하위 폴더(예: `workspace/ns-3fa1/`)로 강제 격리하면 파일 수준의 격리는 완벽해집니다. 그러나 실제 업무 사용자가 파일을 시스템에 공급하는 현실적인 방식을 고려하면 심각한 사용성 문제가 발생합니다. 사용자는 Windows 파일 탐색기를 열어 마우스 드래그 앤 드롭으로 지정된 워크스페이스 폴더에 엑셀이나 문서를 넣습니다. 세션 네임스페이스 ID는 LLM이 대화를 시작한 이후에야 런타임에 동적으로 발급받는 내부 식별자이므로, 사용자는 대화를 시작하기 전에는 자신이 파일을 어느 하위 폴더에 넣어야 할지 결코 알 수 없습니다. 또한 동일한 작업 디렉터리를 다른 로컬 파일 시스템 MCP 서버와 공유하여 함께 연동하는 운영 환경도 고려해야 했습니다.

## 결정 (Decision)

물리 워크스페이스 디렉터리는 시스템 내의 모든 네임스페이스 세션이 단일 공유 디렉터리로 함께 사용하기로 결정했습니다. 네임스페이스를 통해 격리하는 대상은 순수하게 커널 프로세스의 메모리 상태(변수, 함수, 임포트된 모듈, 로드된 데이터프레임)로 엄격히 한정합니다.

네임스페이스별 하위 디렉터리 분리 방안을 실무진과 심도 있게 검토했으나, 사용자가 명시적으로 원하지 않았습니다. 이에 따라 본 결정은 프로젝트 공식 위키에 "사용자 확인 완료 사항: 신규 공식 요구가 없는 한 본 논의를 다시 번복하여 열지 말 것"이라는 확고한 주의 메모와 함께 영구 기록되었습니다.

## 결과 (Consequences)

**얻게 된 이점**

- 파일 업로드 사용자 경험(UX)이 극도로 단순하게 유지됩니다. 사용자는 시스템 내에 존재하는 단 하나의 워크스페이스 폴더만 인지하면 충분합니다.
- 파일 목록 조회 도구(`list_workspace_files`)와 파일 저장 도구(`write_workspace_file`)가 `namespace` 인자를 복잡하게 수신할 필요가 없습니다. 상태가 없는 단순 유틸리티 도구에서 불필요한 필수 인자를 완전히 제거했습니다.
- 한 대화 창에서 코드를 실행하여 생성해 둔 중간 결과 파일(예: 전처리된 `cleaned_data.csv`)을 다른 대화 창에서 파일명만으로 즉시 이어서 참조하고 분석할 수 있는 뛰어난 세션 간 협업 유연성을 확보했습니다.

**수용한 현실적 절충과 위험**

- 서로 다른 대화 세션 간에 출력 파일명이 충돌할 수 있습니다. 두 대화 창에서 모두 파일명을 `chart.png`로 지정하여 저장하면 뒤에 실행된 차트가 앞선 대화의 차트를 덮어쓰게 됩니다. 이를 완화하기 위해 도구 설명문 규칙에 "워크스페이스는 공유되므로 파일명이 겹치지 않도록 고유하게 작명하라"는 지침을 추가했습니다.
- 두 대화 세션의 코드가 완전히 동일한 밀리초 시점에 동시 실행될 경우 산출물이 교차 오귀속될 수 있습니다. 산출물 탐지기가 공유 디렉터리 전체를 대상으로 스냅샷 차이를 대조하기 때문입니다([ADR-005](adr-005-snapshot-diff-artifacts.md)).
- 특정 대화가 다른 대화의 원본 입력 파일을 덮어쓸 위험이 있습니다. 이를 방지하기 위해 파일 저장 도구는 기본적으로 기존 파일 덮어쓰기를 엄격히 거절하도록 안전장치를 두었습니다([ADR-014](adr-014-write-file-tool.md)). 다만 커널 내부에서 실행되는 임의의 Python 코드 자체는 막지 못합니다.

이러한 잠재적 위험들은 단일 사용자가 자신의 업무용 PC에서 한 번에 하나의 대화 창을 번갈아 가며 작업하는 실제 업무 패턴 하에서는 충분히 수용 가능한 실용적인 위험으로 판단했습니다.

**본 ADR이 주는 엔지니어링 교훈**

"과거에 이미 충분히 논의되어 기각되었으므로 다시 논의하지 않는다"는 확정된 의사결정의 종결을 공식 문서로 남기는 것 역시 ADR의 매우 중요한 존재 이유입니다. 아키텍처를 보다 완벽하고 결벽적으로 격리하고 싶어 하는 후속 개발자가 자칫 파일 격리 카드를 다시 꺼내 들며 시간을 낭비하기 쉬운데, 이 기록이 존재함으로써 과거에 왜 그러한 결론에 도달했는지를 명확히 이해하고 불필요한 논쟁을 종식시킬 수 있습니다.
