# ADR-020. 설치 결과는 pip 출력이 아니라 커널과 인덱스에 직접 확인한다

## 상태 (Status)

채택됨 (Accepted) · 2026-09-22, v0.6.0

관련 결정: [ADR-017](adr-017-execution-verdict.md), [ADR-019](adr-019-side-venv-installs.md), [ADR-021](adr-021-tool-time-budget.md)

## 맥락 (Context)

설치 도구를 만들면서 두 가지 판단이 필요했다. 설치가 성공했다고 언제 말할 것인가, 실패했을 때 원인을 어떻게 알려 줄 것인가.

**성공 판단의 함정.** pip이 종료 코드 0으로 끝났다는 것은 다운로드와 설치가 되었다는 증거일 뿐, 코드를 실행하는 커널에서 import된다는 증거는 아니다. 배포판 이름이 실제 모듈 이름과 다를 수도 있고, 파일이 예상 밖의 위치에 설치될 수도 있다. [ADR-017](adr-017-execution-verdict.md)에서 없앤 "확인하지 않은 성공"이 여기서 다시 생길 수 있었다.

**실패 원인을 가리기 어렵다.** 새 PC에서 가장 흔한 실수는 미러 주소를 설정하지 않는 것이다. 이때 pip은 공개 PyPI로 가려다 실패한다. 그런데 pip의 출력만으로는 이를 알아보기 어렵다.

- 미설정 PC에서 몇 분씩 멈추지 않도록 pip 재시도를 0으로 두었다(`SANDBOX_PIP_RETRIES`). 기본값인 재시도 5회에 대기 시간까지 더하면, 모델은 긴 멈춤 끝의 타임아웃을 일시적 장애로 여기고 다시 시도하곤 한다. 그런데 재시도를 끄면 pip은 연결 오류에 대해 아무것도 출력하지 않는다. "인덱스에 닿지 않는다"와 "미러에 그 패키지가 없다"가 똑같이 "맞는 배포판을 찾을 수 없다(No matching distribution found)"로 나온다.
- 더 고약한 경우가 있다. 미러가 평문 http인데 신뢰 호스트로 등록하지 않으면, pip은 그 인덱스를 오류 없이 조용히 버리고 역시 같은 메시지를 낸다.

pip의 출력을 그대로 믿으면, 설정 문제를 패키지 이름 탓으로 돌리게 된다. 모델은 이름을 바꿔 가며 설치를 반복하고, 사용자는 진짜 원인을 끝내 모른다.

## 결정 (Decision)

**성공은 커널이 확인한다.** `install_status: INSTALLED`는 커널 안에서 `importlib.metadata`로 요청한 배포판마다 버전을 조회해, 모두 답이 왔을 때만 쓴다. 배포판 이름으로 조회하므로 `beautifulsoup4`와 `bs4` 같은 이름 차이에 흔들리지 않는다. pip은 성공했는데 커널이 보지 못하면 `FAILED`로 보고하고, "다운로드는 되었지만 import 경로가 맞지 않는다"고 설명한다.

**실패 원인은 인덱스에 직접 묻는다.** pip의 텍스트로 추측하는 대신 두 가지를 직접 확인한다.

- **pip이 실제로 쓸 인덱스를 알아낸다.** 서버 설정(`SANDBOX_PIP_INDEX_URL`), pip 자체 설정 파일, `PIP_INDEX_URL` 환경 변수, 공개 PyPI 순으로 찾는다. 그 주소와 출처를 응답에 적는다. 미설정 PC라면 "pip의 기본값, 즉 이 PC에는 미러가 설정되지 않았다"고 나온다. 이 한 줄만 보고도 사용자가 원인을 알아채는 경우가 많다.
- **그 인덱스에 직접 접속해 본다.** HTTP 응답이 하나라도 오면(401, 403, 404 포함) "닿는다"로 본다. 가리려는 것은 "네트워크가 거기까지 가지 못한다"와 "갔는데 거절당했다"의 차이이기 때문이다.

이 두 정보로 실패를 다음과 같이 나누고, 각각 고칠 설정의 이름을 짚어 준다.

| 경우 | 알아내는 방법 | 알려 주는 해결책 |
|---|---|---|
| 인덱스에 닿지 않는다 | 인덱스에 직접 접속해 실패 | `SANDBOX_PIP_INDEX_URL`을 확인하라. 공개 PyPI라면 "미러가 설정되지 않았다" |
| 평문 http 인덱스를 pip이 버렸다 | pip 출력의 "신뢰할 수 없는 호스트라 무시한다" 경고 | `SANDBOX_PIP_TRUSTED_HOST`에 호스트 이름을 넣어라 |
| 인덱스는 정상인데 패키지가 없다 | "찾을 수 없다" 메시지와 인덱스 접속 성공 | 배포판 이름과 버전 지정을 확인하라 |
| 시간 상한을 넘겼는데 인덱스는 닿는다 | 인덱스 접속 성공 | 패키지가 크다. `SANDBOX_PIP_TIMEOUT`을 늘려라 |

실패 응답의 `next_action`은 "같은 설치를 반복하지 말고, 사용자에게 무엇을 고쳐야 하는지 한 문장으로 알린 뒤, 가능하면 그 패키지 없이 계속하라"다. 사용자 PC의 설정 문제는 모델이 고칠 수 없기 때문이다.

**문제는 대화 전에 드러낸다.** 사전 점검 도구도 실제로 쓰일 인덱스와 도달 가능 여부를 보고한다. 필수 패키지 판정보다 먼저 실행되며, 실패해도 경고일 뿐 점검 자체를 실패시키지는 않는다. 대화 도중에야 설정 문제를 알게 되는 일을 줄이려는 것이다. 설정 예시 파일과 수동 실행 스크립트에도 미러 설정 칸을 드러내, 빠뜨리기 쉬운 지점에서 눈에 띄게 했다.

## 결과 (Consequences)

**좋아진 점**

- `INSTALLED`는 믿을 수 있는 말이 되었다.
- 실패하면 사용자에게 무엇을 고쳐야 하는지가 설정 이름까지 정확히 전달된다.
- 모델이 패키지 이름을 바꿔 가며 헛된 재시도를 하는 일이 줄었다.

**치른 비용**

- 실패할 때 인덱스 접속이 한 번 더 일어난다.
- 설치 후 커널에 버전을 묻는 왕복이 추가된다.
- 진단 규칙이 pip 출력의 특정 문구에 일부 의존한다. pip 버전이 바뀌어 문구가 달라지면 분류가 틀릴 수 있다.

**시험 방법**

실제 미러 없이 실패 경로를 시험하기 위해, 테스트는 RFC 2606이 절대 해석되지 않도록 예약한 도메인을 인덱스 주소로 쓴다. 어떤 네트워크에서 돌려도 항상 같은 방식으로 실패하므로 결과가 흔들리지 않는다.
