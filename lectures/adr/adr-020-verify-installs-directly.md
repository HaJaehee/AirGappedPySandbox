# ADR-020. 패키지 설치 성공 여부는 pip 출력이 아닌 커널 내부에서 직접 검증합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-09-22, v0.6.0

관련 결정: [ADR-017](adr-017-execution-verdict.md), [ADR-019](adr-019-side-venv-installs.md), [ADR-021](adr-021-tool-time-budget.md)

## 맥락 (Context)

패키지 동적 설치 도구(`install_python_packages`)를 새롭게 설계하면서 두 가지 핵심적인 엔지니어링 판단 기준이 필요했습니다. 첫째는 설치가 완벽히 성공했다고 언제 확정할 것인가이며, 둘째는 설치가 실패했을 때 모델과 사용자에게 실패 원인을 어떻게 투명하게 알려줄 것인가였습니다.

**성공 판정의 함정.** pip 서브프로세스가 리턴 코드 0으로 끝났다는 사실은 단지 원격 저장소에서 파일 다운로드와 바이트 압축 해제가 완료되었다는 물리적 증거일 뿐, 실제 코드를 실행할 Jupyter 커널 프로세스 내부에서 해당 패키지를 성공적으로 임포트할 수 있다는 보증이 되지 못합니다. 패키지의 배포판 이름(Distribution Name)이 실제 Python 코드 내의 import 모듈명과 다를 수도 있고, 패키지 파일이 커널의 모듈 검색 경로(`sys.path`)에서 벗어난 엉뚱한 위치에 설치되었을 수도 있습니다. 과거 [ADR-017](adr-017-execution-verdict.md)에서 경계했던 "확인되지 않은 성공" 판정의 위험이 여기서 다시 되살아날 수 있었습니다.

**실패 원인을 식별하기 어려운 한계.** 새로운 업무용 PC에 배포할 때 현업에서 가장 빈번하게 발생하는 실수는 사내 미러 서버 주소 환경 변수(`SANDBOX_PIP_INDEX_URL`)를 누락하는 것입니다. 이때 pip은 폐쇄망에서 접근 불가능한 공용 인터넷 PyPI(`pypi.org`)로 접속을 시도하다가 실패하게 됩니다. 그러나 pip 프로세스가 콘솔에 남기는 기본 로그 텍스트만으로는 그 근본 원인을 명확히 파악하기가 매우 어렵습니다.

- 미설정 PC에서 수 분 동안 멈춰 서서 사용자를 기다리게 만들지 않기 위해 pip의 네트워크 재시도 횟수를 0회(`SANDBOX_PIP_RETRIES=0`)로 강제했습니다. 만약 기본값인 5회 재시도에 지수 백오프 대기 시간까지 누적되면, 모델은 긴 지연 끝에 발생한 타임아웃을 일시적인 일회성 장애로 오판하고 무의미한 재시도를 반복하기 때문입니다. 그런데 재시도를 완전히 끄면 pip은 상세 연결 에러 로그를 생략해 버립니다. 그 결과 "네트워크가 사내 미러에 닿지 않는다"는 인프라 장애와 "미러 서버에 해당 패키지 휠이 없다"는 패키지 누락 문제가 둘 다 똑같이 "일치하는 배포판을 찾을 수 없다 (No matching distribution found)"라는 모호한 동일 메시지로 출력됩니다.
- 더욱 까다로운 예외 상황도 존재합니다. 사내 미러 서버가 비보안 평문 HTTP를 사용하는데 신뢰 호스트(`SANDBOX_PIP_TRUSTED_HOST`)로 등록되지 않은 경우, pip은 에러 메시지를 명확히 띄우는 대신 해당 인덱스를 조용히 무시해 버리고 역시 동일한 에러 메시지를 출력합니다.

만약 pip이 출력한 표면적인 에러 메시지만을 그대로 모델에게 전달한다면, 모델은 환경 설정 누락 문제를 엉뚱하게 패키지 이름 오타 탓으로 돌리게 됩니다. 모델은 패키지 철자를 이리저리 바꿔가며 헛된 재시도를 반복하고, 인간 사용자는 사내 미러 설정이 빠졌다는 진짜 원인을 끝내 인지하지 못하게 됩니다.

## 결정 (Decision)

**설치 성공 여부는 커널 프로세스가 직접 검증합니다.** 최종 성공 판정인 `install_status: INSTALLED`는 pip 실행 직후 백엔드 커널 내부에서 `importlib.metadata` API를 직접 호출하여, 요청된 모든 배포판 패키지의 버전 조회가 성공했을 때만 엄격하게 발급합니다. 배포판 명칭을 기준으로 질의하므로 `beautifulsoup4`와 `bs4`처럼 패키지명과 모듈명이 다른 경우에도 흔들리지 않고 정확히 검증해 냅니다. 만약 pip은 정상 종료되었으나 커널이 해당 패키지를 인식하지 못한다면 `FAILED`로 판정하고 "다운로드는 완료되었으나 커널의 모듈 검색 경로가 일치하지 않는다"고 정직하게 설명합니다.

**실패의 근본 원인은 인덱스 서버에 직접 질의하여 규명합니다.** pip이 출력한 불명확한 텍스트를 추측하는 대신 시스템이 다음 두 가지 사실을 직접 확인합니다.

- **pip이 실제로 참조하게 될 인덱스 URL의 출처를 추적합니다.** 서버 환경 변수(`SANDBOX_PIP_INDEX_URL`), pip 자체 설정 파일, OS 환경 변수 `PIP_INDEX_URL`, 그리고 기본값인 공용 PyPI 주소 순으로 확인합니다. 실제로 적용된 인덱스 주소와 그 설정 출처를 반환 응답에 명확히 표기합니다. 만약 미설정 PC라면 "pip의 기본값인 pypi.org를 바라보고 있으며, 즉 이 PC에는 사내 미러가 설정되지 않았다"고 분명히 적시합니다. 이 한 줄의 정직한 피드백만으로도 사용자는 자신의 설정 실수를 즉각 깨닫게 됩니다.
- **해당 인덱스 서버 엔드포인트에 시스템이 직접 HTTP 연결을 시도해 봅니다.** HTTP 응답 코드가 무엇이든(401 인증 요구, 403 거부, 404 미존재 포함) 일단 수신되기만 하면 네트워크 수준에서 "도달 가능(Reachable)"한 것으로 판정합니다. 시스템이 구분하고자 하는 핵심은 "사내망 패킷이 인덱스 서버까지 물리적으로 도달하지 못하는가"와 "도달했으나 패키지가 없는가"의 차이이기 때문입니다.

이 두 가지 관측 결과를 결합하여 실패 유형을 다음과 같이 정밀 분류하고, 각각 구체적으로 수정해야 할 환경 변수 이름을 명시합니다.

| 분류된 실패 원인 | 시스템의 진단 방법 | 반환 응답이 제시하는 구체적 해결책 |
|---|---|---|
| 미러 인덱스 서버에 도달하지 못함 | 인덱스 직접 소켓 연결 시도 실패 | `SANDBOX_PIP_INDEX_URL`을 확인하십시오. 공용 PyPI 주소라면 "사내 미러 설정이 누락되었다"고 안내합니다. |
| 비보안 평문 HTTP 인덱스를 pip이 조용히 폐기함 | pip 출력 내의 "신뢰할 수 없는 호스트이므로 무시한다" 경고 감지 | 환경 변수 `SANDBOX_PIP_TRUSTED_HOST`에 사내 미러 도메인 호스트명을 명시적으로 등록하십시오. |
| 미러 인덱스는 정상이지만 해당 패키지가 미러에 없음 | 인덱스 직접 접속은 성공했으나 "찾을 수 없다" 발생 | 패키지 배포판 명칭 철자와 요청한 버전 조건식을 다시 확인하십시오. |
| 허용 설치 시간 상한을 초과했으나 인덱스는 정상 도달함 | 인덱스 직접 접속은 정상 성공 | 설치 대상 패키지 휠의 용량이 매우 큽니다. `SANDBOX_PIP_TIMEOUT` 상한을 더 늘려주십시오. |

실패 응답의 최하단 `next_action` 지침은 "동일한 설치를 무의미하게 반복하지 마십시오. 사용자에게 어떤 환경 변수 설정을 수정해야 하는지 한 문장으로 명확히 설명한 뒤, 가능한 경우 해당 패키지 없이 다른 방법으로 분석을 계속 진행하십시오"로 고정했습니다. 사용자 로컬 PC의 환경 설정 누락 문제는 모델이 코드를 아무리 고치더라도 스스로 해결할 수 없기 때문입니다.

**설정 문제는 대화가 시작되기 전에 선제적으로 드러냅니다.** 현장 배포 시 구동하는 사전 점검 도구(`check_env.py`) 역시 실제로 사용될 인덱스 주소와 네트워크 도달 가능 여부를 가장 먼저 검사하여 콘솔에 보고합니다. 필수 라이브러리 검사보다 앞서 실행되며, 도달에 실패하더라도 경고 로그만 남길 뿐 점검 스크립트 자체를 중단시키지는 않습니다. 사용자가 LLM과 대화를 나누는 도중에 뒤늦게 인프라 설정 오류를 발견하고 당황하는 상황을 방지하기 위함입니다. 공식 설정 예제 파일과 수동 실행 스크립트에도 사내 미러 설정 항목을 명시적으로 노출하여 누락을 방지했습니다.

## 결과 (Consequences)

**얻게 된 이점**

- 도구가 반환하는 `INSTALLED` 상태는 언어 모델과 사용자 모두가 100% 신뢰할 수 있는 확실한 성공 지표가 되었습니다.
- 패키지 설치가 실패했을 때 사용자가 구체적으로 어떤 환경 변수를 수정해야 하는지 설정 변수명 수준까지 정확하게 전달됩니다.
- 소형 모델이 패키지 철자를 엉뚱하게 바꿔가며 의미 없는 재시도 루프에 빠지는 비효율을 완벽히 차단했습니다.

**감수한 트레이드오프**

- 설치 실패가 발생했을 때 인덱스 서버로의 추가적인 진단 HTTP 소켓 통신이 1회 더 발생합니다.
- 설치가 성공했을 때도 커널 내부에서 패키지 버전을 조회하는 추가적인 IPC 왕복 검증 오버헤드가 수반됩니다.
- 진단 알고리즘의 일부가 pip 표준 에러 출력의 특정 영문 패턴에 부분적으로 의존합니다. 만약 향후 pip 메이저 버전이 업그레이드되면서 내부 출력 문구가 변경될 경우 진단 분류가 영향을 받을 수 있습니다.

**결정론적 테스트 기법**

실제 사내 미러 서버가 없는 외부 개발 환경에서도 이러한 다양한 실패 경로들을 완벽히 테스트하기 위해, 단위 테스트 스위트는 RFC 2606 표준에 의해 전 세계 인터넷에서 절대 네임 서버가 해석되지 않도록 영구 예약된 특수 도메인(`.invalid`, `.test`)을 모의 인덱스 주소로 주입합니다. 이를 통해 인터넷이 켜져 있든 꺼져 있든 관계없이 언제나 100% 동일한 방식으로 결정론적인 네트워크 단절 실패를 재현할 수 있습니다.
