# ADR-014. 코드를 직접 실행하지 않는 독립적인 파일 기록 전용 도구를 분리 신설합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-08-04, v0.4.0

v0.8.0에서 [ADR-022](adr-022-append-tool.md)가 보완했습니다. 저장 도구에 이어 쓰기 모드를 두지 않는 결정은 유지하되, 응답 한 번의 출력 한도보다 긴 파일을 위해 별도 도구 `append_workspace_file`을 신설했습니다. 아래 결정의 "컨텍스트 윈도우가 파일 크기를 먼저 제한한다"는 근거는 출력 한도를 놓친 것이었습니다.

관련 결정: [ADR-005](adr-005-snapshot-diff-artifacts.md), [ADR-007](adr-007-rules-in-tool-descriptions.md), [ADR-010](adr-010-run-script-file.md), [ADR-013](adr-013-shared-workspace.md)

## 맥락 (Context)

사용자가 "피보나치 수열을 구하는 코드를 작성하여 fib.py라는 파일로 저장해 줘"라고 요청했을 때, v0.3.0 이전 버전까지는 일반 코드 실행 도구(`execute_python_code`)만을 사용하여 처리해야 했습니다. 따라서 모델은 파일 I/O를 수행하는 Python 코드를 작성해야 했고, 그 코드 내부에 실제로 저장할 대상 소스코드를 문자열 리터럴로 중첩 삽입해야 했습니다. 코드 문자열 내부에 또 다른 코드가 포함되는 기이한 자기 참조 구조가 형성됩니다. 따옴표가 이중 삼중으로 겹치고, 저장할 소스코드 안에 docstring이나 역슬래시가 포함되어 있다면 복잡한 이스케이프 처리까지 완벽히 해내야 했습니다.

이 패턴은 중소형 언어 모델이 가장 높은 확률로 실패하는 취약 지점이었습니다. 가장 흔하게 발생했던 실패 증상은 파일 저장 로직을 통째로 누락한 채, 저장해야 할 소스코드 자체를 커널에서 그냥 실행해 버리고 콘솔 출력만 덜렁 내놓는 패턴이었습니다.

## 결정 (Decision)

Python 인터프리터를 거치지 않고 순수 텍스트 데이터를 디스크 파일로 직접 기록하는 독립 도구인 `write_workspace_file(filename, content, overwrite=false)`를 새롭게 추가하기로 결정했습니다. 복잡한 따옴표 중첩 구조 대신, 파일명과 파일 내용이라는 평평(Flat)한 두 개의 독립 문자열 인자를 수신합니다.

세부 설계 결정 사항은 다음과 같습니다.

- **`namespace` 인자를 받지 않습니다.** 본 도구는 커널 메모리 상태를 쓰지 않는 무상태 유틸리티이며, 워크스페이스는 모든 세션이 공유합니다([ADR-013](adr-013-shared-workspace.md)). 불필요한 필수 인자는 소형 모델의 호출 실패 확률만 높입니다.
- **도구 설명문에 무거운 사용 규칙을 주입하지 않습니다.** 규칙 묶음은 주로 커널 실행에 관한 것이며 0번 항목부터 `namespace`를 요구합니다. 단순한 유틸리티 도구를 불필요하게 무겁게 만들지 않습니다([ADR-007](adr-007-rules-in-tool-descriptions.md)). 대신 실행 도구의 설명문 내부에 "순수 파일 저장만 하려면 이 도구를 쓰라"는 안내를 추가하여 상호 경계를 분리했습니다.
- **엄격한 워크스페이스 내부 경로를 강제합니다.** 기록할 파일이 아직 디스크에 없으므로 부모 폴더의 정규화된 절대 경로를 기준으로 경계를 검증합니다. 절대 경로 표기, 드라이브 문자, 상위 폴더 탈출(`..`), 그리고 Windows 시스템 예약 장치명(`NUL`, `CON`, `PRN`, `AUX`, `COM1`~`COM9` 등)의 사용을 엄격히 차단합니다. Windows 환경에서는 이러한 예약 장치명으로 파일 쓰기를 시도할 경우 시스템이 에러를 발생시키지 않고 데이터를 조용히 폐기해 버리기 때문입니다. 하위 디렉터리 생성은 모든 검증을 완벽히 통과한 경우에만 안전하게 수행하며, 경로 앞부분의 `./workspace/` 상대 접두사는 유연하게 정규화하여 제거합니다.
- **기존 파일 덮어쓰기는 기본적으로 엄격히 거절합니다 (`overwrite=false`).** 작업 폴더에는 사용자가 업로드한 소중한 원본 데이터 파일들이 함께 상주합니다. 거절 메시지에는 "`overwrite=true` 옵션을 추가하여 다시 호출하거나 다른 파일명을 사용하십시오"라는 구체적인 해결 가이드를 함께 제공합니다.
- **전달받은 바이트 그대로 원자적으로 저장합니다.** UTF-8 인코딩, BOM 없음, 줄바꿈 문자(LF)를 그대로 유지하여 기록합니다. Windows C 런타임의 텍스트 모드가 줄바꿈 문자를 CRLF로 자동 변환하지 않도록 바이너리 모드로 제어하여, 모델이 전송한 소스코드와 디스크 파일의 내용이 바이트 단위로 100% 완벽히 일치하도록 보장합니다.
- **단일 파일 쓰기 용량 상한을 1MB(`SANDBOX_MAX_WRITE_BYTES`)로 제한합니다.** 파일 본문은 LLM 모델이 직접 생성한 텍스트이므로 컨텍스트 윈도우 한도에 의해 1차적으로 제어됩니다. 이 상한은 잠재적인 무한 루프 폭주를 방어하기 위한 추가 안전장치입니다. 동일한 이유로 인터페이스를 복잡하게 만드는 이어 쓰기(Append) 모드는 의도적으로 배제했습니다.
- **도구 고유의 명확한 반환 응답 포맷을 정의합니다.** 최상단 첫 줄은 `write_status: SUCCESS` 또는 `ERROR`로 시작하며, 기록된 파일 경로, 파일 크기(바이트), 총 줄 수, 그리고 산출물 마크다운 링크가 차례로 노출됩니다. 링크 생성은 실행 도구와 동일한 스냅샷 차이 대조 엔진을 재사용하므로, 파일 저장을 시도했으나 디스크에 파일이 감지되지 않는 조용한 I/O 실패를 즉각 감지하고 경고할 수 있습니다([ADR-005](adr-005-snapshot-diff-artifacts.md)). 특히 `.py` 스크립트 파일을 저장했을 때는 하단에 "`run_python_file` 도구로 실행하십시오"라는 힌트와 함께, 그 호출에는 `namespace` 인자가 필수라는 사실을 친절히 안내합니다.

아울러 동일 릴리스에서 스크립트 실행 도구(`run_python_file`)가 `.py` 확장자가 아닌 임의의 파일을 커널에 전송하기 전 사전 거절하도록 인터페이스 검증을 함께 강화했습니다([ADR-010](adr-010-run-script-file.md)).

## 결과 (Consequences)

**얻게 된 이점**

- 소형 언어 모델이 가장 빈번하게 실패하던 코드 중첩 작성 패턴을 완벽히 해소했습니다. "스크립트 저장 후 실행"이라는 워크플로가 저장 도구와 스크립트 실행 도구라는 두 번의 직관적인 독립 호출로 안정화되었습니다. (실제 기능 검증 테스트에서 1부터 10까지의 피보나치 수열 합인 143을 정확히 산출하는 시나리오를 통과했습니다.)
- 본 시스템에서 가장 엄격한 경로 보안 검증이 적용되는 관문 역할을 수행합니다. 새로운 물리 파일을 디스크에 생성하는 유일한 도구이므로 디렉터리 경로 탈출을 원천 봉쇄할 수 있게 되었습니다.

**감수한 트레이드오프**

- 시스템이 노출하는 도구의 총수가 하나 더 증가했습니다. 도구의 종류가 늘어날수록 모델이 비슷한 도구 사이에서 선택을 혼동할 잠재적 위험이 있습니다. 도구 설명문 간의 상호 교차 참조 힌트를 통해 이를 완화했으나, 향후 도구 명칭을 수정할 때 이러한 연계 문구들을 함께 동기화해야 하는 관리 포인트가 늘어났습니다.
- 본 저장 도구의 응답에는 `SUCCESS` 상태가 사용되는 반면, 코드 실행 도구에는 `SUCCESS`가 존재하지 않습니다. 파일 디스크 쓰기는 MCP 서버가 물리적 결과를 100% 직접 확인할 수 있는 작업이기 때문이지만, 처음 접하는 사용자에게는 다소 일관성이 없어 보일 수 있습니다. "시스템이 직접 확인하고 보증할 수 있는 사실만을 긍정한다"는 동일한 정직성 원칙에 기반하고 있음을 문서로 지속적으로 설명해야 합니다([ADR-017](adr-017-execution-verdict.md)).
