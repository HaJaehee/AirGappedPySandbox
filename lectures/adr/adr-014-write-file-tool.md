# ADR-014. 코드를 실행하지 않는 파일 저장 전용 도구를 둔다

## 상태 (Status)

채택됨 (Accepted) · 2026-08-04, v0.4.0

관련 결정: [ADR-005](adr-005-snapshot-diff-artifacts.md), [ADR-007](adr-007-rules-in-tool-descriptions.md), [ADR-010](adr-010-run-script-file.md), [ADR-013](adr-013-shared-workspace.md)

## 맥락 (Context)

사용자가 "이 코드를 fib.py로 저장해 줘"라고 하면, v0.3.0까지는 코드 실행 도구로 처리할 수밖에 없었다. 모델은 파일을 쓰는 Python 코드를 짜야 하고, 그 코드 안에 저장할 소스를 문자열로 넣어야 했다. 코드 안에 코드가 들어가는 자기 참조 구조다. 따옴표가 겹치고, 저장할 소스에 삼중 따옴표나 역슬래시가 있으면 이스케이프까지 해야 한다.

이 패턴은 중소형 모델이 가장 확실하게 무너지는 곳이었다. 흔한 실패는 파일을 쓰는 부분을 통째로 빼먹고, 저장해야 할 코드를 그냥 실행해 결과만 출력하는 것이었다.

## 결정 (Decision)

코드를 실행하지 않고 텍스트를 그대로 파일로 저장하는 도구 `write_workspace_file(filename, content, overwrite=false)`를 추가한다. 평평한 문자열 두 개가 중첩 구조를 대신한다.

세부 결정은 다음과 같다.

- **`namespace`를 받지 않는다.** 이 도구는 상태를 쓰지 않고, 워크스페이스는 어차피 공유된다([ADR-013](adr-013-shared-workspace.md)). 필요 없는 필수 인자는 실패할 길만 늘린다.
- **사용 규칙을 설명문에 붙이지 않는다.** 규칙은 주로 커널에 관한 것이고 첫 항목부터 `namespace`를 요구한다. 가벼운 도구를 무겁게 만들지 않는다([ADR-007](adr-007-rules-in-tool-descriptions.md)). 대신 실행 도구의 설명문에 "저장만 하려면 이 도구를 써라"는 한 줄을 넣어 두 도구의 영역을 나눈다.
- **경로는 워크스페이스 안으로 강제한다.** 파일이 아직 없으므로 상위 폴더를 기준으로, 실제 경로로 풀어 본 뒤 확인한다. 절대 경로와 드라이브 문자, `..`, Windows 예약 장치 이름(`NUL`, `CON`, `COM1` 등)을 거절한다. 예약 이름을 거절하는 이유는 Windows가 이런 이름으로의 쓰기를 오류 없이 받아서 버리기 때문이다. 하위 폴더는 검사를 통과한 뒤에만 만든다. 앞에 붙은 `./workspace/`는 떼어 낸다.
- **덮어쓰기는 기본적으로 거절한다.** 같은 폴더에 사용자가 올린 원본 PDF와 엑셀이 있다. 거절 메시지에는 "`overwrite=true`로 다시 부르거나 다른 이름을 써라"는 해결 방법을 담는다. 약한 모델은 추상적인 규칙보다 이런 구체적인 지시를 훨씬 잘 따른다.
- **받은 그대로 쓴다.** UTF-8, BOM 없이, 줄바꿈을 LF 그대로 쓴다. Windows의 텍스트 모드가 줄바꿈을 CRLF로 바꾸지 않게 해서, 모델이 보낸 내용과 파일이 바이트 단위로 같게 만든다.
- **크기 상한은 1MB다(`SANDBOX_MAX_WRITE_BYTES`).** 내용은 모델이 직접 만든 텍스트라 모델의 컨텍스트가 이미 크기를 제한한다. 이 상한은 폭주하는 루프를 막는 안전장치일 뿐이다. 같은 이유로 이어 쓰기 모드는 두지 않았다.
- **응답은 자기만의 모양을 쓴다.** 첫 줄은 `write_status: SUCCESS` 또는 `ERROR`, 이어서 경로, 바이트 수, 줄 수, 그리고 산출물 링크다. 링크는 실행 도구와 같은 스냅샷 비교로 만들기 때문에, 저장했는데 차이가 비어 있으면 조용한 실패로 경고할 수 있다([ADR-005](adr-005-snapshot-diff-artifacts.md)). `.py` 파일을 저장하면 "`run_python_file`로 실행하라"는 힌트를 붙이고, 그 호출에는 `namespace`가 필요하다는 사실도 함께 알린다.

같은 릴리스에서 스크립트 실행 도구가 `.py`가 아닌 파일을 커널에 보내기 전에 거절하도록 고쳤다. 설명문에는 `.py`라고 적혀 있었지만 실제로 강제하지 않았고, 저장 도구가 생기면서 이 경로를 지나는 일이 많아질 것이었기 때문이다([ADR-010](adr-010-run-script-file.md)).

## 결과 (Consequences)

**좋아진 점**

- 작은 모델이 가장 자주 실패하던 패턴이 사라졌다. "저장하고 실행하기"가 저장 도구와 스크립트 실행 도구, 두 번의 단순한 호출로 끝난다. 검증에서는 저장 후 실행으로 1부터 10까지의 피보나치 수의 합(143)을 확인했다.
- 경로 검증이 가장 엄격한 곳이 이 도구다. 새 파일을 만드는 유일한 도구라서 경로 탈출을 막을 필요가 가장 크다.

**치른 비용**

- 도구가 하나 늘었다. 도구가 늘면 모델이 비슷한 도구 사이에서 잘못 고를 위험도 는다. 설명문끼리 서로를 가리키게 해서 줄였지만, 도구 이름이나 설명문을 고칠 때 이 연결 문구를 함께 살펴야 한다.
- 이 도구의 응답에는 `SUCCESS`가 있지만 실행 도구에는 없다. 파일 쓰기는 서버가 직접 확인할 수 있는 일이라서 그렇지만, 처음 보는 사람에게는 일관성이 없어 보일 수 있다. 원칙은 같다는 점을 문서로 설명해야 한다([ADR-017](adr-017-execution-verdict.md)).
