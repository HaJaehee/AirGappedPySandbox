# ADR-012. 네임스페이스마다 독립 커널을 배정하고 상시대기 예비 커널 풀로 관리합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-07-25, v0.3.0

관련 결정: [ADR-002](adr-002-persistent-jupyter-kernel.md), [ADR-011](adr-011-namespace-argument.md), [ADR-019](adr-019-side-venv-installs.md), [ADR-021](adr-021-tool-time-budget.md)

## 맥락 (Context)

[ADR-011](adr-011-namespace-argument.md)을 통해 매 도구 호출마다 세션 네임스페이스를 구분할 수 있는 인터페이스가 마련되었습니다. 이제 개별 네임스페이스별로 실제 메모리 변수 공간을 아키텍처 수준에서 어떻게 완벽히 분리할 것인가를 결정해야 했습니다.

기술적으로 검토할 수 있는 접근 방식은 크게 두 가지였습니다. (당시 공식 커밋 기록에는 두 번째 방식을 채택했다는 사실만 남아 있으나, 교육적 이해를 돕기 위해 두 대안의 기술적 트레이드오프를 비교하여 정리했습니다.)

1. **단일 커널 프로세스 내부에서 네임스페이스별 전역 딕셔너리(`globals()`)를 교체합니다.** 실행할 때마다 해당 세션 전용 변수 딕셔너리를 동적으로 갈아 끼우는 방식입니다. 프로세스가 하나뿐이므로 메모리 소모가 적습니다. 그러나 `sys.modules`에 임포트된 모듈 객체, 모듈 검색 경로(`sys.path`), matplotlib의 전역 시각화 상태, OS 현재 작업 디렉터리(cwd) 등 프로세스 레벨에서 공유되는 런타임 상태들은 결코 격리할 수 없습니다. 더욱이 한 대화 세션에서 무한 루프가 발생하면 다른 모든 대화 세션의 실행이 함께 차단되며, 타임아웃 복구를 위해 커널을 재시작하면 모든 사용자의 데이터가 한꺼번에 소멸합니다.
2. **네임스페이스마다 완전히 독립된 커널 프로세스를 1:1로 할당합니다.** OS 프로세스 레벨의 완벽한 상태 격리를 달성할 수 있습니다. 반면 활성화된 세션 수만큼 OS 메모리가 정비례하여 증가하며, 신규 커널을 부팅할 때마다 약 2.5초의 초기 지연이 발생합니다.

## 결정 (Decision)

완벽한 장애 격리를 위해 네임스페이스마다 독자적인 IPython 커널 서브프로세스를 1:1로 배정하기로 결정했습니다. 그리고 프로세스 다중화에 따른 기동 지연과 메모리 누적 비용을 효과적으로 제어하기 위해 **커널 풀(Kernel Pool)** 아키텍처를 도입했습니다.

- **사전 기동 예비 커널 (Pre-warmed Reserve Kernel)**: MCP 서버가 최초 기동할 때 백그라운드에 예비 커널 1개를 미리 부팅해 둡니다. 사용자의 새로운 대화 세션이 유입되면 이 사전 가동된 예비 커널을 즉각 인계하므로, 첫 번째 도구 호출이 기동 지연 없이 약 0.06초 만에 초고속으로 착수됩니다. 예비 슬롯이 비어 있을 때만 부득이하게 동기 방식으로 현장 부팅을 진행합니다.
- **백그라운드 관리 워커 스레드**: 30초 주기로 기상하여 30분(`SANDBOX_NS_IDLE_TIMEOUT`) 이상 호출이 없는 유휴 네임스페이스의 커널 프로세스를 안전하게 종료하고, 예비 커널 슬롯이 비어 있다면 새로운 커널을 백그라운드에서 부팅하여 채워 넣습니다. 시간이 오래 걸리는 커널 부팅은 풀의 전역 락 바깥에서 독립적으로 수행합니다.
- **동시 활성 커널 개수 상한 집행**: 시스템 전체에서 동시에 유지되는 최대 활성 네임스페이스 수를 8개(`SANDBOX_MAX_NAMESPACES`)로 제한합니다. 풀이 가득 찬 상태에서 신규 세션이 들어오면 가장 오랫동안 호출되지 않은 세션(LRU)부터 메모리에서 안전하게 회수합니다.
- **세션별 독립 상태 초기화**: `reset_kernel_state` 도구는 전체가 아닌 지정된 해당 네임스페이스의 커널 프로세스만을 선별하여 안전하게 재시작합니다.
- **유휴 회수 세션의 투명한 재생성**: 유휴 정리된 네임스페이스 ID로 다시 도구 호출이 들어올 경우, 깨끗한 빈 커널 프로세스를 새롭게 생성하여 즉각 할당합니다.

## 결과 (Consequences)

**얻게 된 이점**

- OS 프로세스 레벨의 완벽한 세션 격리를 달성했습니다. 특정 대화 세션에서 무한 루프가 발생하거나 강제 프로세스 재시작이 단행되더라도 다른 대화 세션들은 전혀 영향을 받지 않습니다. 각 커널마다 독립된 락(`RLock`)을 사용하기 때문입니다.
- 신규 대화 세션의 첫 실행 요청을 대기 시간 없이 즉시 처리할 수 있게 되었습니다.
- 최대 동시 유지 커널 개수가 제한되므로, 시스템 전체의 최대 메모리 소비량이 엄격한 예측 가능한 범위(활성 커널 최대 8개 + 예비 커널 1개) 내로 통제됩니다.
- 유휴 세션 회수 메커니즘은 현대 클라우드 멀티테넌트 샌드박스들이 비활성 컨테이너를 관리하는 방식과 정확히 동일한 아키텍처 철학에 기반합니다.

**감수한 트레이드오프**

- 활성 대화 세션 수에 비례하여 시스템 메모리가 소모됩니다. 동일한 대용량 파일을 여러 대화 창에서 각각 열어 분석할 경우 각 커널마다 메모리에 중복 로드됩니다. 이는 완벽한 세션 격리를 위해 지불하는 불가피한 비용입니다.
- 상시 대기 중인 예비 커널 1개가 실제로 사용되기 전까지 항상 기본 유휴 메모리를 점유합니다.
- 유휴 커널 회수가 백그라운드에서 조용히 일어납니다. 30분간 자리를 비웠다가 동일한 세션 ID로 돌아온 모델은 응답 문구상으로는 기존 세션을 재사용한다는 안내를 받지만, 실제로는 새로 부팅된 빈 커널을 배정받게 됩니다. 따라서 이전 대화의 변수를 참조하려 할 때 비로소 `NameError`를 통해 세션 만료 사실을 확인하게 됩니다.
- "실행 중인 모든 커널에 동시에 적용해야 하는" 시스템 차원의 브로드캐스팅 작업이 새롭게 발생했습니다. 사내 미러에서 신규 패키지를 설치한 후 모든 활성 커널의 검색 경로에 venv 경로를 주입하는 작업이 대표적입니다. 이때 장시간 연산을 수행 중인 특정 커널을 얼마 동안 대기할 것인가에 대한 정밀한 시간 예산 정책이 필요해졌습니다([ADR-019](adr-019-side-venv-installs.md), [ADR-021](adr-021-tool-time-budget.md)).
