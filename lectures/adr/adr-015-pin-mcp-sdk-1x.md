# ADR-015. MCP Python SDK를 1.x 대에 고정한다

## 상태 (Status)

채택됨 (Accepted) · 2026-08-26

관련 결정: [ADR-004](adr-004-portable-python-bundle.md), [ADR-011](adr-011-namespace-argument.md), [ADR-021](adr-021-tool-time-budget.md)

## 맥락 (Context)

> 이 결정에 대해 남은 기록은 커밋 메시지 한 줄("mcp 2버전(stateless) 미사용으로 수정")과 의존성 목록의 변경뿐이다. 아래 맥락 중 일부는 당시 코드 구조를 보고 추론한 것이다.

서버 의존성 목록은 처음에 `mcp>=1.2.0`처럼 하한만 적혀 있었다. 2026-08-26에 상한이 붙어 `mcp>=1.2.0,<2`가 되었다. 커밋 메시지로 보아, 2.x 계열이 무상태(stateless) 운용을 전제로 한다는 판단이 있었던 것으로 보인다.

이 서버가 1.x에 기대는 부분은 여럿이다.

- **서버가 상태를 가진다.** 긴 수명의 stdio 연결 하나 위에서, 네임스페이스와 커널의 대응표, 예비 커널, 진행 중인 설치 작업 목록을 메모리에 들고 있다. 이 시스템에서 "상태"는 부수적인 것이 아니라 존재 이유다([ADR-002](adr-002-persistent-jupyter-kernel.md)).
- **1.x의 API를 직접 쓴다.** FastMCP 고수준 API, 스키마에서 숨겨지는 컨텍스트 인자, 진행 알림, 저수준 서버 객체에 버전 정보를 넣는 방식 등이다. 요청 메타데이터에서 대화 id를 읽는 미래 대비 코드도 1.x의 요청 컨텍스트 구조를 전제로 한다([ADR-011](adr-011-namespace-argument.md)).
- **폐쇄망 배포는 빌드 시점에 굳는다.** 빌드 PC에서 설치한 버전이 그대로 반입된다. 상한이 없으면, 다음에 패키지를 다시 만들 때 아무도 검증하지 않은 메이저 버전이 조용히 들어올 수 있다. 오프라인 휠을 다시 받을 때도 마찬가지다.

## 결정 (Decision)

서버 의존성을 `mcp>=1.2.0,<2`로 고정한다. 2.x 계열은 쓰지 않는다.

## 결과 (Consequences)

**좋아진 점**

- 패키지를 다시 만들어도 같은 API를 쓰게 된다. 빌드 결과를 예측할 수 있다.
- 메이저 버전 변경이 들어오려면 누군가 의도적으로 이 상한을 풀어야 한다. 변경이 기록에 남는다.

**치른 비용**

- 2.x에서 나오는 개선과 수정을 받지 못한다. 1.x 계열의 지원이 끝나면 다시 검토해야 하며, 그때는 새 ADR로 기록해야 한다.
- 결정의 근거가 한 줄로만 남아 있다. 나중에 이 상한을 풀지 검토하는 사람은 2.x의 변경 사항을 처음부터 직접 조사해야 한다.

**이 ADR에서 배울 점**

결정 자체는 합리적이지만 기록이 부실한 사례다. 결정을 내린 순간에는 이유가 너무 당연해 보여서 한 줄이면 충분하다고 느끼기 쉽다. 그러나 몇 달 뒤 그 한 줄로는 무엇을 확인했고 무엇이 걱정이었는지 복원할 수 없다. ADR을 결정 시점에 쓰는 이유가 여기에 있다.
