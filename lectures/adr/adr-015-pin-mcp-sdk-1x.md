# ADR-015. MCP Python SDK 의존성을 1.x 대역에 안정적으로 고정합니다

## 상태 (Status)

채택됨 (Accepted) · 2026-08-26

관련 결정: [ADR-004](adr-004-portable-python-bundle.md), [ADR-011](adr-011-namespace-argument.md), [ADR-021](adr-021-tool-time-budget.md)

## 맥락 (Context)

> [!NOTE]
> 본 의사결정에 대해 과거에 남겨진 공식 기록은 커밋 메시지 한 줄("mcp 2버전(stateless) 미사용으로 수정")과 의존성 목록 파일의 버전 제약 변경뿐이었습니다. 아래 기술된 기술적 맥락 중 일부는 당시의 코드베이스 구조를 바탕으로 사후 역추론하여 복원한 것입니다.

서버 의존성 요구 목록(`requirements-server.txt`)은 초기 작성 당시 `mcp>=1.2.0`과 같이 최소 버전 하한선만 느슨하게 명시되어 있었습니다. 그러나 2026-08-26에 버전 상한선이 새롭게 추가되어 `mcp>=1.2.0,<2` 형태로 엄격히 고정되었습니다. 당시의 커밋 메시지 맥락으로 볼 때, 향후 릴리스될 2.x 계열 SDK가 완전 무상태(Stateless) 기반의 아키텍처를 기본 전제로 전환할 것이라는 판단이 작용했던 것으로 파악됩니다.

본 샌드박스 시스템이 공식 1.x 계열 SDK에 깊이 의존하고 있는 핵심 영역들은 다음과 같습니다.

- **서버 프로세스가 영속적인 상태(Stateful)를 가집니다.** 단일 장기 생명주기 stdio 파이프 연결 위에서, 세션 네임스페이스와 커널 객체의 매핑 테이블, 사전 기동된 예비 커널, 현재 진행 중인 백그라운드 패키지 설치 작업 목록을 메모리에 유지합니다. 본 시스템에서 "상태의 보존"은 부차적인 옵션이 아니라 시스템의 핵심 존재 이유입니다([ADR-002](adr-002-persistent-jupyter-kernel.md)).
- **1.x 계열의 고유 API 인터페이스를 직접 활용합니다.** FastMCP 고수준 프레임워크, 도구 스키마에서 자동으로 숨겨지는 컨텍스트 인자 주입, 비동기 실시간 진행률 알림, 저수준 서버 객체에 버전 메타데이터를 등록하는 방식 등이 이에 해당합니다. 향후 클라이언트가 제공할 대화 ID를 수신하기 위해 작성해 둔 예비 코드 역시 1.x 요청 컨텍스트 구조를 전제로 합니다([ADR-011](adr-011-namespace-argument.md)).
- **폐쇄망 오프라인 배포는 빌드 시점에 바이너리가 완전히 고정됩니다.** 외부 인터넷 빌드 PC에서 패키징된 버전이 폐쇄망으로 그대로 반입됩니다. 만약 버전 상한선이 열려 있다면, 향후 유지보수를 위해 패키지 번들을 다시 빌드할 때 아무도 검증하지 않은 급진적인 2.x 메이저 버전이 조용히 유입될 위험이 있습니다. 오프라인 휠을 다시 수집할 때도 동일한 위험이 존재합니다.

## 결정 (Decision)

서버의 MCP SDK 의존성을 `mcp>=1.2.0,<2`로 엄격히 상한 고정(Pinning)하기로 결정했습니다. 2.x 메이저 계열로의 섣부른 전환은 배제합니다.

## 결과 (Consequences)

**얻게 된 이점**

- 향후 오프라인 패키지 번들을 재빌드하거나 휠 아카이브를 다시 수집하더라도 언제나 100% 동일한 API 규격과 동작을 보장받을 수 있습니다. 빌드 및 배포 결과의 결정론적 예측 가능성을 확보했습니다.
- 향후 메이저 버전 업그레이드가 도입되려면 엔지니어가 의도적으로 이 상한선을 풀고 충분한 검증을 거쳐야만 합니다. 모든 중요한 아키텍처 변화가 Git 형상 기록에 투명하게 남게 됩니다.

**감수한 트레이드오프**

- 향후 2.x 계열에서 도입될 잠재적인 성능 최적화나 신규 프로토콜 기능 개선 사항들을 즉각 누리지 못합니다. 향후 1.x 계열의 공식 지원이 종료되는 시점에 마이그레이션 타당성을 다시 검토해야 하며, 그때는 새로운 ADR을 통해 의사결정을 공식화해야 합니다.
- 의사결정의 당시 근거가 Git 커밋 메시지 한 줄로만 간략하게 남아 있었습니다. 훗날 이 버전 상한을 해제할지 검토하는 후속 작업자는 2.x 계열의 세부 변경 내역과 브레이킹 체인지를 처음부터 직접 전수 조사해야 하는 연구 비용을 치러야 합니다.

**본 ADR이 주는 엔지니어링 교훈**

결정 자체는 매우 합리적이고 안전한 선택이었으나, 문서화 기록이 부실했던 전형적인 사례입니다. 결정을 내리던 당시에는 그 이유가 너무나 자명해 보여서 커밋 메시지 한 줄이면 충분하다고 느끼기 쉽습니다. 그러나 수개월이 흐른 뒤 그 한 줄의 텍스트만으로는 당시 무엇을 우려했고 어떤 기술적 한계를 직접 확인했었는지를 완벽히 복원할 수 없습니다. 이것이 바로 중요한 아키텍처 의사결정 시점에 즉시 ADR을 정식으로 작성해 두어야 하는 강력한 이유입니다.
