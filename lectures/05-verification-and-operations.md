# 5장. 검증과 운영

만든 것이 폐쇄망에서 실제로 돌아간다는 것을 어떻게 확신할 수 있을까? 그리고 돌아가기 시작한 뒤에 생기는 문제는 어떻게 알아보고 고칠까? 이 장은 그 두 질문을 다룬다.

## 5.1 검증의 네 층

이 프로젝트는 성격이 다른 검증을 네 층으로 나눠 쓴다.

| 층 | 무엇을 확인하나 | 언제 | 네트워크 |
|---|---|---|---|
| 스모크 테스트 | 커널 실행, 상태 유지, 예외 보고, 타임아웃 복구, 산출물 탐지, 판정 규칙, 경로 검증, 설치 실패 진단, 응답 시간 예산 | 코드를 바꿀 때마다 | 필요 없다 |
| 사전 점검 | 필수·권장 패키지가 있는지, 커널이 실제로 뜨는지, 패키지 인덱스가 어디이고 닿는지 | 빌드 직후, 반입 직후 | 필요 없다(인덱스 확인은 경고만) |
| 오프라인 기능 실측 | 약속한 기능을 대표하는 작업이 실제로 되는지 | 패키지를 새로 만들 때 | 끊은 상태에서 |
| 실제 런타임 확인 | 위 검증을 개발용 가상환경이 아닌 포터블 Python에서 다시 수행 | 배포 전 | |

오프라인 기능 실측에서 돌린 작업은 이런 것들이다. sympy로 x·sin(x)를 적분해 `-x·cos(x) + sin(x)`를 얻는다. pandas와 openpyxl로 엑셀 파일을 쓰고 다시 읽는다. matplotlib으로 차트를 저장한다. reportlab으로 PDF를 만든 뒤 pdfplumber와 PyMuPDF 두 라이브러리로 각각 다시 읽는다. python-docx로 워드 파일을 만든다. polars로 합계를 내고 duckdb로 SQL을 실행한다. 명세가 약속한 기능이 인터넷 없이 실제로 된다는 증거가 여기서 나온다.

마지막 층이 따로 있는 이유가 있다. 개발용 가상환경은 로직이 맞는지를 증명하고, 포터블 Python은 실제로 배포될 물건이 동작하는지를 증명한다. 둘은 다를 수 있다. 실제로 v0.4.1 이후 개발용 인터프리터에서는 numpy 2.4와의 바이너리 호환(ABI) 문제로 스모크 테스트 두 항목(pandas 사용, png 차트 생성)이 계속 실패했다. 커밋 기록에는 이 실패가 개발 환경의 문제이며 해당 변경과 무관하다는 설명과 함께, 포터블 Python에서 다시 확인해야 한다는 메모가 남아 있다. 개발 환경의 결과만 보면 멀쩡한 코드를 고치러 들어가거나, 반대로 개발 환경의 잡음 속에 진짜 문제를 묻어 버리기 쉽다.

## 5.2 스모크 테스트에서 배울 점

스모크 테스트는 버전을 거치며 14개(v0.1.0)에서 36개(v0.4.0), 65개(v0.5.0), 78개(v0.6.0), 86개(v0.7.0)로 늘었다. 늘어난 항목을 들여다보면 몇 가지 쓸 만한 기법이 보인다.

**MCP 없이 도는 테스트.** 커널과 산출물 탐지를 확인하는 기본 항목은 MCP SDK를 import하지 않는다. 도구 함수를 직접 부르는 항목은 SDK가 없으면 실패 대신 건너뛰기(SKIP)로 표시한다. 덕분에 최소한의 Python에서도 핵심 로직을 확인할 수 있다. 정적 뷰에서 본 "MCP를 모르는 부품이 많다"는 구조가 여기서 효과를 낸다.

**판정 매트릭스.** v0.5.0에서 판정 규칙을 바꿀 때, 먼저 "이 코드는 이 판정이 나와야 한다"는 표를 만들고 그 표를 그대로 테스트로 옮겼다. 백그라운드 스레드 예외, 하위 프로세스 비정상 종료, `sys.exit(0)`, 아무 출력 없는 셀 같은 경우가 모두 들어 있다. 규칙을 바꾸는 사람은 이 표를 먼저 고쳐야 하므로, 판정이 슬그머니 바뀌는 일을 막는다.

**네트워크 없이 네트워크 실패를 시험하기.** 설치 실패 진단을 시험하려면 "인덱스에 닿지 않는" 상황이 필요하다. 테스트는 RFC 2606이 절대 해석되지 않도록 예약해 둔 도메인 이름을 인덱스 주소로 준다. 어떤 네트워크에서 돌려도 항상 같은 방식으로 실패하므로 결과가 흔들리지 않는다.

**설치가 아니라 응답을 시험하기.** v0.7.0의 테스트는 pip을 실제로 돌리지 않는다. 대신 느린 설치를 흉내 내고, 도구가 막혀 있지 않고 `RUNNING`으로 답하는지, 작업이 뒤에서 계속 도는지, 다시 부르면 결과를 거둬 오는지, 거둔 뒤 등록부가 비는지, 바쁜 커널을 무한정 기다리지 않는지를 확인한다. 검증하려는 것이 설치 자체가 아니라 "시간 예산 안에 답하는가"이기 때문이다.

**비동기 테스트의 함정.** v0.7.0 작업 중에 기존 테스트 일부가 비동기 함수를 `await`하지 않고 있었다는 사실이 드러났다. 코루틴을 만들기만 하고 실행하지 않으면 테스트는 아무것도 확인하지 않은 채 통과한다. 비동기 코드를 시험할 때 흔히 저지르는 실수다.

## 5.3 알아 두면 좋은 측정값

포터블 WinPython에서 잰 값이다.

| 항목 | 시간 |
|---|---|
| 커널 부팅(예비 커널 준비 비용) | 약 2.5초 |
| 예비 커널을 가져간 새 네임스페이스의 첫 실행 | 약 0.06초 |
| 부팅 후 간단한 실행 한 번 | 약 0.07초 |
| 처음 `import pandas` | 약 1.1초 |
| 두 번째 `import pandas`(캐시) | 약 0.06초 |

배포 패키지 전체 크기는 약 3.47GB다.

## 5.4 자주 만나는 증상

운영하며 만났거나, 구조상 만나기 쉬운 증상을 원인과 함께 정리했다.

| 증상 | 원인 | 대처 |
|---|---|---|
| AnythingLLM에 "Context server request timeout"이 뜬다 | 서버가 60초 안에 답하지 못해 클라이언트가 요청을 취소했다 | v0.7.0 이상인지 확인한다. `SANDBOX_EXEC_TIMEOUT`이 `SANDBOX_TOOL_BUDGET` 이하이고, 둘 다 60초보다 작은지 확인한다 |
| 설치가 매번 실패하고 "이 PC에는 미러가 설정되지 않았다"고 나온다 | `SANDBOX_PIP_INDEX_URL`을 설정하지 않아 pip이 공개 PyPI로 가려 했다 | 설정에 미러 주소를 넣고 서버를 재시작한다 |
| 미러 주소를 넣었는데 "그런 패키지가 없다"고 나온다 | 미러가 평문 http인데 신뢰 호스트로 등록하지 않아 pip이 인덱스를 버렸다 | `SANDBOX_PIP_TRUSTED_HOST`에 미러 호스트 이름을 넣는다 |
| 대화 중에 불러 둔 변수가 갑자기 없다 | 네 가지 중 하나다. 모델이 네임스페이스 id를 빠뜨리거나 바꿨다. 30분 넘게 쉬어서 회수되었다. 네임스페이스가 8개를 넘어 밀려났다. 타임아웃 뒤 커널이 재시작되었다 | 응답 상단의 `active_namespace`가 이전과 같은지, 직전 응답에 재시작 안내가 있었는지 확인한다 |
| 코드가 만든 파일이 링크로 돌아오지 않는다 | 파일을 워크스페이스 밖(절대 경로)에 저장했다. 또는 v0.4.1 이전 버전에서 워크스페이스를 프로젝트 밖으로 옮겼다 | 파일 이름만 쓰도록 안내한다. 버전을 올린다 |
| 워크스페이스 안에 `workspace` 폴더가 또 생겼다 | 모델이 옛 규칙대로 `./workspace/`를 붙여 저장했다. 커널 시작 코드가 호환을 위해 이 하위 폴더를 만들어 둔다 | 산출물로는 정상적으로 잡히므로 급하지 않다. 규칙 4번대로 파일 이름만 쓰게 하면 사라진다 |
| `time.sleep(600)` 같은 코드 뒤에 변수가 모두 사라졌다 | Windows에서는 긴 블로킹 호출을 인터럽트로 깨우지 못해 커널을 재시작했다 | 정상 동작이다. 응답에 재시작 사실이 적혀 있다 |
| 첫 차트만 유난히 느리다 | matplotlib이 글꼴 캐시를 만드는 중이다 | 한 번만 일어난다 |
| `import pymupdf`가 실패한다 | import 이름이 `fitz`다 | `import fitz`를 쓴다 |
| 로그에 "running over TCP without encryption" 경고가 있다 | 커널과의 루프백 통신에 대한 경고다 | 무시한다 |
| 콘솔에서 한글이나 특수문자가 깨진다 | 한국어 Windows 콘솔의 코드 페이지(cp949) 문제다 | 파일과 도구 응답은 UTF-8로 정상이다. 콘솔에 출력해 눈으로 볼 때만 생긴다 |

## 5.5 알려진 한계

이 시스템이 하지 못하는 일을 정직하게 적어 둔다. 새로 합류한 사람이 "버그"로 오해하기 쉬운 것들이다.

- **격리는 관습 수준이다.** 모델이 쓴 코드는 사용자 권한으로 PC의 어떤 파일이든 읽고 쓸 수 있고, 사내망에 접속할 수도 있다.
- **모델이 삼킨 예외는 보이지 않는다.** `try`/`except`로 예외를 잡고 넘어가면 판정은 `RAN_UNVERIFIED`로 나온다. 검증식 인자가 들어오기 전까지는 메울 방법이 없다.
- **늦게 터진 백그라운드 예외는 한 칸 밀려 보고된다.** 사건 장부를 수거한 뒤에 스레드가 죽으면 다음 호출의 결과에 붙는다.
- **네임스페이스의 연속성은 모델에게 달렸다.** 모델이 id를 잃으면 데이터도 잃는다.
- **동시 실행 시 산출물이 잘못 귀속될 수 있다.** 두 대화가 정확히 같은 시각에 실행하면 서로의 파일이 산출물로 잡힐 수 있고, 같은 파일 이름이 겹칠 수 있다.
- **추가 설치로 기본 스택을 업그레이드할 수 없다.** venv의 경로가 검색 목록 뒤에 붙으므로, 포터블 Python에 이미 있는 패키지는 기본 버전이 계속 쓰인다.
- **자동 테스트가 닿지 않는 곳이 있다.** 실제 사내 미러에서의 다운로드, 네트워크를 물리적으로 끊은 상태의 시뮬레이션, 대용량 파일과 장시간 실행의 성능은 자동 테스트로 확인하지 않는다. 미러 다운로드는 배포할 때 사람이 한 번 직접 확인해야 한다.

## 5.6 유지보수 원칙

코드와 문서를 고칠 때 지켜 온 규칙이다.

**버전은 한곳에서 정한다.** 버전 번호의 원본은 설정에 있는 값 하나다. MCP 연결 시 서버가 알리는 버전, README의 버전 이력, 위키의 사실 파일은 스크립트 하나로 함께 갱신한다. 세 곳을 손으로 맞추다 보면 언젠가 어긋난다.

**원본을 먼저 고치고 배포본을 맞춘다.** 저장소에는 서버 코드가 두 벌 있다. 개발용 원본과 배포 패키지 폴더 안의 사본이다. 항상 원본을 먼저 고치고 사본에 복사한다. 이 이중 관리는 알려진 기술 부채이며, 사본을 빌드 단계에서 생성하도록 바꾸는 방안이 검토 과제로 남아 있다.

**무거운 파일은 커밋하지 않는다.** WinPython 폴더, 오프라인 휠, 압축 파일은 합쳐서 수 GB다. 커밋 전에 스테이징된 파일 목록을 확인한다.

**문서 여러 벌을 함께 고친다.** 사용자용 한국어 문서(README, 빌드 매뉴얼, 패키지 안내)와 개발 인계용 영어 위키가 따로 있다. 도구의 인터페이스나 기본값이 바뀌면 이들을 함께 갱신한다. 이번 교육자료를 만들다가도 그런 예를 하나 찾았다. v0.7.0에서 코드의 실행 제한 기본값은 45초로 바뀌었는데, 설정 예시, 수동 실행 스크립트, 사용자 문서, 위키의 예시에는 옛 값 60이 그대로 남아 있었다. 배포 사본까지 합쳐 파일 열 개였고, 2026-09-24에 모두 45로 맞췄다. 문서가 여러 벌이면 이런 일이 생긴다.

## 5.7 앞으로의 과제

| 과제 | 내용 |
|---|---|
| 검증식 인자 | 모델이 성공 조건을 식으로 보내면 서버가 평가해 "검증됨"을 준다([ADR-018](adr/adr-018-expect-verification.md)) |
| 도구 단위 회귀 테스트 | MCP 호출 경로 전체를 거치는 테스트를 스모크 테스트와 분리해 추가 |
| 소스 이중 관리 해소 | 배포본을 빌드 단계에서 생성하고 저장소에서는 제외 |
| 인터럽트 유예 시간 설정화 | 지금은 5초로 고정되어 있다. 재시작이 너무 잦다면 조정할 수 있게 |
| 구조화된 도구 출력 | 클라이언트가 지원하면 텍스트와 함께 기계가 읽을 필드도 제공 |
| 대화 id 자동 연결 | 클라이언트가 요청 메타데이터에 대화 id를 실어 보내기 시작하면 자동으로 쓰도록 이미 준비되어 있다. 클라이언트 쪽 변화를 지켜본다 |
