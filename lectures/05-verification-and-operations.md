# 5장. 검증과 운영

우리가 개발한 시스템이 인터넷이 완전히 차단된 사내 폐쇄망 환경에서 실제로 결함 없이 정상 동작한다는 것을 어떻게 사전에 확신할 수 있을까요? 그리고 실무 운영에 돌입한 이후 예기치 않은 문제가 발생했을 때, 그 원인을 어떻게 신속히 진단하고 해결할 수 있을까요? 이번 장에서는 이 두 가지 핵심 엔지니어링 질문에 대한 실전 해답을 다룹니다.

## 5.1 다층적 검증 전략 (검증의 4개 층위)

본 프로젝트는 성격과 목적이 서로 다른 4가지 층위의 검증 파이프라인을 구축하여 품질을 보증합니다.

| 검증 층위 | 무엇을 집중적으로 검증하는가 | 수행 시점 | 외부 네트워크 필요 여부 |
|---|---|---|---|
| 스모크 테스트 (Smoke Test) | 커널 코드 실행, 세션 상태 보존, 예외 보고, 타임아웃 복구, 산출물 자동 탐지, 실행 판정 룰셋, 경로 보안 검증, 패키지 설치 실패 진단, 응답 시간 예산 준수 | 서버 소스코드를 수정할 때마다 즉시 실행 | 전혀 필요 없음 (완전 오프라인) |
| 오프라인 사전 점검 (Pre-flight Check) | 필수 및 권장 패키지의 물리적 존재 여부, Jupyter 커널 프로세스 정상 부팅 가능 여부, 패키지 미러 인덱스 도달성 | 빌드 직후 및 폐쇄망 반입 직후 | 전혀 필요 없음 (인덱스 도달 실패 시 경고만 출력) |
| 오프라인 기능 실측 검증 | 명세서에서 약속한 대표 데이터 사이언스 작업들이 폐쇄망에서 실제로 완수되는지 확인 | 배포 패키지를 신규 제작할 때마다 수행 | 네트워크를 완전히 물리 차단한 상태에서 수행 |
| 실제 배포 런타임 검증 | 위 검증 절차들을 개발용 가상환경이 아닌 실제 최종 배포용 포터블 WinPython 환경에서 전면 재수행 | 사내망 최종 배포 직전 | 배포 대상 환경과 동일한 조건에서 수행 |

오프라인 기능 실측 검증에서 수행하는 대표적인 작업 시나리오는 다음과 같습니다. sympy를 사용하여 복잡한 함수 $x \cdot \sin(x)$를 부정적분하여 $-x \cdot \cos(x) + \sin(x)$라는 정확한 기호수학 해를 도출합니다. pandas와 openpyxl을 연동하여 대용량 엑셀 파일을 디스크에 쓰고 다시 읽어 들입니다. matplotlib으로 다채로운 차트를 생성하여 이미지로 저장합니다. reportlab으로 커스텀 PDF 문서를 직접 생성한 뒤, pdfplumber와 PyMuPDF 두 가지 상이한 라이브러리로 각각 파싱하여 표 데이터를 역추출합니다. python-docx로 워드 문서를 자동 생성하고, polars로 고속 집계를 수행하며, duckdb로 인메모리 SQL 쿼리를 실행합니다. 요구 명세서가 약속한 모든 고급 데이터 처리 기능들이 인터넷 연결 없이 100% 자급자족으로 동작한다는 물리적 증거가 바로 이 실측 단계에서 도출됩니다.

여기서 네 번째 층위인 '실제 배포 런타임 검증'이 반드시 별도로 존재해야 하는 중요한 이유가 있습니다. 개발용 머신의 가상환경(venv)은 시스템의 비즈니스 로직이 올바른지를 증명할 수 있을 뿐, 실제 사용자의 PC에 반입될 최종 포터블 바이너리가 온전히 동작하는지까지 보증하지는 못합니다. 두 환경의 바이너리 상태는 얼마든지 달라질 수 있기 때문입니다. 실제로 v0.4.1 개발 당시 개발용 인터프리터에서는 최신 numpy 2.4와의 C 확장 모듈 바이너리 호환성(ABI) 문제로 인해 pandas 사용 및 PNG 차트 생성과 관련된 스모크 테스트 2개 항목이 지속적으로 실패하는 현상이 발생했습니다. 당시 커밋 로그에는 이 실패가 개발 PC 로컬 환경의 특수한 버전 불일치 문제이며 소스코드 변경 자체와는 무관하다는 사실을 밝히고, 배포 대상인 포터블 Python에서 반드시 재검증하여 합격 여부를 판정해야 한다는 주의 메모가 기록되어 있습니다. 개발 환경의 결과만을 맹신할 경우 아무런 하자가 없는 완벽한 프로덕션 코드를 헛되이 뜯어고치거나, 반대로 개발 환경의 잡음에 가려져 실제 배포 번들의 치명적인 결함을 놓칠 위험이 있습니다.

## 5.2 스모크 테스트 스위트에서 배울 수 있는 실전 테스팅 기법

본 시스템의 스모크 테스트 스위트는 버전 판올림을 거치며 14개(v0.1.0)에서 36개(v0.4.0), 65개(v0.5.0), 78개(v0.6.0), 그리고 86개(v0.7.0)로 꾸준히 확장되었습니다. 이 테스트 케이스들을 면밀히 분석해 보면 실무에서 매우 유용하게 활용할 수 있는 몇 가지 뛰어난 엔지니어링 테스팅 기법들을 발견할 수 있습니다.

**MCP 프레임워크에 독립적인 초고속 테스트.** Jupyter 커널 제어와 산출물 자동 탐지 로직을 검증하는 핵심 테스트 항목들은 `mcp` SDK 패키지를 일절 임포트하지 않습니다. FastMCP 도구 데코레이터가 적용된 고수준 함수를 직접 호출하는 테스트 항목들의 경우, 실행 환경에 MCP SDK가 설치되어 있지 않다면 실패(FAIL)로 판정하는 대신 안전한 건너뛰기(SKIP)로 처리합니다. 덕분에 개발자는 무거운 프로토콜 환경을 구축할 필요 없이 최소한의 표준 Python 인터프리터만으로도 백엔드 핵심 코어 로직의 무결성을 수 초 만에 검증할 수 있습니다. 앞서 정적 뷰에서 살펴본 "MCP를 모르는 독립 컴포넌트" 아키텍처가 테스팅 생산성에서도 커다란 빛을 발하는 순간입니다.

**데이터 주도형 판정 매트릭스 (Verdict Matrix).** v0.5.0에서 실행 판정 체계를 전면 개편할 때, 개발팀은 먼저 "어떤 런타임 현상이 발생했을 때 정확히 어떤 판정 등급이 부여되어야 하는가"를 완벽히 정의한 거대한 매트릭스 표를 작성하고, 그 표의 모든 셀을 1:1 단위 테스트 케이스로 그대로 구현했습니다. 백그라운드 스레드 크래시, 하위 프로세스의 비정상 종료, 정상적인 `sys.exit(0)`, 아무런 출력도 없는 침묵 셀 등 실무에서 발생할 수 있는 모든 엣지 케이스가 망라되어 있습니다. 향후 판정 룰셋을 수정하려는 작업자는 반드시 이 테스트 매트릭스를 먼저 검토하고 수정해야 하므로, 시스템 판정 로직이 의도치 않게 은밀히 변질되는 퇴행(Regression)을 완벽하게 방지합니다.

**외부 네트워크 없이 오프라인 실패 상황을 결정론적으로 시험하기.** 패키지 설치 실패 진단 로직을 테스트하려면 "외부 패키지 인덱스 서버에 네트워크로 도달할 수 없는 상황"을 인위적으로 재현해야 합니다. 본 테스트는 RFC 2606 표준에 의해 전 세계 인터넷에서 절대 네임 서버가 해석되지 않도록 영구 예약된 특수 도메인 명칭(예: `.invalid`, `.test`)을 모의 인덱스 주소로 주입합니다. 이를 통해 인터넷이 켜져 있는 개발 PC든, 완전히 차단된 폐쇄망 PC든 관계없이 언제나 100% 동일한 방식으로 신속하고 일관되게 네트워크 단절 실패를 유도할 수 있으므로 테스트 결과가 환경에 따라 흔들리지 않습니다.

**느린 실제 설치 대신 시간 예산 준수 여부를 집중 시험하기.** v0.7.0의 동시성 테스트는 수 분이 걸리는 실제 pip 다운로드 명령을 무의미하게 실행하지 않습니다. 대신 백그라운드 스레드에서 정밀한 지연(Delay)을 발생시켜 오래 걸리는 설치 상황을 가상으로 시뮬레이션합니다. 그 상태에서 도구 인터페이스가 메인 루프를 블로킹하지 않고 45초 이내에 `RUNNING` 상태를 정상 반환하는지, 백그라운드 작업이 고아(Orphan)가 되지 않고 끝까지 유지되는지, 동일한 인자로 재호출했을 때 결과를 성공적으로 수거해 오는지, 결과를 수거한 직후 레지스트리가 깨끗이 비워지는지, 그리고 연산 중인 다른 커널을 무한정 대기하지 않는지를 정밀하게 검증합니다. 이 테스트의 목적은 pip 자체의 동작 검증이 아니라, "시스템이 클라이언트 타임아웃 예산 내에서 우아하게 응답하는가"를 검증하는 것이기 때문입니다.

**비동기 테스트 작성 시의 치명적 함정 예방.** v0.7.0 리팩토링 과정에서 기존 비동기 테스트 케이스 중 일부가 비동기 코루틴 함수를 `await` 키워드 없이 단순히 호출만 하고 있었다는 치명적인 실수가 발견되었습니다. Python 비동기 환경에서 코루틴 객체를 생성만 하고 이벤트 루프에서 `await`로 실행하지 않으면, 테스트 프레임워크는 내부의 단언문(assert)을 단 하나도 검증하지 못한 채 테스트가 성공한 것으로 잘못 판정하고 통과해 버립니다. 비동기 코드를 시험할 때 누구나 저지르기 쉬운 실수이므로 각별한 주의가 필요합니다.

## 5.3 운영자가 숙지해야 할 핵심 성능 측정값

본 수치는 실제 타깃 환경인 포터블 WinPython 3.13 런타임에서 직접 측정한 실측 기준값입니다.

| 성능 측정 항목 | 실측 소요 시간 |
|---|---|
| 신규 Jupyter 커널 프로세스 초기 부팅 시간 (예비 커널 준비 비용) | 약 2.5초 |
| 사전 기동된 예비 커널을 즉시 인계받은 신규 네임스페이스의 첫 실행 착수 지연 | 약 0.06초 |
| 커널 기동 완료 후 단순 수치 계산 코드 1회 실행 지연 | 약 0.07초 |
| 커널 세션에서 최초 1회 `import pandas` 실행 시간 | 약 1.1초 |
| 동일 커널 세션에서 2회차 이후 `import pandas` 실행 시간 (메모리 캐시 히트) | 약 0.06초 |

최종 배포 아카이브 전체의 디스크 압축 해제 용량은 약 **3.47GB**입니다.

## 5.4 현업 운영 시 자주 발생하는 장애 증상과 표준 대처법

실제 사내망 현업 운영 과정에서 보고되었거나 시스템 구조상 마주치기 쉬운 전형적인 장애 증상들을 원인 및 해결책과 함께 정리해 드립니다.

| 장애 증상 | 근본 발생 원인 | 표준 권장 대처 방안 |
|---|---|---|
| AnythingLLM 화면에 "Context server request timeout" 에러가 출력됩니다. | MCP 서버가 60초 이내에 최종 응답을 돌려주지 못하여 AnythingLLM 클라이언트가 요청을 강제 종료했습니다. | 서버 버전이 v0.7.0 이상인지 확인하십시오. 환경 변수 `SANDBOX_EXEC_TIMEOUT`이 `SANDBOX_TOOL_BUDGET` 이하로 설정되어 있는지, 그리고 두 값 모두 반드시 60초 미만(권장 45초)으로 지정되어 있는지 확인하시기 바랍니다. |
| 패키지 설치가 항상 실패하며 "이 PC에는 미러가 설정되지 않았다"는 안내가 반환됩니다. | 환경 변수 `SANDBOX_PIP_INDEX_URL`이 설정되지 않아 pip이 사내 폐쇄망에서 접근 불가능한 공용 인터넷 PyPI(`pypi.org`)로 접속을 시도했습니다. | AnythingLLM 설정 파일의 MCP 서버 `env` 블록에 사내 미러 서버 주소를 올바르게 입력한 후 데스크톱 앱을 재시작하십시오. |
| 미러 주소를 바르게 등록했음에도 "일치하는 배포판을 찾을 수 없다"며 설치가 거부됩니다. | 사내 미러 서버가 비보안 평문 HTTP 프로토콜을 사용하는데, pip의 신뢰 호스트로 등록되지 않아 pip이 해당 인덱스를 보안상 조용히 폐기했습니다. | 환경 변수 `SANDBOX_PIP_TRUSTED_HOST`에 사내 미러 서버의 도메인 호스트명을 명시적으로 등록해 주십시오. |
| 이전 대화에서 메모리에 불러 두었던 대용량 변수나 데이터프레임이 갑자기 사라졌습니다 (`NameError`). | 다음 4가지 원인 중 하나입니다. ① 모델이 추론 실수로 세션 ID를 누락했거나 임의로 변경했습니다. ② 30분간 대화가 없어 커널이 유휴 회수되었습니다. ③ 전체 네임스페이스가 8개를 초과하여 LRU 정책으로 밀려났습니다. ④ 타임아웃으로 인해 커널이 강제 재시작되었습니다. | 도구 반환 응답 상단의 `active_namespace`가 이전과 동일한지 확인하시고, 직전 응답 텍스트에 "커널 상태가 초기화되었음" 안내가 포함되어 있었는지 확인하십시오. |

## 5.5 시스템의 알려진 기술적 한계 (Known Limitations)

새롭게 프로젝트를 인수인계받은 개발자나 운영자가 "버그"로 오해하기 쉬운 본 시스템의 구조적 한계점들을 투명하고 정직하게 공유합니다.

- **격리 수준이 OS 완전 격리가 아닌 '관습적 샌드박스' 수준입니다.** 모델이 생성한 임의의 코드는 호스트 사용자 계정의 일반 권한으로 구동되므로 로컬 PC의 임의 파일을 읽고 쓰거나 사내망으로 네트워크 소켓을 생성할 수 있는 물리적 권한을 여전히 가집니다.
- **사용자 코드가 예외를 자체적으로 은폐(try-except-pass)한 경우 시스템이 이를 감지할 수 없습니다.** 인터프리터 수준에서 예외가 밖으로 던져지지 않는 한 판정 엔진은 이를 `RAN_UNVERIFIED`로 처리할 수밖에 없습니다. 검증식(`expect`) 인자 기능이 정식 도입되기 전까지는 피할 수 없는 한계입니다.
- **지연 발생한 백그라운드 스레드의 예외는 한 틱 늦게 보고됩니다.** 메인 코드와 내부 프로브 셀의 실행이 완전히 끝난 직후 비동기 워커 스레드가 뒤늦게 사망할 경우, 해당 오류는 바로 다음 도구 호출의 사건 장부로 이월되어 수거됩니다.
- **세션 상태의 영속성은 모델의 세션 ID 기억력에 절대적으로 의존합니다.** 소형 모델이 컨텍스트 축소 등으로 인해 세션 ID를 분실하고 새 네임스페이스를 호출하면 기존 메모리 상태는 복구할 수 없습니다.
- **동일한 밀리초 시점에 다중 세션 코드가 동시 실행될 경우 산출물이 교차 오귀속될 수 있습니다.** 산출물 탐지기가 공유 워크스페이스 전체를 대상으로 스냅샷 차이를 대조하므로 발생하는 이론적 한계입니다.
- **사내 미러를 통한 패키지 추가 설치로 기본 내장 스택의 버전을 상향 오버라이드할 수 없습니다.** 사이드 venv의 설치 경로가 커널의 모듈 검색 경로(`sys.path`) 가장 뒤편에 추가되므로, 베이스 포터블 Python에 이미 존재하는 패키지는 언제나 원본 버전이 우선적으로 로드됩니다.
- **일부 비기능적 시나리오는 단위 자동화 테스트 스위트의 범위를 벗어납니다.** 실제 사내 미러 서버로부터의 대용량 패키지 다운로드, 물리 망분리 환경의 완벽한 재현, 수 기가바이트의 초대용량 파일 처리 벤치마크 등은 단위 테스트로 자동화하기 어려우므로 현장 배포 시 엔지니어가 수동으로 최종 실측 검증을 수행해야 합니다.

## 5.6 장기 유지보수 및 형상 관리 원칙

코드와 문서를 지속적으로 개선하고 관리할 때 반드시 준수해야 할 핵심 엔지니어링 원칙입니다.

**버전 정보의 단일 진실 공급원(SSOT) 유지.** 시스템 버전 번호의 원천은 환경 설정 모듈에 정의된 단 하나의 상수입니다. MCP 연결 시 클라이언트에 전달되는 버전(`serverInfo`), 메인 README의 변경 이력 표, 그리고 내부 위키의 아키텍처 명세서는 자동화 스크립트를 통해 일괄 갱신되어야 합니다. 수동으로 여러 문서를 개별 수정할 경우 반드시 버전 불일치가 발생합니다.

**개발용 소스 원본을 항상 먼저 수정하고 배포 패키지 사본에 동기화.** 저장소 구조상 개발용 원본 소스 디렉터리와 오프라인 배포 번들 디렉터리 내부에 서버 코드가 이중으로 존재합니다. 항상 루트의 원본 코드를 먼저 수정하고 검증을 완료한 뒤 배포 번들 폴더로 복사해야 합니다. (이 소스코드 이중 관리는 현재 인지하고 있는 기술 부채이며, 향후 CI 빌드 파이프라인에서 배포 번들을 동적으로 자동 생성하도록 개선할 예정입니다.)

**대용량 바이너리 아티팩트의 Git 커밋 엄격 금지.** 수 기가바이트에 달하는 WinPython 포터블 디렉터리, 오프라인 휠 아카이브, ZIP 압축 파일 등은 Git 버전 관리 대상에서 철저히 제외되어야 합니다. 커밋을 생성하기 전에 반드시 `git status`로 스테이징된 파일 목록을 재확인하시기 바랍니다.

**다국어 및 다중 문서의 동시 동기화.** 사용자용 한국어 안내 문서(README, 빌드 매뉴얼, 빠른 시작 가이드)와 개발자 인계용 영문 아키텍처 위키가 독립적으로 유지되고 있습니다. 도구의 시그니처나 환경 변수 기본값이 변경될 경우 모든 관련 문서를 빠짐없이 함께 수정해야 합니다. 실제로 본 교육자료를 작성하는 과정에서도, v0.7.0에서 실행 타임아웃 기본값이 45초로 변경되었음에도 불구하고 예제 JSON 설정과 수동 스크립트 등 총 10개 파일에 과거의 기본값인 60초가 그대로 방치되어 있던 오류를 발견하여 2026-09-24에 전면 일괄 수정한 바 있습니다.

1. 5.1절에서 소개한 4단계 검증 층위 중 자원이나 일정의 극심한 제약으로 인해 단 하나의 검증 층위만을 선택해야 한다면 무엇을 남기시겠습니까? 그 기술적 판단의 근거는 무엇입니까?
