# 2장. 기술 스택

이 장에서는 프로젝트를 이루는 기술을 계층별로 훑는다. 각 기술의 일반적인 소개보다는 "이 시스템에서 왜 그 기술이었는가"에 무게를 둔다.

## 2.1 한눈에 보기

| 계층 | 기술 | 이 시스템에서 맡은 일 |
|---|---|---|
| LLM 앱 | AnythingLLM | 사내 LLM과 대화하고, 에이전트 모드에서 MCP 도구를 호출한다 |
| 도구 프로토콜 | MCP (JSON-RPC 2.0, stdio 전송) | LLM 앱과 샌드박스 사이의 약속 |
| 서버 프레임워크 | MCP 공식 Python SDK의 FastMCP (1.x) | Python 함수를 MCP 도구로 노출한다 |
| 실행 엔진 | Jupyter 커널 (jupyter_client, ipykernel, IPython) | 코드를 실행하고 변수를 기억한다 |
| 프로세스 간 통신 | ZeroMQ, 127.0.0.1 루프백 | 서버와 커널 사이에서 메시지를 나른다 |

| 패키지 공급 | 오프라인 휠, 사내 PyPI 미러, venv | 반입 시점의 설치, 런타임 추가 설치 |
| 동시성 | threading, asyncio | 커널 직렬화, 백그라운드 설치, 커널 풀 관리 |

## 2.2 MCP (Model Context Protocol)

MCP는 LLM 애플리케이션이 외부 도구나 데이터에 접근하는 방식을 표준화한 프로토콜이다. LLM 앱이 클라이언트, 기능을 제공하는 쪽이 서버가 된다. 서버는 도구(tools), 리소스(resources), 프롬프트(prompts)를 제공할 수 있는데 이 프로젝트는 도구만 쓴다.

메시지 형식은 JSON-RPC 2.0이다. 연결이 맺어지면 클라이언트와 서버가 `initialize` 요청으로 서로의 정보를 주고받는다. 이때 서버는 자기 이름과 버전을 알리는데, 이 프로젝트는 여기에 v0.7.0 같은 버전 번호를 싣는다. 이어서 클라이언트는 `tools/list`로 도구 목록을 받아 간다. 목록의 각 도구에는 이름, 설명문(description), 입력 스키마(JSON Schema)가 들어 있다. 모델이 도구를 쓰기로 하면 클라이언트가 `tools/call`로 도구 이름과 인자를 보내고, 서버는 결과를 콘텐츠 목록(텍스트, 이미지 등)으로 돌려준다.

전송 방식은 크게 둘이다. 클라이언트가 서버를 자식 프로세스로 띄우고 표준 입출력으로 메시지를 주고받는 stdio 방식, 그리고 네트워크로 연결하는 HTTP 방식이다. 이 프로젝트는 stdio를 쓴다. AnythingLLM이 설정 파일에 적힌 명령으로 Python 프로세스를 띄우면, 그 프로세스의 stdin과 stdout이 곧 통신 채널이 된다. 포트를 열 필요도, 방화벽을 건드릴 필요도 없다.

이 프로젝트를 이해하려면 MCP의 성질 세 가지를 알아 둬야 한다.

**도구 설명문은 모델이 읽는 프롬프트다.** 클라이언트는 받아 온 도구 목록을 LLM의 컨텍스트에 넣는다. 모델은 설명문을 읽고 언제, 어떻게 그 도구를 쓸지 판단한다. 설명문에 무엇을 쓰느냐가 곧 모델의 행동을 바꾼다는 뜻이다. 이 프로젝트가 사용 규칙을 설명문에 심은 이유가 여기 있다([ADR-007](adr/adr-007-rules-in-tool-descriptions.md)).

**클라이언트는 무한정 기다리지 않는다.** MCP 클라이언트 SDK는 요청마다 제한시간을 두며 기본값은 60초다. 서버가 그 안에 답하지 못하면 클라이언트가 요청을 취소하고, AnythingLLM은 "Context server request timeout"이라는 메시지를 띄운다. 서버 쪽은 아무 문제 없이 일하고 있어도 사용자 눈에는 고장으로 보인다([ADR-021](adr/adr-021-tool-time-budget.md)).

**stdio 연결은 대화를 구분하지 않는다.** 서버 프로세스 하나에 연결이 하나 있을 뿐이다. 지금 들어온 호출이 어느 대화에서 왔는지 알려 주는 표준 필드는 이 프로젝트를 만들던 시점에 없었다. 요청마다 붙일 수 있는 메타데이터 자리(`_meta`)는 있지만, AnythingLLM은 거기에 대화 id를 넣지 않는다. 이 사실이 네임스페이스 설계로 이어진다([ADR-011](adr/adr-011-namespace-argument.md)).

## 2.3 FastMCP

FastMCP는 MCP 공식 Python SDK에 들어 있는 고수준 API다. Python 함수에 데코레이터를 붙이면 함수 이름이 도구 이름이 되고, 타입 힌트로부터 입력 스키마가 만들어진다. 설명문은 데코레이터 인자로 따로 줄 수 있다.

편리한 기능이 하나 있다. 함수 인자 중에 SDK의 컨텍스트 객체 타입이 있으면, FastMCP가 그 인자를 스키마에서 숨기고 호출할 때 자동으로 채워 준다. 모델은 그런 인자가 있는 줄 모르고, 서버는 그 객체를 통해 요청 메타데이터를 읽거나 진행 상황 알림을 보낼 수 있다. 이 프로젝트는 이 통로를 두 곳에 쓴다. 언젠가 클라이언트가 보내 줄 대화 id를 읽는 자리, 그리고 패키지 설치 중에 보내는 진행 알림이다.

도구 함수는 동기 함수로도, 비동기 함수로도 만들 수 있다. 오래 걸리는 설치 도구는 비동기로 만들고, 무거운 작업은 별도 스레드로 넘겨 이벤트 루프를 붙잡지 않게 했다.

SDK 버전은 1.x 대로 묶어 두었다. 2.x를 쓰지 않기로 한 결정은 [ADR-015](adr/adr-015-pin-mcp-sdk-1x.md)에 있다.

## 2.4 AnythingLLM

AnythingLLM은 여러 LLM 백엔드에 붙어 채팅, 문서 검색, 에이전트 기능을 제공하는 앱이다. 이 환경에서는 사용자 PC에 데스크톱 판을 설치해 사내 LLM 서버에 OpenAI 호환 API로 연결해 두었다.

MCP 서버는 JSON 설정 파일에 등록한다. 서버마다 실행할 명령(`command`), 인자(`args`), 환경 변수(`env`)를 적는다. AnythingLLM은 이 정보로 서버 프로세스를 띄우고, 에이전트 모드에서 모델이 그 도구를 부를 수 있게 한다.

한 가지 꼭 알아 둘 점은 AnythingLLM이 MCP 서버를 인스턴스 단위로 하나만 띄운다는 것이다. 사용자가 대화 창을 다섯 개 열어도 서버 프로세스는 하나이고, 다섯 대화의 도구 호출이 모두 그 프로세스로 들어온다.

## 2.5 Jupyter 커널과 메시징 프로토콜

상태를 유지하는 실행기를 직접 만들려고 하면 할 일이 생각보다 많다. 코드를 실행할 별도 프로세스를 띄우고, 코드를 보내고, 출력을 흘려받고, 예외를 잡고, 무한 루프를 끊고, 죽으면 다시 살려야 한다. Jupyter 생태계는 이 문제를 오랫동안 풀어 왔다. 노트북 화면 뒤에서 실제로 코드를 실행하는 것이 "커널"이라는 별도 프로세스다.

이 프로젝트는 노트북 없이 커널만 가져다 쓴다.

- **ipykernel**: Python 커널 구현체. 안에서 IPython이 코드를 실행한다.
- **jupyter_client**: 커널을 띄우고 대화하는 라이브러리. 커널 프로세스의 수명을 다루는 관리자(KernelManager)와, 메시지를 주고받는 클라이언트(KernelClient)로 나뉜다.

서버와 커널은 ZeroMQ 소켓 여러 개로 통신한다. 용도에 따라 채널이 나뉘는데 이 프로젝트에서 중요한 것은 두 개다.

| 채널 | 방향 | 용도 |
|---|---|---|
| shell | 요청과 응답 | 코드 실행 요청(`execute_request`)을 보내고 실행 결과 응답을 받는다 |
| iopub | 커널이 모두에게 방송 | 실행 중에 생기는 모든 일. 표준 출력(`stream`), 마지막 식의 값(`execute_result`), 예외(`error`), 상태 변화(`status`) |

이 밖에 인터럽트와 종료에 쓰는 control, 입력을 요청하는 stdin, 생존을 확인하는 heartbeat 채널이 있다.

코드 한 번을 실행하는 흐름은 이렇다. 클라이언트가 shell 채널로 `execute_request`를 보내면 요청마다 고유한 `msg_id`가 붙는다. 커널은 iopub 채널로 먼저 `status: busy`를 알리고, 코드가 출력하는 대로 `stream` 메시지를 흘려보내고, 예외가 나면 `error` 메시지를 보낸 뒤, 마지막으로 `status: idle`을 알린다. iopub의 모든 메시지에는 어느 요청 때문에 생긴 것인지를 가리키는 `parent_header.msg_id`가 붙어 있다.

덕분에 실행기가 할 일은 단순해진다. 요청을 보내고, iopub에서 내 `msg_id`에 딸린 메시지만 골라 모으다가, `idle`이 오면 끝났다고 본다. 요청을 보내기 전에 앞선 요청이 남긴 메시지를 비워 두는 것도 잊으면 안 된다. 이 흐름은 [동적 뷰](03-architecture/02-dynamic-view.md)에서 그림으로 다시 본다.

ZeroMQ 연결은 127.0.0.1 루프백 주소를 쓴다. 루프백은 네트워크 어댑터가 없어도 동작하므로 폐쇄망과 부딪히지 않는다. 커널이 뜰 때 "암호화 없이 TCP로 동작한다"는 경고가 로그에 찍히는데, PC 안쪽 통신에 대한 경고라서 무시해도 된다.

커널 관리자는 커널을 인터럽트하거나(실행 중인 코드에 KeyboardInterrupt를 일으킨다) 재시작하는(프로세스를 새로 띄워 메모리를 비운다) 기능도 준다. 둘 다 타임아웃 처리에 쓰인다.

## 2.6 IPython에서 알아 둘 동작

커널 안에서 코드를 실행하는 것은 IPython이다. 평범하게 `python script.py`로 실행할 때와 다른 점이 몇 가지 있다.

- 사용자 코드가 실행되는 전역 공간의 `__name__`이 이미 `"__main__"`이다. 그래서 스크립트 파일의 소스를 이 공간에서 그대로 실행하면 `if __name__ == "__main__":` 블록도 돈다([ADR-010](adr/adr-010-run-script-file.md)).
- 셀의 마지막 줄이 식이면 그 값의 표현(`repr`)이 `execute_result`로 나온다. `print`하지 않아도 값이 보이는 이유다.
- 코드가 `sys.exit()`를 부르면 IPython은 프로세스를 끝내지 않고 `SystemExit`를 오류로 보고한다. 종료 코드 0으로 정상 종료한 스크립트도 "에러"로 보인다는 뜻이다. v0.5.0에서 이 문제를 바로잡았다([ADR-017](adr/adr-017-execution-verdict.md)).

## 2.7 포터블 Python: WinPython

폐쇄망 PC에 Python과 수십 개 라이브러리를 들여놓는 방법은 여러 가지다. 빌드 매뉴얼에서 검토한 선택지를 비교하면 다음과 같다.

| 방식 | 장점 | 단점 |
|---|---|---|
| WinPython | 압축만 풀면 어디서든 실행된다. pip이 들어 있다 | 크다 |
| python.org embeddable 패키지 | 가장 작다 | pip이 없고 `site`가 꺼져 있어 손이 많이 간다 |
| conda-pack | conda 환경을 옮길 수 있게 묶어 준다 | conda에 익숙해야 하고, 풀고 나서 경로 보정 단계가 필요하다 |
| 일반 venv 복사 | 익숙하다 | 절대 경로에 묶여 있어서 다른 위치로 옮기면 깨진다 |

프로젝트는 WinPython 3.13(Python 3.13.13)을 택했다. 데이터 스택과 서버 의존성을 모두 설치한 뒤의 크기는 약 3.47GB다. 명세에 적힌 "4GB 포터블 Python"이 바로 이것이다([ADR-004](adr/adr-004-portable-python-bundle.md)).

포터블 런타임에서 가장 조심할 것은 플랫폼 일치다. numpy, scipy, PyMuPDF, pyzmq 같은 패키지는 운영체제, CPU 아키텍처, Python 마이너 버전마다 따로 컴파일된 바이너리(휠)를 쓴다. 빌드 PC가 대상 PC와 같은 Windows 64비트(win_amd64)여야 하고, Python 마이너 버전도 같아야 한다.

## 2.8 데이터 스택

커널용 Python에 미리 넣어 둔 라이브러리를 쓰임새별로 묶으면 다음과 같다.

| 쓰임새 | 라이브러리 |
|---|---|
| 수치·기호 계산 | numpy, scipy, sympy |
| 표 데이터 | pandas, polars, duckdb, pyarrow |
| 스프레드시트 | openpyxl(xlsx 읽기·쓰기), xlsxwriter(xlsx 쓰기), xlrd(구형 xls) |
| PDF | pdfplumber(표 추출에 강함), pypdf, PyMuPDF |
| 워드·파워포인트 | python-docx, python-pptx |
| XML·HTML·마크다운 | lxml, xmltodict, beautifulsoup4, markdown |
| 보고서 생성 | reportlab(PDF 생성), jinja2(템플릿) |
| 시각화 | matplotlib, seaborn, plotly |
| 기타 | Pillow(이미지), rapidfuzz(유사 문자열 매칭), python-dateutil |

이 가운데 pandas, numpy, scipy, sympy, matplotlib, openpyxl, lxml, beautifulsoup4 여덟 개는 "필수"로 분류된다. 하나라도 빠지면 사전 점검이 실패로 끝난다. 나머지는 "권장"이라 빠져도 경고만 한다.

함정도 몇 가지 있다. PyMuPDF는 패키지 이름과 import 이름이 달라서 `import fitz`로 불러온다. beautifulsoup4는 `bs4`, python-docx는 `docx`, python-pptx는 `pptx`, Pillow는 `PIL`이다. "설치되어 있는가"를 확인할 때 배포판 이름으로 볼지 import 이름으로 볼지 헷갈리기 쉬운 이유다.

matplotlib은 기본 설정대로면 창을 띄우려 한다. 커널은 화면이 없는 프로세스이므로 커널이 시작될 때 이미지 파일만 만드는 `Agg` 백엔드로 바꿔 둔다. 첫 차트를 그릴 때 글꼴 캐시를 만드느라 한 번 느린데, PC 안에서만 일어나는 일이라 네트워크와는 상관없다.

## 2.9 오프라인 휠

서버 자체가 쓰는 의존성은 mcp, jupyter_client, ipykernel 세 개다(딸려 오는 하위 의존성까지 합치면 수십 개가 된다). 포터블 Python에 이미 들어 있으면 따로 할 일이 없다. 그런데 대상 PC에 쓸 만한 Python이 이미 있어서 서버 의존성만 추가하고 싶을 때가 있다. 이런 경우를 위해 인터넷이 되는 PC에서 휠 파일을 미리 받아 두는 방법도 함께 제공한다.

pip은 대상 플랫폼과 Python 버전을 지정해 휠을 내려받을 수 있다(`pip download --only-binary=:all: --platform win_amd64 --python-version 3.13`). 이렇게 받은 휠 폴더를 들고 가서, 폐쇄망 PC에서는 인덱스를 보지 말고 그 폴더에서만 찾으라고 지시해 설치한다(`pip install --no-index --find-links <폴더>`). 이 프로젝트는 Python 3.11, 3.12, 3.13용 휠을 모두 받아 69개 파일로 묶어 두었다. 대상 PC의 Python 마이너 버전을 미리 몰라도 설치할 수 있게 하려는 것이다.

## 2.10 사내 PyPI 미러와 가상환경

v0.6.0 무렵 사내망에 PyPI 미러가 생겼다. "대상 PC에서는 pip을 쓸 수 없다"는 전제가 바뀐 것이다. 그렇다고 3.47GB짜리 포터블 Python을 런타임에 고치고 싶지는 않았다. 그래서 Python의 기능 몇 가지를 조합했다([ADR-019](adr/adr-019-side-venv-installs.md)).

첫째는 `--system-site-packages` 옵션으로 만든 가상환경(venv)이다. 이렇게 만든 venv는 새 패키지를 자기 폴더에 설치하면서도 바탕이 된 Python의 패키지를 그대로 볼 수 있다. pip은 pandas가 이미 있다는 걸 알고 다시 받지 않는다.

둘째는 `site.addsitedir`다. 이미 실행 중인 인터프리터의 모듈 검색 경로에 폴더를 추가하는 함수다. 패키지를 설치한 뒤 커널을 재시작하면 대화 중에 불러 둔 데이터가 사라진다. 그래서 재시작하는 대신 이 함수로 venv의 패키지 폴더를 살아 있는 커널에 붙인다. 이 함수는 경로를 목록의 뒤쪽에 덧붙인다는 점을 기억해 두자. 이 성질이 뒤에서 한계로 돌아온다.

셋째는 `importlib.metadata`다. 배포판 이름으로 설치된 버전을 조회하는 표준 라이브러리 기능이다. 이것을 커널 안에서 실행하면 "지금 이 커널이 그 패키지를 볼 수 있는가"를 직접 확인하는 셈이 된다. 배포판 이름으로 묻기 때문에 앞에서 말한 `beautifulsoup4`와 `bs4` 같은 이름 차이도 신경 쓸 필요가 없다.

pip을 미러에 연결할 때 알아 둘 옵션이 두 개 있다. `--index-url`은 패키지를 찾을 인덱스 주소다. `--trusted-host`는 그 인덱스가 https가 아닌 평문 http이거나 사내 인증서를 쓸 때 필요하다. 이 옵션 없이 http 인덱스를 주면 pip은 오류를 내는 대신 그 인덱스를 조용히 무시해 버린다. 이 동작 때문에 벌어진 일은 [ADR-020](adr/adr-020-verify-installs-directly.md)에 있다.

## 2.11 스레드와 비동기

서버 프로세스 안에는 여러 흐름이 동시에 있다.

- MCP 요청을 처리하는 이벤트 루프(asyncio)
- 커널 풀을 돌보는 백그라운드 스레드. 30초마다 오래 쓰지 않은 커널을 정리하고 예비 커널을 채운다.
- 패키지 설치를 수행하는 백그라운드 스레드. 설치 요청마다 하나씩 뜨고, 실제 pip 실행은 한 번에 하나만 돌도록 줄을 세운다.

커널 하나는 한 번에 한 요청만 처리해야 한다. 두 요청이 같은 커널의 메시지 채널을 번갈아 읽으면 출력이 뒤섞인다. 그래서 커널마다 재진입 가능한 락(RLock)을 두고 모든 조작을 그 락 안에서 한다. 서로 다른 커널은 서로 다른 락을 쓰므로 서로를 막지 않는다.

비동기 도구 함수 안에서 블로킹 작업(커널 호출, pip 실행)을 그대로 하면 이벤트 루프가 멈춘다. 설치 도구는 이런 작업을 `asyncio.to_thread`로 스레드에 넘기고, 기다리는 동안에는 0.5초 간격으로 깨어나 남은 시간을 확인하고, 5초마다 진행 알림을 보낸다.

## 생각해 볼 문제

1. stdio 대신 HTTP 전송을 썼다면 무엇이 좋아지고 무엇이 나빠질까? 여러 사용자가 샌드박스 서버 하나를 공유하는 상황을 떠올려 보자.
2. Jupyter 커널 대신, 호출마다 `subprocess`로 Python을 띄우되 결과 데이터를 pickle 파일로 저장했다가 다음 호출에서 불러오는 방식은 어떨까? 어떤 종류의 데이터에서 이 방식이 무너질까?
3. iopub 채널에서 `msg_id`로 메시지를 거르지 않으면 어떤 상황에서 문제가 생길까?
4. `--system-site-packages` venv에, 바탕 Python에도 있는 패키지를 더 높은 버전으로 설치했다. 커널은 어느 버전을 쓰게 될까? `site.addsitedir`가 경로를 어디에 추가하는지 떠올려 보자.
