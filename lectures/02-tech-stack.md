# 2장. 기술 스택

이번 장에서는 프로젝트를 구성하는 핵심 기술들을 계층별로 살펴봅니다. 단순히 각 기술의 일반적인 개념을 나열하기보다는, "본 시스템에서 왜 이 기술을 선택해야만 했는가"라는 기술적 의사결정 맥락에 초점을 맞추어 설명합니다.

## 2.1 기술 스택 한눈에 보기

## 2.2 MCP (Model Context Protocol)

MCP는 대형 언어 모델(LLM) 애플리케이션이 외부의 다양한 도구나 데이터 소스에 안전하게 접근할 수 있도록 Anthropic이 주도하여 표준화한 개방형 프로토콜입니다. 구조적으로는 LLM 앱이 클라이언트가 되고, 특정 기능을 제공하는 프로그램이 MCP 서버가 됩니다. 서버는 도구(Tools), 리소스(Resources), 프롬프트 템플릿(Prompts)의 세 가지 기능을 노출할 수 있는데, 본 프로젝트에서는 순수하게 '도구(Tools)' 기능만을 집중적으로 활용합니다.

통신 메시지는 JSON-RPC 2.0 표준 규격을 따릅니다. 클라이언트와 서버 사이에 프로세스 파이프가 연결되면, 먼저 `initialize` 요청을 주고받으며 서로의 프로토콜 버전과 지원 사양을 확인하는 핸드셰이크 과정을 거칩니다. 이때 서버는 자신의 이름과 버전을 전달하며, 본 프로젝트에서는 여기에 `v0.7.0`과 같은 시스템 버전 번호를 실어 클라이언트에 전달합니다. 이어서 클라이언트는 `tools/list` 요청을 전송하여 서버가 제공하는 전체 도구 목록을 조회합니다. 각 도구의 명세에는 도구 이름, 역할 설명문(Description), 그리고 인자 형식을 정의한 입력 스키마(JSON Schema)가 포함됩니다. 모델이 특정 도구를 사용하기로 결정하면 클라이언트는 `tools/call` 요청을 통해 도구 이름과 인자 값을 전달하며, 서버는 실행 결과를 가공하여 텍스트나 이미지 등의 콘텐츠 목록 형태로 반환합니다.

전송 계층(Transport)은 크게 두 가지 방식을 지원합니다. 클라이언트가 서버를 로컬 자식 프로세스로 직접 실행하고 표준 입출력(stdin/stdout)을 통해 메시지를 주고받는 stdio 방식과, 로컬/원격 네트워크 소켓을 이용하는 HTTP(SSE) 방식입니다. 본 프로젝트는 stdio 방식을 채택했습니다. AnythingLLM이 설정 파일에 지정된 경로에 따라 Python 프로세스를 구동하면, 해당 프로세스의 stdin과 stdout 파이프가 곧바로 양방향 통신 채널이 됩니다. 따라서 별도의 로컬 네트워크 포트를 개방할 필요가 없으며, 복잡한 방화벽 규칙이나 네트워크 보안 심의에서도 완전히 자유롭다는 결정적인 장점이 있습니다.

본 프로젝트의 동작 방식을 정확히 이해하기 위해서는 MCP가 지닌 다음 세 가지 본질적인 특성을 반드시 염두에 두어야 합니다.

**첫째, 도구 설명문(Description)은 모델이 읽고 판단하는 시스템 프롬프트입니다.** 클라이언트는 서버로부터 받아온 도구 목록과 설명문을 LLM의 프롬프트 컨텍스트에 그대로 주입합니다. 언어 모델은 오직 이 설명문에 적힌 텍스트만을 근거로 삼아 해당 도구를 언제, 어떤 형식으로 호출할지 판단합니다. 즉, 설명문에 어떤 문장과 지침을 기재하느냐에 따라 모델의 행동 패턴이 직접적으로 변화합니다. 본 프로젝트가 도구의 안전 사용 규칙을 시스템 프롬프트 대신 도구 설명문 내부에 집중적으로 배치한 이유가 바로 여기에 있습니다([ADR-007](adr/adr-007-rules-in-tool-descriptions.md)).

**둘째, 클라이언트는 서버의 응답을 무한정 기다려 주지 않습니다.** MCP 클라이언트 SDK는 모든 요청에 엄격한 타임아웃 제한 시간을 적용하며, 기본 설정값은 60초입니다. 서버가 아무리 정상적으로 연산을 수행하고 있더라도 60초 이내에 최종 응답을 돌려주지 못하면 클라이언트는 요청을 강제로 취소해 버립니다. 이 경우 AnythingLLM 화면에는 "Context server request timeout"이라는 오류 메시지만 출력되며, 사용자는 시스템 전체가 멈춘 것으로 오해하게 됩니다([ADR-021](adr/adr-021-tool-time-budget.md)).

**셋째, stdio 연결 채널은 여러 대화 세션을 스스로 구분하지 못합니다.** 클라이언트와 서버 프로세스 사이에는 단 하나의 표준 입출력 파이프만 존재합니다. 따라서 지금 들어온 도구 호출이 사용자의 여러 대화 창 중 구체적으로 어느 대화 세션에서 발생한 것인지 알려주는 표준 메타데이터 필드가 본 프로젝트 착수 시점에는 존재하지 않았습니다. 비록 프로토콜 수준에 `_meta`라는 메타데이터 필드가 정의되어 있긴 하지만, AnythingLLM 클라이언트는 여기에 대화 세션 ID를 넣어주지 않습니다. 이 현실적인 한계로 인해 모델이 직접 자신의 대화 ID를 인자로 넘기도록 강제하는 네임스페이스 설계가 필요해졌습니다([ADR-011](adr/adr-011-namespace-argument.md)).

## 2.3 FastMCP 프레임워크

FastMCP는 공식 MCP Python SDK에 내장된 고수준(High-level) 프레임워크입니다. 일반 Python 함수 위에 `@mcp.tool()` 데코레이터를 지정하기만 하면 함수의 이름이 곧 도구명이 되고, 함수의 타입 힌트(Type Annotation)를 바탕으로 Pydantic이 유효한 JSON Schema를 자동으로 생성해 줍니다. 도구 설명문 역시 함수의 독스트링(Docstring)이나 데코레이터 인자를 통해 손쉽게 선언할 수 있습니다.

특히 FastMCP에는 매우 유용한 '컨텍스트 주입(Context Injection)' 기능이 포함되어 있습니다. 도구 함수의 매개변수 중 MCP SDK의 `Context` 타입이 선언되어 있으면, FastMCP는 이 파라미터를 LLM에 노출되는 도구 스키마에서 자동으로 숨겨 줍니다. 그리고 런타임에 도구가 호출될 때 현재 요청의 내부 컨텍스트 객체를 해당 인자로 직접 주입해 줍니다. 덕분에 모델은 불필요한 시스템 인자의 존재를 신경 쓸 필요가 없으며, 서버 코드는 이 컨텍스트 객체를 활용하여 요청 메타데이터를 확인하거나 클라이언트에 실시간 진행률 알림(Progress Notification)을 전송할 수 있습니다. 본 프로젝트에서는 이 통로를 두 가지 핵심 지점에서 활용합니다. 향후 클라이언트가 대화 ID를 전달해 올 경우 이를 투명하게 수신하는 경로, 그리고 장시간 소요되는 패키지 설치 작업 도중 클라이언트에 진행 상황을 실시간으로 보고하는 통로입니다.

또한 도구 함수는 동기(Sync) 방식과 비동기(Async) 방식 모두 자유롭게 정의할 수 있습니다. 시간이 오래 소요되는 패키지 설치 도구 등은 비동기 함수로 구현하였으며, 동기 블로킹 방식으로 동작하는 Jupyter 커널 호출이나 무거운 pip 실행 작업은 `asyncio.to_thread`를 통해 별도의 OS 스레드로 분리하여 메인 이벤트 루프가 멈추지 않도록 보호했습니다.

한편 SDK 버전은 1.x 대역에 고정하여 사용하고 있습니다. 2.x 계열로 섣불리 전환하지 않고 버전을 고정한 기술적 배경은 [ADR-015](adr/adr-015-pin-mcp-sdk-1x.md)에서 확인하실 수 있습니다.

## 2.4 AnythingLLM 클라이언트

AnythingLLM은 다양한 상용/오픈소스 LLM 백엔드와 유연하게 연동되어 대화형 채팅, RAG 기반 문서 검색, 그리고 자율 에이전트 워크플로를 제공하는 데스크톱 애플리케이션입니다. 본 환경에서는 사용자 PC에 데스크톱 버전을 설치한 후, 사내 격리망에 위치한 원격 LLM 서버와 OpenAI 호환 API 인터페이스로 연동하여 활용하고 있습니다.

MCP 서버 연동 설정은 AnythingLLM의 JSON 설정 파일에 서버 메타데이터를 등록함으로써 이루어집니다. 각 MCP 서버 항목에 실행 파일 경로(`command`), 실행 인자 목록(`args`), 그리고 필요한 환경 변수(`env`)를 지정합니다. 사용자가 에이전트 모드에서 대화를 시작하면 AnythingLLM은 이 설정을 바탕으로 로컬 MCP 서버 프로세스를 자식 프로세스로 구동하고, 모델이 필요하다고 판단할 때마다 해당 도구들을 자동으로 호출합니다.

여기서 시스템 아키텍처 관점에서 반드시 유의해야 할 결정적인 사실은, AnythingLLM이 MCP 서버를 **인스턴스 단위로 단 하나만 구동**한다는 점입니다. 사용자가 화면에서 대화 탭을 5개 열어서 서로 다른 주제로 동시에 대화를 나누더라도 로컬 백그라운드에서 실행되는 MCP 서버 프로세스는 단 하나뿐입니다. 즉, 5개의 독립된 대화 세션에서 발생하는 도구 호출 요청이 모두 단 하나의 서버 프로세스로 들어오게 됩니다.

## 2.5 Jupyter 커널과 ZeroMQ 메시징 프로토콜

대화가 이어져도 변수와 상태를 지속적으로 유지하는 코드 실행기(Stateful Runner)를 밑바닥부터 직접 개발하려면 수많은 복잡한 엔지니어링 난제들을 해결해야 합니다. 코드를 격리하여 실행할 별도의 안전한 프로세스를 띄워야 하고, 소스코드를 표준 프로토콜로 전달해야 하며, 표준 출력과 표준 에러 스트림을 실시간으로 가로채야 합니다. 또한 런타임 예외를 안전하게 포착하고, 무한 루프에 빠진 프로세스를 강제 인터럽트해야 하며, 프로세스가 비정상 종료되었을 때 메모리를 정리하고 스스로 복구하는 체계도 갖추어야 합니다. Jupyter 오픈소스 생태계는 지난 십수 년간 이 복잡한 문제들을 가장 정교하고 안정적으로 해결해 왔습니다. Jupyter 노트북 인터페이스 뒤편에서 실제 코드 실행과 메모리 상태 관리를 전담하는 핵심 프로세스가 바로 "커널(Kernel)"입니다.

본 교육 프로젝트는 웹 브라우저 UI나 무거운 노트북 서버 없이, 순수 백엔드 커널 엔진 라이브러리만을 임베디드 형태로 추출하여 사용합니다.

- **ipykernel**: 표준 Python 커널 구현체입니다. 내부적으로 IPython 환경을 내장하여 실제 코드를 실행하고 메모리 네임스페이스를 관리합니다.
- **jupyter_client**: 커널 프로세스를 생성하고 관리하며 메시지를 주고받는 핵심 클라이언트 라이브러리입니다. 커널 프로세스의 시작과 종료, 재시작 등 수명주기를 전담하는 관리자(`KernelManager`)와, 통신 채널을 통해 실제 명령을 송수신하는 클라이언트(`KernelClient`)로 명확히 역할이 분리되어 있습니다.

MCP 서버와 Jupyter 커널 프로세스는 ZeroMQ 기반의 다중 소켓 통신을 통해 유기적으로 상호작용합니다. 용도에 따라 독립된 통신 채널들이 존재하며, 본 시스템의 실행 흐름에서 핵심적인 역할을 하는 채널은 다음 두 가지입니다.

| 채널명 | 통신 방향 | 본 시스템에서의 핵심 용도 |
|---|---|---|
| shell | 양방향 (요청-응답) | 코드 실행 요청(`execute_request`)을 커널에 전달하고, 실행 완료에 따른 최종 상태 응답(`execute_reply`)을 수신합니다. |
| iopub | 단방향 (커널 브로드캐스트) | 코드 실행 도중 발생하는 모든 실시간 이벤트를 수신합니다. 표준 출력 스트림(`stream`), 최종 식 평가 결과(`execute_result`), 런타임 예외 및 트레이스백(`error`), 커널 상태 전이(`status: busy/idle`) 등이 포함됩니다. |

이 외에도 강제 인터럽트 및 프로세스 즉각 종료에 사용하는 `control` 채널, 사용자 대화형 입력을 요청하는 `stdin` 채널, 커널 프로세스의 생존 여부를 주기적으로 체크하는 `heartbeat` 채널 등이 백그라운드에서 동작합니다.

단일 코드 블록이 실행되는 전체적인 라이프사이클은 다음과 같습니다. 클라이언트가 `shell` 채널을 통해 `execute_request` 메시지를 전송하면, 해당 요청마다 전역적으로 고유한 `msg_id`가 발급됩니다. 커널은 요청을 수신하자마자 `iopub` 채널로 `status: busy` 상태를 즉시 알립니다. 코드가 실행되는 동안 `print` 등의 출력이 발생하면 실시간으로 `stream` 메시지를 흘려보내고, 예외가 발생하면 에러 트레이스백을 담은 `error` 메시지를 전송합니다. 마지막으로 모든 실행이 완료되면 커널은 `status: idle` 메시지를 브로드캐스팅합니다. 여기서 중요한 점은 `iopub`으로 수신되는 모든 개별 메시지의 헤더(`parent_header.msg_id`)에 해당 이벤트를 촉발한 최초 요청의 `msg_id`가 명확히 기록되어 있다는 사실입니다.

이러한 메시징 구조 덕분에 실행기 코어의 책임은 매우 명료해집니다. 커널에 실행 요청을 보낸 후, `iopub` 채널로 들어오는 수많은 메시지 중 내 요청의 `msg_id`와 일치하는 메시지만을 선별하여 버퍼에 수집하다가, 최종적으로 `idle` 상태 메시지가 도착하면 실행이 끝난 것으로 판단하고 결과를 취합합니다. 또한 새 요청을 보내기 직전에 이전 요청이 남겨두었을지 모를 잔여 메시지들을 깨끗이 비워내는 작업(Flush)도 필수적으로 수행해야 합니다. 이 상세한 실행 시퀀스는 [동적 뷰](03-architecture/02-dynamic-view.md)의 시퀀스 다이어그램에서 구체적으로 확인하실 수 있습니다.

ZeroMQ 소켓 바인딩은 로컬 루프백 주소인 `127.0.0.1`만을 사용합니다. 루프백 통신은 물리적 네트워크 카드나 외부 인터넷 연결이 전혀 없는 환경에서도 OS 커널 내부에서 원활하게 동작하므로 사내 폐쇄망 보안 규정과 완벽히 부합합니다. 커널 프로세스가 처음 기동될 때 "암호화(HMAC) 없이 비보안 TCP로 동작한다"는 안내 경고가 콘솔에 출력될 수 있으나, 이는 PC 내부 프로세스 간 통신에 국한된 알림이므로 정상적인 동작이며 안심하셔도 됩니다.

아울러 `KernelManager`는 실행 중인 커널에 강제 인터럽트를 전달하여 무한 루프 코드에 `KeyboardInterrupt` 예외를 발생시키거나, 프로세스를 완전히 강제 종료한 뒤 깨끗한 메모리 상태로 신규 기동하는 재시작(Restart) API를 완벽히 지원합니다. 이 두 가지 기능은 시스템의 엄격한 타임아웃 방어 체계에서 핵심적인 복구 수단으로 활용됩니다.

## 2.6 IPython 환경에서 반드시 알아 두어야 할 동작 특성

커널 프로세스 내부에서 실제 코드를 파싱하고 실행하는 주체는 IPython 인터프리터 엔진입니다. 따라서 명령줄에서 `python script.py` 형태로 일반 스크립트를 직접 실행할 때와 비교하여 다음과 같은 몇 가지 중요한 동작 차이가 존재합니다.

- 코드가 실행되는 전역 네임스페이스(Global Scope)의 모듈 이름인 `__name__` 변수에 이미 `"__main__"` 문자열이 할당되어 있습니다. 따라서 일반 스크립트 소스코드를 이 네임스페이스 안에서 그대로 실행하더라도 파일 하단의 `if __name__ == "__main__":` 블록이 누락 없이 정상적으로 실행됩니다([ADR-010](adr/adr-010-run-script-file.md)).
- 실행된 코드 블록의 가장 마지막 라인이 단독 표현식(Expression)으로 끝날 경우, 별도로 `print()` 함수를 호출하지 않더라도 해당 식의 평가 결과(`repr`)가 `iopub` 채널의 `execute_result` 메시지로 자동 캡처되어 반환됩니다.
- 사용자 코드가 명시적으로 `sys.exit()`를 호출할 경우, 일반 Python 프로세스처럼 전체 프로세스가 즉시 종료되는 것이 아니라 IPython 환경이 이를 가로채어 `SystemExit` 예외 객체로 변환한 후 오류 메시지로 보고합니다. 따라서 종료 코드 0으로 지극히 정상 종료된 스크립트 파일조차 시스템 상에서는 심각한 "실행 에러"처럼 잘못 전달될 위험이 있었습니다. 본 프로젝트는 v0.5.0에서 이 동작을 정밀하게 보정하여 정상 종료로 올바르게 판정하도록 개선했습니다([ADR-017](adr/adr-017-execution-verdict.md)).

## 2.7 포터블 Python 런타임: WinPython 선정 배경

외부 인터넷이 완전히 차단된 사내망 PC에 독립된 Python 런타임과 수십 종의 데이터 분석 라이브러리를 안전하게 공급하는 방법에는 여러 가지 기술적 대안이 존재합니다. 프로젝트 기획 당시 검토했던 주요 후보들을 비교하면 다음과 같습니다.

| 공급 방식 | 핵심 장점 | 단점 |
|---|---|---|
| WinPython 번들 | 임의의 디렉터리에 압축 해제만 하면 즉시 독립 실행됩니다. pip 및 컴파일 도구가 완벽히 포함되어 있습니다. | 초기 배포 번들의 용량이 수 기가바이트(GB) 단위로 다소 큽니다. |
| 공식 python.org Embeddable 패키지 | 용량이 수십 MB 단위로 매우 작고 가볍습니다. | pip 패키지 관리자가 기본 제외되어 있으며, `site` 모듈이 비활성화되어 있어 외부 라이브러리 추가 구성이 매우 번거롭습니다. |
| conda-pack 아카이브 | 복잡한 C/C++ 의존성을 포함한 Conda 가상환경을 그대로 패키징할 수 있습니다. | 사용자가 Conda 도구에 익숙해야 하며, 아카이브 압축 해제 후 하드코딩된 절대 경로들을 일괄 재조정하는 별도 보정 스크립트가 필요합니다. |
| 일반 virtualenv (venv) 디렉터리 통째 복사 | 기존 Python 개발자들에게 가장 익숙한 방식입니다. | 생성 당시 호스트 환경의 절대 경로가 내부에 하드코딩되므로, 다른 PC나 경로로 복사하면 즉시 경로 참조 오류가 발생하여 정상 동작하지 않습니다. |

이러한 비교 평가를 거쳐 본 프로젝트는 최종적으로 **WinPython 3.13**(Python 3.13.13 기반)을 공식 런타임으로 선정했습니다. 필수 데이터 사이언스 패키지와 MCP 서버 구동 의존성을 모두 사전 설치하여 패키징한 최종 번들의 크기는 약 3.47GB입니다. 초기 요구 명세서에 명시되었던 "약 4GB 규모의 포터블 Python 번들"의 실체가 바로 이 패키지입니다([ADR-004](adr/adr-004-portable-python-bundle.md)).

포터블 Python 번들을 오프라인으로 제작할 때 가장 각별히 주의해야 할 점은 **바이너리 플랫폼의 일치**입니다. numpy, scipy, PyMuPDF, pyzmq와 같이 C/C++ 네이티브 확장 모듈을 포함하는 고성능 패키지들은 운영체제(OS), CPU 아키텍처, 그리고 Python의 마이너 버전별로 사전 빌드된 바이너리 휠(Wheel) 파일을 사용합니다. 따라서 빌드를 수행하는 작업용 PC와 실제 패키지가 배포되어 구동될 폐쇄망 PC는 반드시 동일한 Windows 64비트(`win_amd64`) 아키텍처여야 하며, Python의 세부 마이너 버전 역시 동일해야만 런타임 링크 오류를 방지할 수 있습니다.

## 2.8 기본 내장 데이터 사이언스 스택

폐쇄망 환경에서도 임직원들이 데이터 분석 및 자동화 업무를 원활하게 수행할 수 있도록, 커널용 Python 환경에 사전 설치하여 제공하는 핵심 라이브러리 목록은 다음과 같습니다.

| 업무 활용 영역 | 내장 라이브러리 목록 |
|---|---|
| 수치 해석 및 기호 수학 | numpy, scipy, sympy |
| 정형 표 데이터 분석 | pandas, polars, duckdb, pyarrow |
| 엑셀 및 스프레드시트 처리 | openpyxl (xlsx 읽기/쓰기), xlsxwriter (고속 xlsx 생성), xlrd (구형 xls 파싱) |
| PDF 문서 분석 및 텍스트 추출 | pdfplumber (표 구조 추출에 강력), pypdf, PyMuPDF |
| 오피스 문서 자동화 | python-docx (워드 문서 생성/파싱), python-pptx (파워포인트 자동화) |
| 웹 및 마크다운 문서 처리 | lxml, xmltodict, beautifulsoup4, markdown |
| 보고서 자동 생성 | reportlab (순수 Python 기반 PDF 리포트 빌드), jinja2 (텍스트 템플릿 엔진) |
| 데이터 시각화 | matplotlib, seaborn, plotly |
| 유틸리티 및 텍스트 처리 | Pillow (이미지 처리), rapidfuzz (고속 유사 문자열 검색), python-dateutil |

위 패키지 중 `pandas`, `numpy`, `scipy`, `sympy`, `matplotlib`, `openpyxl`, `lxml`, `beautifulsoup4`의 8개 핵심 라이브러리는 시스템의 "필수 의존성"으로 지정되어 있습니다. 서버 기동 시 진행되는 오프라인 사전 점검(Pre-flight Check) 단계에서 이 중 단 하나라도 누락되면 서버는 기동을 중단하고 실패를 반환합니다. 반면 나머지 라이브러리들은 "권장 의존성"으로 분류되어 누락되더라도 경고 로그만 남긴 채 정상 기동됩니다.

실무 개발 및 점검 시 주의해야 할 몇 가지 패키지 명칭 불일치 문제가 있습니다. 예를 들어 PyMuPDF는 패키지 설치명과 실제 Python 코드 내의 import 패키지명이 달라서 반드시 `import fitz`로 호출해야 합니다. 또한 beautifulsoup4는 `import bs4`, python-docx는 `import docx`, python-pptx는 `import pptx`, Pillow는 `import PIL`을 사용합니다. 따라서 특정 라이브러리의 설치 여부를 프로그램 코드로 검사할 때, pip 배포판 명칭으로 확인할 것인지 아니면 import 모듈 명칭으로 확인할 것인지 명확히 구분해야 혼선을 방지할 수 있습니다.

또한 `matplotlib`은 GUI가 활성화된 일반 데스크톱 환경에서는 기본적으로 새 창을 띄워 차트를 렌더링하려고 시도합니다. 그러나 백그라운드에서 백엔드로 구동되는 Jupyter 커널은 화면 디스플레이가 연결되지 않은 헤드리스(Headless) 프로세스입니다. 따라서 커널이 초기화될 때 화면을 띄우지 않고 메모리 상에서 이미지 파일만을 안전하게 렌더링할 수 있도록 백엔드를 즉시 `Agg` 모드로 강제 전환해 둡니다. 참고로 첫 번째 차트를 생성할 때 OS에 설치된 시스템 폰트들의 캐시를 구축하느라 수 초간 초기 지연이 발생할 수 있는데, 이는 순수하게 로컬 디스크 I/O 작업일 뿐 네트워크 통신과는 전혀 무관합니다.

## 2.9 오프라인 휠(Wheel) 아카이브 패키징

샌드박스 서버 프로세스 자체를 구동하는 데 필요한 최소 의존성은 `mcp`, `jupyter_client`, `ipykernel`의 3가지 핵심 패키지입니다(다만 이 패키지들이 요구하는 전이적 하위 의존성까지 모두 포함하면 수십 개에 달합니다). 포터블 Python 번들을 온전히 사용할 수 있는 환경이라면 이미 이들이 내장되어 있으므로 추가 작업이 필요 없습니다. 그러나 폐쇄망 PC에 이미 사내 표준 Python 환경이 사전에 설치되어 있어서, 포터블 번들 전체를 반입하는 대신 본 서버 구동용 패키지만 가볍게 추가 설치하고자 하는 운영 시나리오가 있을 수 있습니다. 본 프로젝트는 이러한 요구에 대응하기 위해 인터넷이 연결된 외부 PC에서 사전에 종속성 휠 파일들을 일괄 수집하여 번들링하는 절차를 완벽히 지원합니다.

pip은 대상 OS 플랫폼과 Python 버전을 명시하여 외부 머신에서 해당 규격의 휠 파일만을 다운로드할 수 있는 기능을 제공합니다(`pip download --only-binary=:all: --platform win_amd64 --python-version 3.13`). 이렇게 수집된 오프라인 휠 디렉터리를 USB 등의 승인된 매체로 폐쇄망 PC에 반입한 뒤, 외부 인덱스를 조회하지 않고 해당 로컬 디렉터리만을 바라보도록 지시하여 패키지를 안전하게 설치합니다(`pip install --no-index --find-links <휠_폴더_경로>`). 본 프로젝트는 현업 PC에 이미 깔려 있을지 모를 다양한 버전에 대비하여 Python 3.11, 3.12, 3.13을 지원하는 총 69개의 바이너리 휠 파일을 사전 패키징하여 제공합니다. 이를 통해 대상 PC의 세부 Python 버전을 사전에 알지 못하더라도 유연하게 설치를 진행할 수 있습니다.

## 2.10 사내 PyPI 미러 서버와 사이드 가상환경(venv)

프로젝트 운영 중반(v0.6.0 시점)에 전사 인프라 차원에서 사내 폐쇄망 내부에 공식 PyPI 미러 서버가 구축되었습니다. 이에 따라 "대상 PC에서는 런타임에 pip을 일절 실행할 수 없다"는 기존의 전제 조건에 중대한 변화가 생겼습니다. 하지만 사용자가 임의의 패키지를 자유롭게 설치하도록 허용하면서도, 이미 안정적으로 검증해 둔 3.47GB 용량의 포터블 Python 기본 환경이 오염되거나 훼손되는 문제는 반드시 방지해야 했습니다. 이에 따라 표준 Python이 제공하는 몇 가지 격리 메커니즘을 조합하여 이 문제를 해결했습니다([ADR-019](adr/adr-019-side-venv-installs.md)).

첫 번째 기법은 `--system-site-packages` 옵션을 활성화하여 생성한 사이드 가상환경(Side venv)입니다. 이 옵션으로 구축된 venv는 신규로 설치되는 패키지만을 자신의 독립된 격리 폴더에 저장하면서도, 상위 기본 Python 환경에 이미 설치된 대용량 패키지(pandas, numpy 등)들을 투명하게 참조할 수 있습니다. 따라서 pip은 pandas가 이미 베이스 환경에 존재함을 인지하고 중복 다운로드 없이 즉시 재사용합니다.

두 번째 기법은 `site.addsitedir()` 함수의 동적 활용입니다. 이 함수는 이미 구동 중인 Python 인터프리터의 실시간 모듈 검색 경로(`sys.path`)에 특정 디렉터리를 동적으로 추가해 줍니다. 패키지 설치가 완료되었다고 해서 실행 중인 커널을 재시작해 버리면, 사용자가 이전 대화에서 메모리에 적재해 둔 수많은 데이터프레임과 분석 변수들이 전부 사라져 버립니다. 따라서 커널을 재시작하는 대신, `site.addsitedir()`를 커널 내부에서 즉각 실행하여 방금 생성된 사이드 venv의 패키지 설치 경로를 실행 중인 커널 세션에 실시간으로 반영합니다. 다만 여기서 반드시 유의할 점은 이 함수가 신규 경로를 검색 우선순위의 가장 뒤쪽에 추가한다는 사실입니다. 이 동작 특성은 후술할 버전 오버라이딩 한계의 원인이 됩니다.

세 번째 기법은 표준 라이브러리인 `importlib.metadata`를 통한 설치 검증입니다. 패키지의 배포판 이름(Distribution Name)을 기준으로 설치된 실제 버전을 조회하는 표준 API입니다. 이 검증 코드를 커널 내부에서 직접 실행함으로써, "현재 동작 중인 커널 세션이 해당 패키지를 실제로 정상 로드할 수 있는가"를 가장 직접적이고 확실하게 증명할 수 있습니다. 배포판 명칭을 기준으로 질의하기 때문에 앞서 언급했던 `beautifulsoup4`와 `bs4` 사이의 복잡한 패키지명-모듈명 불일치 문제도 자연스럽게 해소됩니다.

사내 pip 미러 서버를 연동할 때 반드시 숙지해야 할 핵심 옵션 두 가지가 있습니다. 첫째는 패키지 검색 대상 저장소 주소를 지정하는 `--index-url`입니다. 둘째는 해당 미러 서버가 사내 사설 SSL 인증서를 사용하거나 보안이 해제된 평문 HTTP 주소를 사용할 때 보안 검증을 우회하기 위한 `--trusted-host`입니다. 만약 HTTP 기반의 사내 미러 서버를 지정하면서 이 신뢰 호스트 옵션을 누락할 경우, pip은 에러 메시지를 명확히 띄우는 대신 해당 인덱스를 조용히 무시해 버리고 아무 패키지도 찾지 못하는 현상이 발생합니다. 이 동작 특성으로 인해 발생했던 실제 장애 사례는 [ADR-020](adr/adr-020-verify-installs-directly.md)에서 자세히 다룹니다.

## 2.11 스레드와 비동기 동시성 제어 모델

MCP 서버 프로세스 내부에서는 여러 갈래의 실행 흐름(동시성)이 긴밀하게 협력하며 동작합니다.

- **MCP 요청 수신 및 디스패치**: 클라이언트와의 비동기 JSON-RPC 통신을 총괄하는 메인 이벤트 루프(`asyncio`)
- **유휴 커널 풀 관리 워커**: 30초 주기로 깨어나 오랫동안 사용되지 않은 유휴 커널 세션을 안전하게 정리하고 상시 대기 중인 예비 커널을 보충하는 백그라운드 관리 스레드
- **패키지 백그라운드 설치 워커**: 대용량 패키지 설치 요청이 들어왔을 때 메인 루프를 방해하지 않고 독립 실행되는 설치 전용 스레드 (내부 락을 통해 한 번에 단 하나의 pip 작업만 순차 실행되도록 직렬화)

여기서 하나의 Jupyter 커널 세션은 구조적으로 한 번에 단 하나의 실행 요청만을 처리해야 합니다. 만약 서로 다른 두 개의 요청이 동일한 커널의 ZeroMQ 소켓 채널을 동시에 읽고 쓰려 한다면 메시지 프레임이 뒤섞여 심각한 프로토콜 오염이 발생합니다. 이를 방지하기 위해 각 커널 객체마다 전용 재진입 가능 락(`threading.RLock`)을 배치하고, 모든 커널 조작 및 통신을 반드시 이 락 안에서만 수행하도록 강제했습니다. 서로 다른 커널은 서로 다른 독자 락을 사용하므로 다중 세션 환경에서도 상호 간섭 없이 높은 병렬성을 유지합니다.

또한 비동기 도구 함수 내부에서 동기 블로킹 호출(커널 소켓 대기, 무거운 pip 프로세스 실행 등)을 직접 수행하면 메인 이벤트 루프가 즉시 멈춰 전체 MCP 서버가 응답하지 못하게 됩니다. 따라서 패키지 설치 도구 등은 이러한 블로킹 작업을 `asyncio.to_thread`로 안전하게 백그라운드 스레드에 위임합니다. 그동안 메인 비동기 루프는 0.5초 주기로 타이머를 폴링하며 남은 타임아웃 예산을 정밀하게 감시하고, 5초 주기로 클라이언트에 작업 진행률 알림을 전송하여 클라이언트 타임아웃으로 인한 연결 종료를 안정적으로 방지합니다.

## 생각해 볼 문제

1. stdio 파이프 방식 대신 로컬 HTTP/SSE 전송 방식을 채택했다면 시스템 아키텍처에 어떤 장단점이 발생하겠습니까? 특히 여러 사용자나 여러 클라이언트가 중앙의 단일 샌드박스 서버 인스턴스를 공유하는 환경을 가정하고 비교해 보시기 바랍니다.
2. 상태를 유지하는 Jupyter 커널 프로세스 대신, 매 도구 호출마다 `subprocess`로 Python 프로세스를 새로 띄우되 이전 실행의 결과 변수들을 pickle 파일로 디스크에 직렬화했다가 다음 호출에서 역직렬화하는 방식을 적용한다면 어떤 한계와 장애에 직면하겠습니까? 어떤 종류의 데이터 객체에서 이 구조가 정상 동작하지 않거나 심각한 문제를 일으키겠습니까?
3. ZeroMQ의 `iopub` 메시지 스트림을 수신할 때 메시지 헤더의 `msg_id`를 기준으로 응답을 정밀하게 필터링하지 않는다면, 실제 다중 요청 또는 타임아웃 복구 상황에서 구체적으로 어떤 비정상적인 버그가 유발되겠습니까?
4. `--system-site-packages` 옵션으로 구축된 가상환경에, 베이스 포터블 환경에 이미 설치되어 있는 패키지보다 더 높은 신규 버전의 패키지를 중복 설치했습니다. 이때 커널 세션 내부에서는 구버전과 신버전 중 어느 쪽이 임포트되겠습니까? 앞서 설명한 `site.addsitedir()` 함수의 동작 방식과 검색 경로 순서를 바탕으로 그 이유를 논리적으로 설명해 보시기 바랍니다.
