# 4장. LLM을 위한 도구 설계

보통의 API는 사람 개발자가 쓴다. 개발자는 헷갈리면 문서를 다시 읽고, 예제를 찾아보고, 디버거를 켠다. MCP 도구를 쓰는 것은 LLM이다. 모델은 도구 설명문을 읽고, 인자를 채워 부르고, 돌아온 텍스트를 읽고, 다음 행동을 정한다. 되묻지 않는다. 모델이 작을수록 긴 설명문을 흘려 읽고, 응답의 앞머리와 끝부분에 크게 기댄다.

이 프로젝트의 v0.4.0 이후 변경은 대부분 이 사실을 하나씩 배워 간 기록이다. 코드는 설계대로 동작했는데 모델이 결과를 잘못 읽어서 사용자에게 틀린 답이 갔다. 이 장에서는 그 과정에서 얻은 원칙을 일곱 가지로 정리한다. 이 원칙들은 이 프로젝트에만 해당하지 않는다. LLM이 부르는 도구를 만든다면 어디에나 적용할 수 있다.

## 4.1 설명문은 문서가 아니라 프롬프트다

MCP 클라이언트는 도구 목록을 받아 그대로 모델의 컨텍스트에 넣는다. 모델이 도구에 대해 아는 것은 이름, 입력 스키마, 설명문이 전부다. README나 위키는 모델에게 보이지 않는다.

그래서 이 프로젝트는 코드 실행 도구의 설명문에 번호를 붙인 사용 규칙을 넣었다. 현재 규칙을 우리말로 옮기면 이렇다.

0. **네임스페이스.** 첫 호출에는 `"new"`를 넘기고, 이후에는 응답에 나온 `active_namespace` 값을 그대로 넘겨라.
1. **설치 금지.** 실행하는 코드 안에서 pip, apt, conda를 쓰지 말고 네트워크에 접속하지 마라. 필요한 라이브러리가 목록에 없으면 설치 도구를 불러라. (이어서 미리 설치된 라이브러리 목록이 나온다.)
2. **출력.** `print()`한 것만 돌아온다. 최종 값과 요약은 모두 `print()`로 감싸라.
3. **그림과 보고서.** `plt.show()`를 쓰지 말고 `plt.savefig('chart.png')` 후 `plt.close()`를 불러라. plotly는 `write_html`로 저장하라.
4. **경로.** 작업 디렉터리가 곧 워크스페이스다. `./workspace/`를 붙이지 말고 파일 이름만 써라. 워크스페이스는 다른 대화와 공유되니 파일 이름을 겹치지 않게 지어라.
5. **자가 수정.** stderr에 오류가 있으면 트레이스백을 읽고 고쳐서 같은 네임스페이스로 다시 실행하라.
6. **"실행됨"은 "성공함"이 아니다.** 판정 값은 샌드박스가 관측한 것만 말한다. 출력이 요청에 실제로 답하는지 확인하기 전에는 성공했다고 보고하지 마라. 응답 마지막 줄의 `next_action`을 따르라.

규칙마다 막으려는 실패가 하나씩 있다. 폐쇄망에서 `pip install`을 시도하면 한참 멈췄다가 실패한다. `plt.show()`는 화면이 없는 커널에서 아무것도 남기지 않는다. `print`를 빼먹으면 계산은 했는데 결과가 돌아오지 않는다. 규칙은 이런 실패를 미리 알려 주는 역할을 한다.

규칙에는 비용도 있다. 이 규칙 묶음만 해도 도구 하나당 500토큰 가까이 된다. 그래서 규칙은 코드를 실행하는 두 도구에만 붙이고, 파일 저장 도구와 목록 도구에는 붙이지 않았다. 가볍게 쓰라고 만든 도구의 설명문을 무겁게 만들면 만든 의미가 없다. 게다가 규칙의 첫 항목은 `namespace`를 요구하는데, 이 두 도구는 `namespace`를 받지 않는다. 규칙을 붙였다면 모델만 헷갈렸을 것이다.

그리고 한계가 있다. 약한 모델은 긴 규칙을 끝까지 지키지 않는다. v0.5.0을 설계하며 정리한 문서에는 이런 취지의 문장이 있다. 약한 모델은 규칙은 안 읽어도 첫 줄은 읽는다. 규칙으로 설득하는 데 기대지 말고, 응답의 모양으로 강제하자는 것이다. 다음 원칙들이 여기서 나왔다.

## 4.2 중요한 것은 처음과 끝에 둔다

모델은 긴 텍스트의 가운데보다 처음과 끝을 더 잘 붙잡는다. 이 성질을 거스르지 말고 이용하기로 했다. v0.5.0 이후 실행 도구의 응답은 이렇게 배치된다.

```
execution_status: RAN_WITH_ERRORS                  ← 첫 줄: 판정
The code finished, but errors were reported ...     ← 판정의 뜻

active_namespace: ns-3fa1                           ← 네임스페이스 안내
Reusing your namespace. Keep passing namespace="ns-3fa1".

--- stderr ---                                      ← 판정의 근거를 먼저
...

--- stdout ---
rc ignored

--- artifacts ---
(no new files created in the workspace)

[reminder] your namespace = "ns-3fa1" -- ...        ← 네임스페이스 재안내
next_action: Treat this as unfinished until you ... ← 마지막 줄: 할 일
```

판정이 첫 줄, 해야 할 일이 마지막 줄이다. stderr를 stdout보다 위에 올린 것도 같은 이유다. 판정이 `FAILED`라면 그 이유는 stderr에 있으니, 모델이 판정 바로 다음에 근거를 읽게 된다.

`next_action`은 명령문이다. "성공으로 보고하지 마라. stderr를 읽고 고쳐서 같은 네임스페이스로 다시 실행하라"처럼 구체적인 행동을 지시한다. 판정마다 문구가 다르고, 모델이 그다음에 할 일을 고민하지 않아도 되게 쓴다.

이 배치는 설치 도구에도 그대로 적용했다. 첫 줄은 `install_status:`, 마지막 줄은 `next_action:`이다. 한 시스템 안의 도구들이 같은 모양으로 답하면 모델이 하나를 익힌 뒤 나머지를 쉽게 따라온다.

## 4.3 확인하지 못한 성공은 말하지 않는다

v0.4.1까지 코드 실행 결과의 상태 값은 `SUCCESS`, `ERROR`, `TIMEOUT` 셋이었다. `SUCCESS`의 실제 뜻은 "예외가 밖으로 새어 나오지 않았다"였다. 그런데 모델은 이 단어를 "사용자가 시킨 일이 끝났다"로 읽었다. 실제로 재 보니 다음이 모두 `SUCCESS`로 보고되고 있었다.

| 실행한 코드 | 당시 상태 | 실제로 일어난 일 |
|---|---|---|
| `logging.error('db unreachable')` | SUCCESS | stderr에 오류 로그가 찍혔다 |
| `traceback.print_exc()` | SUCCESS | 예외를 잡아서 트레이스백만 출력했다 |
| 백그라운드 스레드에서 예외 | SUCCESS | 스레드가 죽었다 |
| `subprocess.run(...)`이 종료 코드 3 | SUCCESS | 하위 프로세스가 실패했다 |
| `x = 1` | SUCCESS | 아무것도 출력하지 않았다 |
| `sys.exit(0)` | **ERROR** | 정상 종료였다 |

모델은 첫 줄의 SUCCESS를 보고 사용자에게 "완료했습니다"라고 답했다. 마지막 줄처럼 정상 종료가 ERROR로 나오자 멀쩡한 코드를 "고치려고" 헤매기도 했다.

고친 방향은 단어를 바꾸는 것만이 아니었다. 샌드박스가 **증명할 수 있는 것**과 **없는 것**을 나눴다. 샌드박스는 실패를 증명할 수 있다. 예외가 났고, 종료 코드가 0이 아니고, 스레드가 죽었다는 것은 관측된다. 그러나 성공은 증명할 수 없다. 코드가 사용자의 의도대로 동작했는지는 서버가 알 길이 없다. 그래서 새 어휘에서 가장 좋은 판정은 `RAN_UNVERIFIED`, "예외 없이 끝났지만 검증되지 않았다"다. `SUCCESS`라는 단어는 아예 없앴다.

| 판정 | 뜻 |
|---|---|
| `RAN_UNVERIFIED` | 예외 없이 끝났다. 성공의 증거는 아니다 |
| `RAN_NO_OUTPUT` | 끝났지만 출력도 파일 변화도 없어서 무엇을 했는지 알 수 없다 |
| `RAN_WITH_ERRORS` | 끝났지만 실행 중에 오류가 보고되었다 |
| `FAILED` | 예외, 0이 아닌 종료 코드, 또는 도구의 거절 |
| `TIMEOUT` | 제한시간에 걸려 끝나지 못했다 |

반대 방향의 위험도 있다. 경보가 지나치면 모델이 끝없이 재시도한다. `logging.warning` 수준의 잡음에도 "실패"라고 하면, 약한 모델은 멀쩡한 코드를 계속 고친다. 그래서 `RAN_WITH_ERRORS`는 "실패"가 아니라 "보고하기 전에 확인하라"로 표현했다. `next_action`도 "실제 문제라면 한 번 고쳐서 다시 실행하고, 무해하다면 그렇다고 분명히 말하라"다. 또한 stdout에 `FAIL`이라는 글자가 찍혔다고 판정을 바꾸지는 않는다. 평범한 출력의 단어로 판정을 흔들면 오탐이 너무 많다.

같은 원칙이 설치 도구에도 적용되었다. pip이 종료 코드 0으로 끝났다는 것은 다운로드가 되었다는 증거일 뿐, 커널에서 import된다는 증거는 아니다. 그래서 `INSTALLED`는 커널이 각 패키지의 버전을 직접 대답했을 때만 쓴다. 반대로 파일 저장 도구는 `SUCCESS`를 쓴다. 파일은 서버가 직접 썼고, 쓴 결과를 서버가 확인할 수 있기 때문이다. 기준은 같다. **서버가 확인한 것만 긍정한다.**

## 4.4 거절할 때는 고치는 방법까지 말한다

약한 모델은 "규칙 위반"이라는 추상적인 말보다 "이렇게 다시 불러라"라는 구체적인 지시를 훨씬 잘 따른다. 이 프로젝트의 거절 메시지는 모두 해결 방법을 담고 있다.

| 상황 | 응답이 알려 주는 해결 방법 |
|---|---|
| 저장하려는 파일이 이미 있다 | `overwrite=true`로 다시 부르거나 다른 파일 이름을 써라 |
| 실행하려는 파일이 없다 | `list_workspace_files`로 있는 파일을 확인하라 |
| 설치 요청에 URL이나 pip 플래그가 섞였다 | 어느 토큰이 문제였는지 짚고, 패키지 이름만 다시 보내라 |
| 설치가 아직 끝나지 않았다(`RUNNING`) | 정확히 이 `packages` 문자열과 이 `namespace`로 지금 다시 불러라. 그사이 다른 설치를 시작하지 마라 |
| 미러가 설정되지 않아 설치에 실패했다 | 같은 설치를 반복하지 말고, 사용자에게 무엇을 고쳐야 하는지 한 문장으로 알려라 |
| `namespace` 없이 초기화를 요청했다 | 되돌리려는 `ns-XXXX` 값을 달라 |

마지막에서 두 번째 줄을 눈여겨보자. 사용자 PC의 설정 문제는 모델이 고칠 수 없다. 그럴 때는 재시도를 막고, 사람에게 넘길 말을 정해 준다.

도구가 요청 자체를 거절할 때도 실패한 실행과 같은 모양으로 답한다. 첫 줄은 `execution_status: FAILED`이고 바로 다음 줄에 "도구가 요청을 거절했으므로 코드는 전혀 실행되지 않았다"고 적는다. 모양이 같으면 모델이 거절을 특별한 경우로 다루지 않아도 된다.

## 4.5 인자는 평평하게, 모양은 단순하게

v0.4.0 이전에는 "이 코드를 fib.py로 저장해 줘"라는 요청을 처리하려면 모델이 이런 코드를 써야 했다.

```python
source = '''def fib(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

if __name__ == "__main__":
    print(sum(fib(i) for i in range(1, 11)))
'''
with open("fib.py", "w", encoding="utf-8") as f:
    f.write(source)
```

코드 안에 코드가 문자열로 들어간다. 따옴표가 겹치고, 저장할 소스 안에 삼중 따옴표나 역슬래시가 있으면 이스케이프도 해야 한다. 작은 모델은 이 자기 참조 구조에서 거의 확실하게 무너진다. 흔한 실패 모습은 저장하는 부분을 빼먹고 피보나치 계산 결과만 출력하는 것이었다.

해법은 문자열 두 개를 받는 저장 전용 도구였다. 파일 이름과 내용을 따로 받으니 중첩이 사라진다([ADR-014](adr/adr-014-write-file-tool.md)). 같은 생각이 다른 곳에도 적용되었다.

- 설치 도구의 `packages`는 JSON 배열이 아니라 문자열 하나다. `"polars, rapidfuzz>=3.0"`처럼 쉼표나 공백으로 구분한다. 작은 모델은 배열보다 평범한 문자열을 훨씬 안정적으로 만든다.
- 네임스페이스를 새로 만들 때 `"new"`가 정답이지만, 빈 문자열이나 `"auto"`, `"default"`, `"none"`, `"null"`도 같은 뜻으로 받아 준다.
- 경로는 `fib.py`로 써도 `./workspace/fib.py`로 써도 같은 파일로 해석한다.
- 저장 도구에는 이어 쓰기(append) 모드를 두지 않았다. 쓸 일이 드물고, 반쯤 필수인 인자가 하나 더 생기면 그만큼 틀릴 여지가 늘어난다.

요약하면, 모델이 중첩 구조를 만들거나 이스케이프를 신경 써야 하는 인자를 없애고, 모델이 흔히 쓰는 변형을 서버가 너그럽게 받아 주는 것이다.

## 4.6 모델의 기억에 기대야 한다면 되풀이해 준다

네임스페이스는 모델이 대화 내내 id를 기억해서 다시 보내야 작동한다. 모델의 기억은 믿을 만한 저장소가 아니다. 그래서 몇 겹의 장치를 두었다.

- id를 모델이 짓지 않는다. 약한 모델에게 id를 지어 보라고 하면 `"a"`, `"1"`, `"session"` 같은 뻔한 값을 지어 다른 대화와 겹치게 만든다. 서버가 `ns-3fa1`처럼 겹치지 않는 값을 발급한다.
- `namespace`를 필수 인자로 만들었다. 스키마가 필수라고 하면 모델은 호출할 때마다 이 인자를 의식하게 된다.
- 모든 응답의 맨 위와 맨 아래에 현재 id를 되풀이한다. 가장 최근 컨텍스트에 id가 있어야 앞선 대화가 잘려 나가도 모델이 계속 같은 값을 보낼 가능성이 높다.

이렇게 해도 완벽하지 않다. 컨텍스트가 크게 잘리면 모델은 id를 잃고 새 네임스페이스를 만든다. 그러면 불러 둔 데이터가 "사라진" 것처럼 보인다. 이 대책은 모델이 약할수록 덜 통하는데, 이 프로젝트가 상대하는 것이 바로 약한 모델이다. 진짜 해결책은 클라이언트가 요청마다 대화 id를 실어 보내는 것이고, 서버는 그 값을 읽을 자리를 미리 마련해 두었다([ADR-011](adr/adr-011-namespace-argument.md)).

일반화하면 이렇다. 정확성이 걸린 값은 가능한 한 모델의 기억 밖에 둔다. 어쩔 수 없이 모델에게 맡겨야 한다면, 그 값을 응답마다 되돌려 주어 모델이 베껴 쓰기만 하면 되게 만든다.

## 4.7 도구 사이의 경계를 분명히 한다

도구가 늘어나면 모델은 비슷한 도구 사이에서 잘못 고른다. 이 프로젝트의 도구는 3개에서 6개로 늘었고, 하나를 더할 때마다 경계를 정리했다.

- 코드 실행 도구의 설명문에는 "실행하지 않고 저장만 하려면 저장 도구를 써라, 그쪽이 더 간단하고 네임스페이스도 필요 없다"는 한 줄이 들어 있다. 두 도구가 겹치는 영역을 설명문에서 직접 나눠 준 것이다.
- 저장 도구가 스크립트 파일을 저장하면 응답 끝에 "`run_python_file`로 실행하라"는 힌트를 붙인다. 다음에 쓸 도구로 자연스럽게 이어 준다.
- 상태를 쓰지 않는 도구(저장, 목록)는 `namespace`를 받지 않는다. 필요 없는 필수 인자는 실패할 길만 하나 늘린다.

도구의 이름과 설명문을 바꿀 때는 이런 연결 문구도 함께 살펴야 한다. 한쪽만 고치면 경계가 다시 흐려진다.

## 4.8 관측할 수 없는 것은 약속하지 않는다

마지막 원칙은 정직함에 관한 것이다. 모델이 코드 안에서 `try`/`except`로 예외를 잡고 삼켜 버리면, 서버는 그 사실을 볼 방법이 없다. 커널 바깥에서는 관측할 수단이 없다. 이 프로젝트는 이 한계를 숨기지 않고 문서에 적었다. 그리고 판정의 최고 등급을 "검증되지 않음"으로 둔 것 자체가 이 한계를 인정한 결과다.

이 틈을 메울 방법으로 제안된 것이 검증식 인자다. 모델이 "이 조건이 참이면 성공"이라는 파이썬 식을 함께 보내면, 서버가 본 코드 실행 뒤에 따로 평가해서 참일 때만 "검증됨"을 준다. 모델은 증거를 내야만 성공이라는 말을 얻을 수 있다. 도구 스키마가 바뀌는 변경이라 아직 구현하지 않았다([ADR-018](adr/adr-018-expect-verification.md)).

## 4.9 점검표

지금까지의 원칙을 도구를 만들 때 쓸 수 있는 점검표로 정리한다.

| 점검 항목 | 이 프로젝트에서의 예 |
|---|---|
| 모델이 알아야 할 규칙이 설명문에 있는가? README에만 있지 않은가? | 실행 도구 설명문의 규칙 0~6 |
| 가벼운 도구에 무거운 규칙을 붙이지 않았는가? | 저장·목록 도구에는 규칙을 붙이지 않음 |
| 응답의 첫 줄이 결과의 등급을 말하는가? | `execution_status:`, `install_status:` |
| 응답의 마지막 줄이 다음 행동을 지시하는가? | `next_action:` |
| 긍정적인 판정은 서버가 실제로 확인한 사실인가? | `SUCCESS` 제거, 커널이 확인한 `INSTALLED` |
| 경보가 지나쳐 재시도 루프를 부르지 않는가? | `RAN_WITH_ERRORS`는 "확인하라"로 표현 |
| 거절 메시지에 해결 방법이 들어 있는가? | 덮어쓰기 거절, `RUNNING`의 재호출 지시 |
| 모델이 중첩 구조나 이스케이프를 만들어야 하는 인자가 있는가? | 저장 전용 도구, 문자열 하나로 받는 패키지 목록 |
| 필수 인자가 정말 필요한가? | 저장·목록 도구에는 `namespace`가 없음 |
| 모델이 기억해야 할 값을 응답마다 돌려주는가? | 네임스페이스 배너와 재안내 |
| 비슷한 도구끼리 설명문에서 서로를 가리키는가? | 실행 도구에서 저장 도구로 가는 한 줄 |
| 관측할 수 없는 것을 약속하고 있지 않은가? | 삼킨 예외는 볼 수 없다고 문서에 명시 |

## 생각해 볼 문제

1. `RAN_WITH_ERRORS`를 `FAILED`로 합치면 어떤 일이 생길까? 반대로 `RAN_UNVERIFIED`에 합치면?
2. 검증식 인자를 도입하면 약한 모델이 `assert True` 같은 의미 없는 검증식을 보내지 않을까? 이를 줄이려면 설명문이나 응답에 무엇을 넣어야 할까?
3. 응답 텍스트를 영어로 쓴 것은 모델이 읽기 때문이다. 사내 LLM이 한국어 데이터로 주로 학습된 모델이라면 응답을 한국어로 바꾸는 편이 나을까? 어떤 실험으로 판단할 수 있을까?
4. 여러분이 만들었거나 쓰고 있는 LLM 도구 하나를 골라 4.9의 점검표로 점검해 보자.
