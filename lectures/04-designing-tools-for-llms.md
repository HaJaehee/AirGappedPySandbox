# 4장. LLM을 위한 도구 설계

일반적인 소프트웨어 API는 사람 개발자가 직접 코드를 작성하여 호출합니다. 개발자는 인터페이스가 헷갈리면 공식 문서를 다시 찾아 읽고, 코드 예제를 검색하며, 디버거를 붙여 실행 과정을 추적합니다. 그러나 MCP 도구를 직접 호출하는 주체는 사람이 아닌 '대형 언어 모델(LLM)'입니다. 모델은 시스템 프롬프트에 주입된 도구 설명문(Description)을 읽고, 인자 값을 스스로 구성하여 호출하며, 반환된 결과 텍스트를 해석하여 다음 행동을 자율적으로 결정합니다. 모르는 것을 스스로 되묻지 않습니다. 특히 파라미터 규모가 작은 경량 모델일수록 길고 복잡한 설명문을 끝까지 주의 깊게 읽지 못하며, 반환 응답의 가장 앞머리와 끝부분 텍스트에 과도하게 의존하는 특성을 보입니다.

본 프로젝트에서 v0.4.0 이후 단행된 수많은 아키텍처 개선은 바로 이러한 LLM의 행동 특성을 체득해 온 기록입니다. 백엔드 코드는 설계한 규격대로 정상 동작했으나, 소형 모델이 그 반환 결과를 잘못 해석함으로써 최종 사용자에게 잘못되거나 왜곡된 답변이 전달되었습니다. 이번 장에서는 그 시행착오 과정에서 도출해 낸 핵심 도구 설계 원칙들을 체계적으로 정리해 드립니다. 이 원칙들은 본 프로젝트뿐만 아니라, LLM 에이전트와 연동되는 모든 외부 도구 인터페이스를 설계할 때 범용적으로 적용할 수 있는 실전 지침이 될 것입니다.

## 4.1 도구 설명문은 단순한 문서가 아니라 모델을 제어하는 프롬프트입니다

MCP 클라이언트는 서버로부터 수신한 도구 목록을 그대로 언어 모델의 시스템 프롬프트 컨텍스트에 주입합니다. 모델이 특정 도구에 대해 알 수 있는 정보는 도구 이름, 입력 JSON Schema, 그리고 설명문(Description) 텍스트가 전부입니다. 저장소에 작성해 둔 README나 아키텍처 문서는 모델의 시야에 전혀 들어오지 않습니다.

따라서 본 프로젝트는 코드 실행 계열 도구의 독스트링 설명문 내부에 번호를 매긴 핵심 사용 규칙들을 집중적으로 주입했습니다. 현재 적용되어 있는 규칙들을 정리하면 다음과 같습니다.

0. **네임스페이스 관리.** 첫 번째 호출 시에는 `"new"`를 전달하고, 이후 후속 대화에서는 이전 응답에 명시된 `active_namespace` 값을 그대로 전달하십시오.
1. **임의 설치 및 네트워크 호출 금지.** 실행 코드 내부에서 pip, apt, conda 명령을 실행하지 말고 외부 네트워크 소켓에 접속하지 마십시오. 필요한 라이브러리가 기본 목록에 없다면 패키지 설치 전용 도구를 호출하십시오. (이어서 기본 사전 설치된 30여 종의 라이브러리 목록이 제시됩니다.)
2. **명시적 콘솔 출력.** `print()`로 출력된 내용만이 모델에게 반환됩니다. 최종 계산 값과 요약 결과는 반드시 `print()` 함수로 감싸서 출력하십시오.
3. **시각화 차트 및 리포트 저장.** `plt.show()`를 호출하지 말고 `plt.savefig('chart.png')`로 파일 저장 후 `plt.close()`를 호출하십시오. Plotly 시각화는 `write_html` 메서드로 저장하십시오.
4. **파일 경로 표기.** 커널의 현재 작업 디렉터리가 곧 워크스페이스입니다. 경로 앞에 불필요하게 `./workspace/`를 덧붙이지 말고 순수 파일 이름만 사용하십시오. 워크스페이스는 다른 대화 세션과 공유되므로 파일명이 충돌하지 않도록 고유하게 작명하십시오.
5. **자가 오류 수정 (Self-Correction).** stderr에 에러 메시지가 출력되면 에러 트레이스백을 면밀히 분석하여 코드를 수정한 뒤, 동일한 네임스페이스를 유지하여 다시 실행하십시오.
6. **"실행 완료"는 "과업 성공"을 의미하지 않음.** 반환되는 판정 코드는 샌드박스 런타임이 기술적으로 관측한 사실만을 나타냅니다. 표준 출력이 사용자의 원래 질문에 실제로 정확한 정답을 제시하는지 모델 스스로 검증하기 전에는 사용자에게 성공했다고 보고하지 마십시오. 응답 최하단의 `next_action` 지침을 반드시 준수하십시오.

각 규칙은 현업 운영 중 실제로 마주쳤던 실패 사례들을 방어하기 위해 만들어졌습니다. 외부 인터넷이 차단된 폐쇄망에서 `pip install`을 시도하면 타임아웃에 걸려 한참 동안 멈췄다가 결국 실패합니다. 디스플레이 화면이 없는 헤드리스 커널에서 `plt.show()`를 호출하면 아무런 이미지 파일도 디스크에 남지 않습니다. 복잡한 계산 코드를 열심히 실행해 놓고 `print()`를 누락하면 정작 모델에게는 아무런 결과 숫자가 돌아오지 않습니다. 도구 설명문 내부의 규칙은 이러한 전형적인 실수들을 사전에 방지하는 가이드라인 역할을 수행합니다.

그러나 설명문에 규칙을 추가하는 데는 명확한 토큰 비용이 발생합니다. 위 규칙 묶음만 해도 도구 하나당 500토큰에 가까운 귀중한 프롬프트 컨텍스트를 소모합니다. 따라서 이러한 상세 규칙은 실제 코드를 동적으로 평가하는 두 가지 실행 도구에만 전략적으로 배치하고, 단순 파일 저장 도구나 목록 조회 도구에는 일절 포함하지 않았습니다. 가볍고 단순하게 사용되어야 할 유틸리티 도구의 설명문을 무겁게 만들면 도구의 효용성이 떨어지기 때문입니다. 더욱이 규칙의 0번 항목은 `namespace` 인자의 사용을 강제하고 있는데, 파일 저장 도구는 애초에 `namespace` 인자를 받지 않는 무상태 도구입니다. 만약 여기에 동일한 규칙을 일괄 주입했다면 소형 모델은 심각한 인자 혼란에 빠졌을 것입니다.

더 나아가 텍스트 규칙만으로는 근본적인 한계가 존재합니다. 추론 능력이 취약한 소형 모델은 아무리 잘 작성된 규칙이라도 문장이 길어지면 끝까지 준수하지 못하고 무시해 버립니다. v0.5.0 설계 당시 개발팀이 내린 가장 중요한 결론은 다음과 같았습니다. "소형 모델은 복잡한 프롬프트 규칙은 흘려 읽어도, 반환된 응답 텍스트의 첫 줄만큼은 반드시 읽는다." 즉, 모델을 긴 텍스트 지침으로 설득하려 들지 말고, 도구가 반환하는 응답의 물리적 레이아웃 자체로 모델의 후속 행동을 유도해야 한다는 통찰입니다.

## 4.2 가장 중요한 정보는 반드시 첫 줄과 마지막 줄에 배치해야 합니다

대형 언어 모델은 긴 텍스트의 중간에 위치한 정보보다, 텍스트의 가장 앞부분(Primacy Effect)과 가장 뒷부분(Recency Effect)에 위치한 문장을 압도적으로 주의 깊게(Attention) 참조합니다. 이 인지적 특성을 고려하여 아키텍처에 적극 반영했습니다. v0.5.0 이후 코드 실행 도구의 응답 텍스트는 다음과 같은 고정 템플릿으로 엄격하게 배치됩니다.

```
execution_status: RAN_WITH_ERRORS                  ← [첫 줄] 기계 판정 등급
The code finished, but errors were reported ...     ← 판정 등급의 정확한 의미

active_namespace: ns-3fa1                           ← 현재 세션 네임스페이스 안내
Reusing your namespace. Keep passing namespace="ns-3fa1".

--- stderr ---                                      ← 판정의 객관적 근거를 최우선 노출
...

--- stdout ---                                      ← 일반 표준 출력 스트림
rc ignored

--- artifacts ---                                   ← 생성된 파일 산출물 링크
(no new files created in the workspace)

[reminder] your namespace = "ns-3fa1" -- ...        ← 후속 호출을 위한 세션 ID 리마인더
next_action: Treat this as unfinished until you ... ← [마지막 줄] 모델이 취해야 할 행동 지침
```

시스템이 내린 최종 실행 판정이 최상단 첫 줄에 위치하고, 모델이 즉시 수행해야 할 행동 지침이 최하단 마지막 줄에 배치됩니다. 표준 에러(stderr) 스트림을 표준 출력(stdout)보다 위쪽에 먼저 배치한 이유 역시 동일합니다. 만약 실행 결과가 `FAILED`나 `RAN_WITH_ERRORS`라면 그 결정적인 원인은 stderr에 적혀 있으므로, 모델이 판정 코드를 읽자마자 그 실패의 기술적 근거를 즉시 시야에 담을 수 있도록 유도한 것입니다.

특히 마지막 줄의 `next_action`은 모호한 설명이 아닌 명확한 단문 명령형으로 작성됩니다. "사용자에게 임의로 성공했다고 보고하지 마십시오. stderr의 트레이스백을 정밀 분석하여 코드를 수정한 뒤 동일한 네임스페이스로 즉시 재실행하십시오"와 같이 구체적인 행동을 직접 지시합니다. 판정 상태마다 지침 문구가 동적으로 변경되며, 소형 모델이 다음에 무엇을 해야 할지 고민하다가 환각을 일으키지 않도록 확실한 가이드라인을 제공합니다.

이 레이아웃 철학은 패키지 설치 도구에도 동일하게 적용되었습니다. 최상단 첫 줄은 `install_status:`로 시작하고, 최하단 마지막 줄은 `next_action:`으로 끝납니다. 시스템 내의 모든 도구가 동일한 응답 구조를 공유하면, 모델이 하나의 도구 인터페이스에 적응한 후 다른 도구의 결과도 일관된 방식으로 수월하게 해석할 수 있습니다.

## 4.3 시스템이 객관적으로 확인하지 못한 성공은 절대 성공이라고 말하지 않습니다

초기 v0.4.1 버전까지 코드 실행 도구가 반환하던 상태 값은 `SUCCESS`, `ERROR`, `TIMEOUT`의 단순한 3가지였습니다. 당시 `SUCCESS`의 기술적 실체는 단순히 "인터프리터 밖으로 처리되지 않은 예외가 튀어나오지 않았다"는 뜻에 불과했습니다. 그러나 언어 모델은 이 단어를 "사용자가 요청한 과업이 완벽히 끝났다"라고 단정적으로 해석했습니다. 실제로 과거 기록을 정밀 분석해 보니 다음과 같은 심각한 오류 상황들이 전부 `SUCCESS`로 둔갑하여 모델에 전달되고 있었습니다.

| 실행된 Python 코드 예시 | 당시 반환 상태 | 실제로 발생한 런타임 현상 |
|---|---|---|
| `logging.error('db unreachable')` | SUCCESS | stderr에 치명적인 데이터베이스 에러 로그가 기록되었습니다. |
| `traceback.print_exc()` | SUCCESS | 코드가 예외를 임의로 try-except로 잡아서 화면에 트레이스백만 출력했습니다. |
| 백그라운드 스레드 내부 크래시 | SUCCESS | 워커 스레드가 비정상 종료(크래시)되었으나 메인 스레드는 정상 종료되었습니다. |
| `subprocess.run(...)` 종료 코드 3 | SUCCESS | 하위 CLI 프로세스가 실패 코드를 반환했습니다. |
| `x = 1` | SUCCESS | 콘솔에 아무런 출력도 남기지 않았습니다. |
| `sys.exit(0)` | **ERROR** | 정상적인 스크립트 종료였음에도 IPython의 예외 처리로 인해 에러로 판정되었습니다. |

모델은 첫 줄의 `SUCCESS` 단어만 보고 곧바로 사용자에게 "요청하신 작업을 성공적으로 완료했습니다!"라고 잘못 보고했습니다. 반면 마지막 행처럼 지극히 정상 종료된 스크립트가 `ERROR`로 잘못 보고되자, 모델은 아무런 문제가 없는 코드를 "오류를 고치겠다"며 엉뚱하게 수정하고 불필요한 재실행을 반복했습니다.

이 결함을 바로잡기 위해 단순히 용어 몇 개를 교체하는 데 그치지 않고, 샌드박스 시스템이 **객관적으로 증명할 수 있는 영역**과 **증명할 수 없는 영역**의 경계를 명확히 설정했습니다. 런타임 샌드박스는 기술적 '실패'는 완벽히 증명할 수 있습니다. 예외가 발생했고, 종료 코드가 0이 아니며, 스레드가 비정상 종료되었다는 사실은 시스템 관측을 통해 100% 포착할 수 있습니다. 그러나 '과업의 성공'은 샌드박스가 결코 증명할 수 없습니다. 실행된 코드가 사용자의 원래 질문 의도나 비즈니스 논리에 부합하는지 여부는 오직 사용자의 지시를 직접 전달받은 LLM 모델만이 판단할 수 있습니다.

따라서 전면 개편된 판정 체계에서는 가장 완벽하게 실행된 경우라 할지라도 `RAN_UNVERIFIED`("인터프리터는 예외 없이 통과했으나 과업 성공 여부는 검증되지 않았음")라는 신중한 등급을 부여합니다. 모호하고 위험한 `SUCCESS`라는 단어는 코드 실행 도구의 판정 어휘에서 완전히 제외했습니다.

| 개편된 실행 판정 등급 | 판정의 정확한 의미와 한계 |
|---|---|
| `RAN_UNVERIFIED` | 코드가 예외 없이 실행을 마쳤습니다. 그러나 요청된 과업이 실제로 성공했음을 보장하지는 않습니다. |
| `RAN_NO_OUTPUT` | 코드가 정상 종료되었으나 표준 출력도 없고 생성된 파일도 전혀 없어 실제 수행 내용을 확인할 수 없습니다. |
| `RAN_WITH_ERRORS` | 코드가 끝까지 실행되었으나 실행 과정에서 오류 로그나 하위 프로세스 실패가 포착되었습니다. |
| `FAILED` | 처리되지 않은 예외가 발생했거나, 0이 아닌 종료 코드로 끝났거나, 도구 입력 검증 단계에서 거절되었습니다. |
| `TIMEOUT` | 허용된 시간 예산을 초과하여 인터럽트 또는 강제 프로세스 재시작 조치가 단행되었습니다. |

물론 반대 방향의 과도한 경보 역시 경계해야 합니다. 시스템의 경고가 너무 엄격하면 모델이 불필요한 수정 루프(Retry Loop)에 영구히 갇히게 됩니다. 만약 무해한 `logging.warning`이나 정보성 경고 로그에도 무조건 `FAILED` 판정을 내려버린다면, 소형 모델은 아무런 문제가 없는 코드를 고치겠다며 혼란에 빠질 것입니다. 따라서 `RAN_WITH_ERRORS`는 '치명적 실패'가 아닌 '결과를 사용자에게 보고하기 전에 면밀히 재확인하라'는 중립적인 뉘앙스로 전달합니다. `next_action` 지침 역시 "실제 결함이라면 수정하여 재실행하고, 무해한 로그라면 사용자에게 정직하게 설명하라"는 균형 잡힌 가이드를 제공합니다. 아울러 stdout에 `FAIL`이라는 문자열이 우연히 출력되었다고 해서 판정을 흔들지 않는 원칙을 고수합니다.

이 엄격한 정직성 원칙은 패키지 설치 도구에도 철저히 관철되었습니다. pip 프로세스가 리턴 코드 0으로 끝났다는 사실은 단지 인터넷에서 파일 다운로드가 완료되었다는 의미일 뿐, 현재 실행 중인 커널에서 해당 패키지를 실제로 import할 수 있다는 증거가 되지 못합니다. 따라서 `INSTALLED` 상태는 커널이 각 패키지의 설치 버전을 내부 API를 통해 직접 증명해 냈을 때만 부여됩니다. 반면 파일 저장 도구(`write_workspace_file`)는 명시적으로 `SUCCESS` 상태를 사용합니다. 파일 디스크 쓰기는 MCP 서버 자신이 직접 수행한 I/O 작업이며, 기록된 바이트 수를 서버가 100% 완벽하게 확인할 수 있기 때문입니다. 기준은 하나로 수렴합니다. **"시스템이 직접 확인하고 보증할 수 있는 사실만을 긍정한다."**

## 4.4 요청을 거절할 때는 반드시 구체적인 해결 방법까지 함께 안내해야 합니다

소형 언어 모델은 "규칙을 위반했습니다"라는 추상적인 경고 문구보다, "이렇게 인자를 수정하여 다시 호출하십시오"라는 구체적인 가이드라인을 훨씬 더 정확하게 준수합니다. 본 시스템의 모든 에러 및 거절 응답은 반드시 실질적인 해결 대안을 함께 담아 반환됩니다.

| 거절 및 실패 발생 상황 | 도구 응답이 제공하는 구체적인 해결 대안 |
|---|---|
| 저장하려는 파일명이 이미 워크스페이스에 존재합니다. | `overwrite=true` 옵션을 추가하여 다시 호출하거나 다른 고유한 파일명을 사용하십시오. |
| 실행하려는 스크립트 파일이 디스크에 존재하지 않습니다. | 먼저 `list_workspace_files` 도구를 호출하여 현재 존재하는 정확한 파일명을 확인하십시오. |
| 패키지 설치 인자에 URL이나 pip CLI 옵션 플래그가 섞여 있습니다. | 어떤 토큰이 잘못되었는지 정확히 짚어주고, 순수 패키지 명칭만을 공백으로 구분하여 다시 전달하십시오. |
| 대용량 패키지 설치 작업이 백그라운드에서 진행 중입니다 (`RUNNING`). | 정확히 동일한 `packages` 문자열과 `namespace` 인자를 사용하여 지금 즉시 도구를 재호출하십시오. |
| 사내 미러가 구성되지 않아 패키지 설치에 최종 실패했습니다. | 동일한 설치를 무의미하게 반복하지 마십시오. 사용자에게 "사내 PyPI 미러 설정이 필요하다"는 사실을 명확히 안내하십시오. |
| `namespace` 인자 없이 커널 상태 초기화를 요청했습니다. | 초기화하고자 하는 정확한 세션 ID(`ns-XXXX`)를 인자로 지정해 주십시오. |

위 표에서 5번째 항목(미러 미설정 안내)에 주목해 주시기 바랍니다. 사용자 PC의 환경 변수 누락 문제는 LLM 모델이 코드를 아무리 수정하고 재시도하더라도 스스로 해결할 수 없는 외부 인프라 문제입니다. 이러한 경우 모델의 맹목적인 무한 재시도를 즉각 차단하고, 최종 사용자에게 전달해야 할 정확한 문제 안내 문구를 직접 쥐여주는 것이 도구의 중요한 역할입니다.

또한 도구가 유효성 검증 실패로 인해 요청 자체를 사전 거절할 때도, 일반적인 코드 실행 실패 응답과 동일한 텍스트 구조로 응답합니다. 최상단 첫 줄은 `execution_status: FAILED`로 시작하며, 바로 다음 줄에 "도구 사전 검증에서 거절되었으므로 코드는 커널에서 전혀 실행되지 않았음"을 명시합니다. 응답의 구조가 일관되면 모델은 거절 상황을 별도의 복잡한 예외 분기로 처리할 필요 없이 기존 오류 대응 흐름과 동일하게 매끄럽게 처리할 수 있습니다.

## 4.5 인자 스키마는 최대한 단순(Flat)하게, 입력 형태는 직관적으로 유지해야 합니다

v0.4.0 이전 버전에서는 "피보나치 수열을 구하는 코드를 작성하여 fib.py라는 파일로 저장해 줘"라는 사용자의 단순한 요청을 처리하기 위해 소형 모델이 다음과 같이 복잡한 Python 코드를 직접 작성해야 했습니다.

```python
source = '''def fib(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

if __name__ == "__main__":
    print(sum(fib(i) for i in range(1, 11)))
'''
with open("fib.py", "w", encoding="utf-8") as f:
    f.write(source)
```

코드 문자열 내부에 또 다른 코드가 중첩되는 기이한 자기 참조(Self-referential) 구조가 형성됩니다. 따옴표가 이중 삼중으로 겹치고, 저장할 소스코드 안에 docstring이나 역슬래시(`\`)가 포함되어 있다면 이스케이프(Escape) 처리까지 신경 써야 합니다. 소형 언어 모델은 이러한 중첩 문자열 생성 작업에서 높은 확률로 문법 오류를 일으키며 실패합니다. 가장 흔하게 발생했던 실패 증상은 파일 저장 로직을 통째로 누락한 채 피보나치 계산 결과만을 콘솔에 출력하고 끝내는 패턴이었습니다.

이 문제에 대한 근본적인 해법은 단 두 개의 문자열 인자(`filename`, `content`)만을 받는 전용 파일 저장 도구(`write_workspace_file`)를 새롭게 분리하는 것이었습니다. 파일 이름과 파일 본문을 서로 분리된 독립 인자로 수신하자 복잡한 따옴표 중첩 문제가 완벽히 해소되었습니다([ADR-014](adr/adr-014-write-file-tool.md)). 이 단순화 철학은 시스템의 다른 모든 인터페이스에도 일관되게 적용되었습니다.

- 패키지 설치 도구의 `packages` 인자는 복잡한 JSON 문자열 배열 형태가 아닌, 단순한 단일 텍스트 문자열입니다. `"polars, rapidfuzz>=3.0"`과 같이 쉼표나 공백으로 자연스럽게 나열하도록 설계했습니다. 소형 모델은 정형화된 JSON 배열보다 평범한 구분자 문자열을 훨씬 더 안정적으로 생성해 냅니다.
- 새로운 네임스페이스 생성을 요청할 때 표준 규격은 `"new"` 문자열이지만, 모델이 실수로 빈 문자열(`""`)을 넘기거나 `"auto"`, `"default"`, `"none"`, `"null"`과 같은 유사 단어를 전달하더라도 서버가 동일한 신규 세션 발급 요청으로 유연하게 수용합니다.
- 파일 경로 인자 역시 모델이 순수 파일명(`fib.py`)으로 전달하든 경로 접두사가 포함된 상대 경로(`workspace/fib.py` 또는 `./workspace/fib.py`)로 전달하든 동일한 파일 위치로 투명하게 정규화하여 처리합니다.
- 파일 저장 도구에 복잡한 이어 쓰기(Append) 모드를 의도적으로 추가하지 않았습니다. 실무에서 거의 쓰이지 않는 부가 옵션 인자가 하나 더 늘어나면, 그만큼 소형 모델이 인터페이스를 오해하고 잘못 호출할 수 있는 위험만 넓어지기 때문입니다. 응답 한 번에 담을 수 없는 긴 파일이 실제로 필요해졌을 때(v0.8.0)에도 이 원칙을 지켜, 저장 도구에 인자를 더하는 대신 이름이 곧 동작인 별도 도구 `append_workspace_file`을 추가했습니다([ADR-022](adr/adr-022-append-tool.md)).

요약하자면, 모델이 복잡한 중첩 구조를 만들거나 이스케이프 규칙을 신경 써야 하는 인자 형태를 시스템에서 배제하고, 모델이 흔히 저지르는 사소한 변형 표현들을 서버 계층에서 최대한 너그럽게 포용하도록 설계하는 것입니다.

## 4.6 모델의 불안정한 기억력에 의존해야 한다면 서버가 끊임없이 되풀이해 주어야 합니다

네임스페이스 기반의 세션 격리 아키텍처는 모델이 대화가 이어지는 내내 자신의 세션 ID를 성실히 기억하여 다음 호출 시 인자로 다시 전달해 주어야만 정상 작동합니다. 그러나 소형 언어 모델의 단기 기억력은 결코 신뢰할 수 있는 저장소가 아닙니다. 따라서 모델이 ID를 잊어버리지 않도록 다중 안전장치를 구축했습니다.

- 모델에게 세션 ID를 스스로 작명하도록 허용하지 않습니다. 약한 모델에게 ID 작명을 맡기면 `"a"`, `"1"`, `"session"`, `"test"`와 같이 지극히 단순한 값을 지어내어 다른 대화 세션의 커널을 오염시키는 충돌을 유발합니다. 반드시 서버가 `ns-3fa1`과 같은 무작위 고유 ID를 발급하여 전달합니다.
- `namespace` 매개변수를 도구 스키마의 '필수(Required) 인자'로 엄격히 선언했습니다. 필수 인자로 지정해 두어야만 모델이 도구를 호출할 때마다 세션 ID의 존재를 강하게 의식하게 됩니다.
- 도구가 반환하는 모든 응답 텍스트의 최상단 배너와 최하단 리마인더 구역에 현재 활성화된 세션 ID를 지속적으로 되풀이하여 출력합니다. 가장 최근 컨텍스트 윈도우에 ID 문자열이 선명하게 노출되어 있어야만, 이전 대화가 토큰 한도로 인해 잘려 나가더라도 모델이 올바른 세션 ID를 계속해서 재사용할 수 있습니다.

물론 이러한 프롬프트 수준의 방어책이 100% 완벽할 수는 없습니다. 대화가 매우 길어져 컨텍스트가 대폭 잘려 나가면, 모델은 결국 세션 ID를 분실하고 무심코 `namespace="new"`를 전달하게 됩니다. 그 순간 이전 대화에서 메모리에 적재해 둔 수많은 분석 데이터들이 한순간에 사라진 것처럼 보이는 한계에 직면합니다. 이 한계는 모델의 체급이 작을수록 더 자주 발생합니다. 이 문제의 가장 근본적인 최종 해결책은 클라이언트 데스크톱 앱(AnythingLLM)이 매 도구 호출 요청마다 대화 세션 ID를 프로토콜 수준에서 자동으로 실어 보내는 것이며, 본 MCP 서버는 향후 클라이언트가 이 기능을 지원할 때 즉시 수신할 수 있는 컨텍스트 통로를 이미 구축해 두었습니다([ADR-011](adr/adr-011-namespace-argument.md)).

이 경험에서 도출할 수 있는 일반화된 설계 원칙은 다음과 같습니다. "시스템의 정확성을 좌우하는 중요한 상태 값은 가능한 한 모델의 취약한 기억력 외부에 보관하십시오. 만약 어쩔 수 없이 모델의 컨텍스트를 경유해야만 한다면, 그 값을 매 응답마다 친절하게 되돌려 주어 모델이 단순히 복사하여 붙여넣는 수준으로만 동작하도록 설계하십시오."

## 4.7 유사한 도구 사이의 책임 경계를 명확히 분리하고 상호 안내해야 합니다

서버가 제공하는 도구의 종류가 많아질수록 모델은 유사한 목적을 가진 도구들 사이에서 어떤 것을 선택해야 할지 혼란에 빠집니다. 본 프로젝트의 도구는 초기 3개에서 현재 6개로 확장되었으며, 새로운 도구를 추가할 때마다 기존 도구들과의 경계를 명확히 구획하는 작업을 병행했습니다.

- 일반 코드 실행 도구(`execute_python_code`)의 독스트링 설명문에는 "코드를 실행하지 않고 순수 파일로 저장만 하려는 목적이라면 `write_workspace_file` 도구를 사용하십시오. 그 방식이 훨씬 안전하고 복잡한 네임스페이스도 필요 없습니다"라는 명시적인 안내 문구를 주입했습니다. 두 도구의 기능적 교집합 영역을 설명문 수준에서 선제적으로 정리해 준 것입니다.
- 파일 저장 도구가 `.py` 확장자를 가진 스크립트 파일을 성공적으로 기록했을 때는, 반환 응답 최하단에 "방금 저장된 스크립트를 즉시 실행하려면 `run_python_file` 도구를 호출하십시오"라는 실전 힌트를 자동으로 덧붙입니다. 이를 통해 모델이 다음 워크플로 단계로 자연스럽게 전환할 수 있도록 유도합니다.
- 상태를 공유할 필요가 없는 유틸리티 도구(파일 저장, 파일 목록 조회)는 애초에 `namespace` 인자를 받지 않도록 스키마를 철저히 분리했습니다. 불필요한 필수 인자가 스키마에 포함되어 있으면 모델이 도구를 오판하고 호출에 실패할 확률만 높아지기 때문입니다.

도구의 이름이나 설명문을 수정할 때는 이러한 교차 참조 힌트 문구들도 반드시 함께 점검해야 합니다. 어느 한쪽만 수정하고 연계 힌트를 방치하면 도구 간의 경계가 다시 흐려져 모델의 오작동을 유발하게 됩니다.

## 4.8 시스템이 직접 관측할 수 없는 영역은 섣불리 약속하지 않습니다

마지막 설계 원칙은 시스템의 '엔지니어링 정직성'에 관한 것입니다. 만약 사용자가 작성한 코드 내부에서 광범위한 `try: ... except Exception: pass` 블록을 사용하여 모든 런타임 예외를 조용히 집어삼켜 버렸다면, 샌드박스 런타임은 백그라운드에서 무슨 치명적인 결함이 발생했는지 감지할 방법이 없습니다. 커널 프로세스 외부에서는 인터프리터 내부의 침묵하는 논리적 실패를 관측할 물리적 수단이 존재하지 않기 때문입니다.

본 프로젝트는 이러한 런타임의 내재적 한계를 결코 감추거나 외면하지 않고 문서에 솔직하게 명시했습니다. 그리고 판정 체계의 최상위 등급을 섣불리 '성공'이라 부르지 않고 `RAN_UNVERIFIED`("검증되지 않은 실행")로 선언한 것 자체가 바로 이러한 불완전성을 정직하게 수용한 결과입니다.

이 관측의 사각지대를 메우기 위한 차세대 해법으로 제안된 것이 바로 **검증식 인자 (Expect Verification)**입니다. 모델이 실행 코드와 함께 "이 논리 조건식이 True로 평가되어야만 과업이 성공한 것이다"라는 명시적인 Python 단언식(예: `len(df) > 0 and 'total' in df.columns`)을 도구 인자로 동봉하여 전달하는 방식입니다. 서버는 본 코드가 실행된 직후 이 검증식을 동일한 커널 세션에서 독립적으로 평가하여 참으로 확인되었을 때만 비로소 '검증된 성공' 판정을 발급합니다. 즉, 모델 스스로 자신의 작업 결과에 대한 객관적인 증거를 시스템에 제출하도록 요구하는 구조입니다. 이는 도구 스키마의 대대적인 확장을 수반하는 변경이므로 현재는 정식 채택 전 제안 단계로 유지되고 있습니다([ADR-018](adr/adr-018-expect-verification.md)).

## 4.9 LLM 친화적 도구 설계를 위한 실전 자가 점검표

지금까지 살펴본 핵심 원칙을 실무에서 도구를 개발할 때 즉각 활용할 수 있는 점검 체크리스트로 정리해 드립니다.

| 자가 점검 항목 | 본 프로젝트에서의 구체적 적용 사례 |
|---|---|
| 모델이 반드시 숙지해야 할 핵심 제약과 규칙이 도구 설명문(Description)에 명시되어 있습니까? | 코드 실행 도구 설명문에 주입된 0~6번 상세 사용 규칙 |
| 단순 유틸리티 도구에 불필요하게 무거운 설명문 규칙을 남발하지 않았습니까? | 파일 저장 도구 및 목록 조회 도구에는 복잡한 네임스페이스 규칙을 과감히 생략 |
| 반환 응답의 최상단 첫 줄이 시스템의 객관적인 실행 등급을 명확히 선언하고 있습니까? | `execution_status:`, `install_status:`의 첫 줄 고정 노출 |
| 반환 응답의 최하단 마지막 줄이 모델의 다음 행동 지침을 명확히 지시하고 있습니까? | `next_action:` 단문 명령형 지침의 최하단 배치 |
| 긍정적인 반환 판정은 시스템이 실제로 직접 검증 완료한 객관적 사실에 기반합니까? | 모호한 `SUCCESS` 제외, 커널 API로 버전을 직접 검증한 `INSTALLED` 도입 |
| 시스템의 경고 수준이 지나치게 민감하여 모델을 무한 재시도 루프에 빠뜨리지 않습니까? | `RAN_WITH_ERRORS`를 치명적 실패가 아닌 신중한 '사전 확인 권고'로 완화 |
| 도구 호출 거절 메시지에 구체적인 해결 대안과 수정 가이드가 함께 포함되어 있습니까? | 덮어쓰기 거절 시 `overwrite=true` 안내, `RUNNING` 상태 시 동일 인자 재호출 지시 |
| 모델이 복잡한 중첩 문자열 구조나 까다로운 이스케이프를 작성해야 하는 인자가 존재합니까? | 전용 파일 저장 도구 분리, 패키지 목록을 평평한 단일 텍스트 문자열로 수용 |
| 필수(Required)로 선언된 인자가 정말로 모든 시나리오에서 반드시 필요합니까? | 상태를 쓰지 않는 저장 및 목록 조회 도구에서 `namespace` 인자를 과감히 제거 |
| 대화 간에 유지되어야 할 핵심 상태 값을 시스템이 매 응답마다 친절히 되돌려주고 있습니까? | 상단 네임스페이스 배너 및 하단 세션 리마인더 반복 주입 |
| 기능이 유사한 도구들이 각자의 설명문에서 상호 역할 분담을 명확히 안내하고 있습니까? | 코드 실행 도구에서 파일 저장 전용 도구로의 명시적 전환 안내 |
| 시스템이 물리적으로 관측할 수 없는 영역에 대해 거짓된 보장을 약속하고 있지 않습니까? | 삼켜진 예외의 관측 불가성을 문서에 솔직히 인정하고 `RAN_UNVERIFIED` 등급 유지 |

## 생각해 볼 문제

1. 판정 체계에서 `RAN_WITH_ERRORS` 등급을 완전히 없애고 전부 `FAILED`로 통합해 버린다면 실제 소형 LLM의 대화 흐름에서 어떤 부작용이 발생하겠습니까? 반대로 `RAN_UNVERIFIED`와 통합해 버린다면 어떤 위험이 초래되겠습니까?
2. 4.8절의 검증식(`expect`) 인자를 도입할 경우, 추론 능력이 다소 부족한 소형 모델이 판정 통과만을 노리고 `assert True`나 `1 == 1`과 같은 무의미한 항진식을 남발할 위험이 있습니다. 이러한 모델의 우회 시도를 방지하고 실질적인 검증식을 유도하려면 도구 설명문이나 반환 응답에 어떤 제도적 장치를 추가해야 하겠습니까?
3. 본 시스템의 도구 응답 텍스트가 모두 영어로 작성된 이유는 대상 모델의 언어적 이해 특성을 고려했기 때문입니다. 만약 사내에 도입된 LLM이 한국어 코퍼스를 중심으로 파인튜닝된 한국어 특화 모델이라면 도구 응답을 한국어로 전면 개편하는 것이 바람직하겠습니까? 이를 객관적으로 검증하기 위해 어떤 A/B 테스트 실험을 설계하시겠습니까?
4. 여러분이 실무에서 직접 개발하였거나 현재 사용 중인 사내/오픈소스 LLM 도구 하나를 임의로 선정하여, 4.9절의 점검표 항목들을 바탕으로 모델 친화성 관점에서 냉정하게 진단해 보시기 바랍니다.
